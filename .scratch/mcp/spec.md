# SolidTrace MCP server

Status: ready-for-agent

**Origin:** the plan the user approved on 2026-10-17. This file is the spec. Departures go in Implementation decisions at the end. Tickets are in [issues/](issues/).

## Context

The user wants SolidTrace to have an MCP server that lets an agent do almost anything, as Sentry's and Better Stack's do. It builds on the logs v2 work on `feature/logs-v2`: Queries, SQL, Charts, Dashboards and Monitors are its core, plus Issues and a few admin actions. Today Console has only cookie sessions. The `api/v1` routes point at controllers that don't exist, and there is no Field list outside the browser. The goal is one MCP URL, added to Claude Code or Cursor with a token, where an agent acts as the token's user, with the rights that user has in the UI.

**Decided with the user (2026-10-17):**
- **Auth:** API tokens made in User settings and sent as `Authorization: Bearer`. No OAuth in v1; it can come later, since only the way a token is obtained would change.
- **Scope:** the logs work and Issues, plus admin actions: create a Project, manage keys, invite members. Membership is per Organization; there are no Project members.
- **Authorization:** a token names a user, not a role. Each tool call reads that user's role in the Organization it acts on and runs the same policy as the UI.
- **SQL:** `run_sql` is listed only while the instance setting allows SQL queries. SQL queries become read-only everywhere, in the UI and the MCP (G2), so `run_sql` is a read tool, not marked destructive.
- **Keys become admin-only** in both the UI and the MCP. Creating a Project stays open to any member.

## Design

**Where it runs:** inside Console, at `POST /mcp`. It uses the official `mcp` gem (1.8.0), with `MCP::Server::Transports::StreamableHTTPTransport.new(server, stateless: true, enable_json_response: true)` driven from a controller via `handle_request`. Console owns users, membership, policies and the EventStore client with its timeouts and the `ChartRuns` cap; EventStore knows only Project keys. This follows the reasoning of ADR 0006. Stateless JSON means no SSE stream holds a Puma thread. Query tools go through `ChartRuns.hold` and `EventStoreProxy::RUN_TIMEOUT_SECONDS` (30 s), as a Dashboard chart does. Record this as ADR 0009 (MCP in Console, API tokens), with the options considered:
- the MCP in EventStore (Go), which knows only Project keys, not users or roles;
- a stdio program each developer installs;
- OAuth sign-in in v1, deferred. It is needed for claude.ai's and ChatGPT's web connectors, and can be added later without changing the tools or their permission checks, since an OAuth token also names a user.

**Tokens:**
- An `api_tokens` table: `user_id`, `name`, `token_digest` (SHA-256 of a high-entropy `st_…` secret, looked up by digest), `last_used_at` and `created_at`.
- Revoking a token deletes its row.
- `last_used_at` is written at most once a minute, so as not to take SQLite's write lock on every call.
- The User settings page makes a token, shows it once with copy-paste snippets (`claude mcp add --transport http solidtrace <console>/mcp --header "Authorization: Bearer …"` and Cursor's JSON), lists tokens by name, creation and last use, and revokes them.

**Each request:**
1. `McpController < ActionController::API` reads the Bearer token. A missing or unknown one gets a `401` with `WWW-Authenticate: Bearer`.
2. It builds an `MCP::Server` with `server_context: { user:, console_url: }` and the tool list. `run_sql` is in the list only while `InstanceSetting.current.sql_queries_enabled?`.
3. It hands the request to the transport.

**Tool base** (`console/app/mcp/`):
- Resolves `organization` (a slug; optional when the user has exactly one Organization, and the error lists the choices otherwise) and `project` (a slug within it).
- Runs Pundit policies.
- Turns failures into tool errors (`isError: true`) the model can act on:
  - `EventStore::Rejected` returns the Query's mistakes with their positions.
  - `ChartRuns::Busy` says "busy, run again in a moment".
  - `TimedOut` suggests a shorter range.
  - `SQLQueriesOff`.
  - `Pundit::NotAuthorizedError` says "only an Organization admin can …".
  - `RecordNotFound` names the tool that lists the valid values.
- Read tools, `run_sql` among them, carry `readOnlyHint`. Deletes and key rotation carry `destructiveHint`.

**Small, linked answers:**
- Objects are compact JSON.
- Logs are one line each: time, level, service, a message cut at about 500 characters, a few Attributes and the id. Default 50, at most 200, with the next cursor. `get_log` returns the whole Log.
- Tables are a header plus at most 100 rows, with "N more: narrow the Query".
- Every answer ends with its Console link: the explorer with that Query and range (built as `lib/logs/explorerState.ts` reads its URL), a Dashboard, a Monitor or an Issue.
- Ranges are `range` (`15m`, `1h`, `24h`, `7d`; default `1h`) or ISO 8601 `from`/`to`.

**Tool catalogue:**

| Area | Tools |
|---|---|
| Context | `whoami` (user, Organizations, role in each), `list_projects` |
| Logs | `query_logs`, `get_log`, `list_fields`, `query_language_reference`, `run_sql` (when SQL is on) |
| Dashboards | `list_dashboards`, `get_dashboard`, `create_dashboard`, `update_dashboard`, `delete_dashboard`, `add_chart`, `update_chart`, `delete_chart`, `get_chart_data` |
| Monitors | `list_monitors` (firing groups, last run), `get_monitor` (states, last runs), `create_monitor`, `update_monitor` (including on/off), `delete_monitor`, `run_monitor`, `list_integrations` (read-only: id, name, provider, enabled) |
| Issues | `list_issues`, `get_issue` (latest or a given Event: exception, top frames, tags, trace id, with a hint to `query_logs where trace_id == …`), `update_issue` (resolve or unresolve, assign by email or `unassigned`), `add_comment` |
| Admin | `create_project`, `get_project_setup` (DSN, Log ingest URL and key, a curl example), `create_key`, `rotate_key`, `delete_key`, `list_members`, `invite_member` |

`query_logs`'s description carries a short cheat sheet: stages, `where`, `summarize count() by bin_auto(time)`, and the rule that a number only matches a number. `query_language_reference` returns `docs/logs/query-language.md`. The Console image is built from `console/` only, so a copy lives in `console/app/mcp/docs/`, and a test fails when the two differ.

**Code that moves out of controllers**, so the MCP and the UI share it rather than copy it:
- `MonitorsController#save`, `#checked_save` and `#integrations_param` move to `LogMonitor`, saving the Monitor with its Integrations and checking the Query before the transaction.
- `ChartRunning#run_chart`'s "answers Logs, not a table" rule moves into a call that returns the table or raises, used by the controller concern and the chart tools.
- The invite flow in `OrganizationUsersController#create` (find or create the user, reactivate, membership, email) moves to a service.
- `ApplicationController#public_ingest_url` moves to a place the MCP controller can reach.
- `IssuesController#resolve` and `#unresolve` use the status enum, not `0` and `1`.

### 01, API tokens

- **Create answers JSON, not an Inertia redirect.** Decision: ApiTokensController#create answers JSON with the secret, and the component calls it with fetch and a CSRF header (as lib/dashboards/api.ts does), then reloads the api_tokens prop with router.reload. Revoke is an Inertia router.delete that redirects back with a flash notice. Why: Passing the secret through the flash would put it in the session cookie. Answering it once in JSON keeps it out of any store, which matches 'shown once and never stored'. Where: `console/app/controllers/api_tokens_controller.rb, console/app/frontend/lib/apiTokens.ts`.
- **Token routes at the top level.** Spec said: UserSettingsController or a small ApiTokensController. Decision: `resources :api_tokens, only: [:create, :destroy]` sits next to `resource :user_settings`, outside the /:org_slug scope. Why: A token names a user, not an Organization, and the User settings page is served both with and without an org slug. Where: `console/config/routes.rb`.
- **mcp_url built by hand.** Decision: mcp_url is "#{request.base_url}/mcp", because the `post "mcp"` route doesn't exist yet. Ticket 02 can switch it to the route helper once it adds the route. Why: The task says snippets use the Console's base URL as the request sees it. Where: `console/app/controllers/user_settings_controller.rb`.
- **Section reads page props itself.** Decision: The ApiTokens component reads api_tokens and mcp_url with usePage(), so User.tsx changes only by an import and one mount line, and its props interface stays as it was. Why: This keeps merge conflicts with the looks pass small. Where: `console/app/frontend/pages/Settings/components/ApiTokens.tsx`.
- **Secret encoding.** Decision: The secret is "st_" + SecureRandom.urlsafe_base64(32): 32 random bytes as 43 URL-safe characters, with no padding. Why: The ticket asks for at least 32 random bytes, and this form is safe in a header and on a shell command line. Where: `console/app/models/api_token.rb`.
- **Name rules.** Decision: A name is required (it is stripped first) and at most 100 characters. Names don't have to be unique per user. Why: The ticket says nothing about uniqueness, and duplicate names do no harm because tokens are revoked by id. Where: `console/app/models/api_token.rb`.
- **Tokens deleted with their user.** Decision: User has_many :api_tokens, dependent: :delete_all. Why: The foreign key would otherwise block deleting a user. A deleted user's tokens must stop working anyway. Where: `console/app/models/user.rb`.
- **Existing put('/user/settings') left alone.** Decision: User.tsx's profile form PUTs to /user/settings, which doesn't match the /user_settings or /:org_slug/settings/user routes. I didn't change it. Why: It is outside this ticket, and the page should change by as few lines as possible. Raising it so the orchestrator can decide whether to file it. Where: `console/app/frontend/pages/Settings/User.tsx`.

### 02, MCP endpoint and tool base

- **What mcp 1.8.0 does.** Decision: These facts come from reading mcp 1.8.0:
  - `StreamableHTTPTransport.new(server, stateless: true, enable_json_response: true)` and `#handle_request(Rack::Request)` return a Rack triple whose body is an Array.
  - In stateless mode the transport answers GET with 405 but DELETE with 200.
  - DNS rebinding protection is on by default and accepts only loopback Hosts.
  - `serve_subscriptions_listen: false` is the documented setting for a controller that renders its response.
  - The server calls `Tool.call(**args, server_context:)` on the tool class. server_context is an MCP::ServerContext that passes `[]` on to our Hash, and argument keys are symbols.
  - `Annotations.new` defaults to destructive_hint: true and open_world_hint: true, and a tool with no annotations sends none.
  - An error result is `MCP::Tool::Response.new(content, error: true)`, sent as `isError`.
  - An exception a tool doesn't rescue becomes a JSON-RPC -32603 'Internal error calling tool X' and goes to `configuration.exception_reporter`.
  - Tool names come from the demodulized, underscored class name.
  - With no MCP-Protocol-Version header, the transport assumes 2025-03-26.

  Why: Ticket 02 asked for the gem's behaviour to be recorded here; it comes from reading the installed gem's source. Where: `console/app/controllers/mcp_controller.rb, console/app/mcp/mcp_tools/base.rb`.
- **DELETE answers 405 from the controller.** Spec said: GET and DELETE answer 405 as the stateless transport does. Decision: GET and DELETE /mcp are routed to McpController#method_not_allowed. It answers 405 with Allow: POST and a JSON-RPC -32600 body after the token check, so a request without a token still gets 401. Why: The gem's stateless transport answers DELETE with 200, so routing DELETE to it would not give the 405 the ticket asks for. Where: `console/config/routes.rb, console/app/controllers/mcp_controller.rb`.
- **The transport's DNS rebinding check is off.** Decision: The transport is created with `dns_rebinding_protection: false` and `serve_subscriptions_listen: false`. Why: The check accepts only loopback Hosts, so it would turn away Console's own host. It protects servers that trust whoever can reach them. Every request here needs a Bearer token, which a rebound page doesn't have. Rails' config.hosts is not set in production, so the reason given is the token, not a Rails Host check. ADR 0009 says this. Where: `console/app/controllers/mcp_controller.rb`.
- **The public ingest URL moved to EventStore.** Spec said: Move ApplicationController#public_ingest_url somewhere McpController can use it, such as a small concern or module. Decision: `EventStore.public_ingest_url(console_url)` takes Console's URL, not a request. ApplicationController#public_ingest_url passes request.base_url to it. Why: Tools have only console_url in server_context, and ticket 09's get_project_setup needs the ingest URL. This is one function next to EventStore.ingest_url instead of a new concern. Where: `console/app/services/event_store.rb`.
- **Mistake formatting extracted to EventStore.mistakes.** Decision: MonitorQueryCheck's 'line L, column C: message' formatting moved to EventStore.mistakes(body). The tool base and MonitorQueryCheck both use it. Why: The brief says to reuse code, never copy it. Tool errors for EventStore::Rejected need the same lines with positions. Where: `console/app/services/event_store.rb, console/app/services/monitor_query_check.rb`.
- **Answer format, and where the registry lives.** Decision: An answer is one text content: compact JSON (JSON.generate, nils kept) or text, then '\nConsole: <url>'. There is no structuredContent, to avoid sending the payload twice. The registry is `McpServer::TOOLS`, and a tool is listed when `TOOLS.select(&:listed?)` keeps it. Why: The spec asks for compact answers that end with a Console link. Tools live under the McpTools namespace so their names don't clash with the gem's MCP module. Where: `console/app/mcp/`.
- **Extra tool-error mapping, and the not-found map filled ahead.** Spec said: The spec lists Rejected, Busy, TimedOut, SQLQueriesOff, NotAuthorized and RecordNotFound. Decision: Base also maps ActiveRecord::RecordInvalid to 'Not saved: …' and EventStore::Unavailable to 'EventStore is unavailable'. LISTED_BY is filled ahead for every model in the tool catalogue. Why: The create and update tools in tickets 06 to 09 will meet validation errors, and an unavailable EventStore should be an answer the model can act on, as it is in the UI. Filling the map now means later tickets can rely on `find`. Where: `console/app/mcp/mcp_tools/base.rb`.
- **Annotations.** Decision: Read tools set readOnly and idempotent, with destructive and openWorld false. writes! and destructive! set destructive explicitly. openWorld is false unless a tool passes open_world: true. Why: The gem defaults destructiveHint to true, so read tools must say false. Updates count as non-destructive, as the spec marks only deletes and key rotation destructive. Where: `console/app/mcp/mcp_tools/base.rb`.
- **The SQL-gated listing is tested before run_sql exists.** Decision: The integration test checks that no tool needing SQL, and no run_sql, is listed while SQL is off, and that every tool is listed while it's on. A base test toggles the setting with a stub tool that needs SQL. Why: run_sql comes in ticket 05, so for now the gate is tested through needs_sql_queries! on a stub tool.
- **The range accepts every span the explorer accepts.** Spec said: range (15m, 1h, 24h, 7d; default 1h). Decision: `range` accepts any span lib/timeRange.ts's isSpan accepts: \d+[mhd], more than zero and at most ten years. 15m, 1h, 24h and 7d are the examples given. Why: Links then keep the span, and the explorer reads it back instead of falling back to its default range. Where: `console/app/mcp/mcp_tools/time_range.rb`.
- **Report directly from the MCP initializer, not through Rails.error.** Spec said: The spec doesn't say; the earlier implementer's note said the failures went to Sentry through Rails.error.report. Decision: The exception_reporter lambda calls Rails.logger.error and Sentry.capture_exception itself. sentry.rb is unchanged: register_error_subscriber stays off. Why: This is the smallest fix and it stays inside the MCP server. Turning on register_error_subscriber would change things for the whole app: every Rails.error report or handle inside Rails would start going to Sentry, which is outside this ticket. Where: `console/config/initializers/mcp.rb`.
- **Which gem errors count as client mistakes.** Decision: The reporter skips a RequestHandlerError unless its error_type is :internal_error. Everything else is logged and sent: a tool's own exception, which arrives unwrapped, and the gem's internal-error RequestHandlerErrors. Why: I probed the gem. 'Tool not found' and bad logging/setLevel params come in as invalid_params RequestHandlerErrors, which are client mistakes. A tool bug comes in as its original error. ping, prompts/list, resources/list and unknown methods report nothing. Where: `console/config/initializers/mcp.rb`.
- **Where the reporter test lives.** Decision: A new file, console/test/mcp/exception_reporter_test.rb, runs real tools/call requests through McpServer.build(...).handle. It stubs Sentry.capture_exception and Rails.logger, and makes a tool fail inside its run by stubbing the user's organization_users. Why: The failure starts inside run, so the test also checks that McpTools::Base#answer doesn't swallow unexpected errors. Running through server.handle uses the global MCP.configuration that the initializer sets. Where: `console/test/mcp/exception_reporter_test.rb`.

### 03, Fields endpoint in EventStore

- **Answer shape: two lists plus truncated.** Spec said: the built-in fields ...; the top Attributes as { name, type, logs }. Decision: The answer is {built_in: [{name, type}], attributes: [{name, type, logs}], truncated}. built_in types use the Query language's names: "datetime" for time, "string" for the others. Why: The ticket asks for the built-in fields and the Attributes as {name, type, logs}. Two lists keep the built-in fields, which have no counts, apart. truncated fetches one row past the limit, matching the tables' 'truncated' and the spec's 'N more' style, so an agent knows the list was cut. Where: `event_store/handler/logs_fields.go`.
- **Attribute type names kept as log_key_counts stores them.** Decision: type is "string", "number" or "bool" (storage.AttributeType). JSON Attributes never appear, because countKeys only counts promotedTypes. Late Logs aren't counted either, and a day with more than 1000 keys keeps only its top 1000 by an approximate count (Space-Saving). This is noted in the AttributeCounts doc comment. Why: The orchestrator asked to keep the type column's names. These are also the names the Query language uses for the same types. Where: `event_store/storage/logs_fields.go`.
- **Range edges by UTC day.** Spec said: summed from logs.log_key_counts over the range's UTC days. Decision: The days counted are LogDay(from) through LogDay(to - 1ns): every UTC day [from, to) touches. A to at exactly midnight leaves that day out, and from == to counts from's day. from and to are required RFC 3339 times; dates alone are refused with 400, using rangeProblem's message. Why: Queries read [from, to) as half-open, so a to at midnight has no Logs from that day.
- **Limit validation.** Decision: If no limit is given, it is 100. A limit that isn't a whole number of 1 or more (0, -1, 'ten', '1.5') gets a 400, and anything above 500 is cut to 500. Why: The ticket gives the default and the cap. A query parameter can tell 0 apart from no limit, unlike the JSON limit in the run endpoints, so 0 is refused rather than read as the default.
- **Order of tied counts.** Decision: ORDER BY logs DESC, key, type. Why: The answer is deterministic, and a name with two types shows its entries next to each other when their counts tie.
- **Handler in its own file.** Spec said: handler/routes.go, handler/logs.go, storage/logs_*.go. Decision: Fields lives in handler/logs_fields.go and storage in storage/logs_fields.go, not in handler/logs.go. Why: The repo already gives each logs endpoint its own file (logs_histogram.go, logs_run.go, logs_sql.go). The ticket names handler/logs.go only as a general location. Where: `event_store/handler/logs_fields.go`.
- **post! error handling shared with a new get!.** Decision: post!'s rescue chain moved into a private execute!(sql:, **request), which post! and a new get!(url, params) both use. logs_fields therefore raises Rejected on a 400, as every other Log call does. The existing request! (used by get_log and the Events calls) is left as it was: it raises Unavailable on a 400 and returns nil on a 404. Why: The ticket asks for the same error handling as the other logs calls, and the brief says to reuse code rather than copy it. Where: `console/app/services/event_store.rb`.
- **Built-in fields come from the compiler.** Decision: A new exported logquery.BuiltInFields() reads builtInOrder and builtInFields, so the list can't drift from what Queries accept. The _time alias isn't listed. Why: Reuse. The ticket says to list the built-in fields as docs/logs/query-language.md does, and the tests pin exactly that list. Where: `event_store/logquery/compile.go`.

### 04, SQL queries are read-only

- **Probe answers on DuckDB 1.5.6.** Decision: On DuckDB 1.5.6:
  - **Every non-SELECT is rejected.** json_serialize_sql answers {"error":true,"error_type":"not implemented","error_message":"Only SELECT statements can be serialized to json!"}.
    - Seen for: DROP, INSERT, UPDATE, DELETE, CREATE, both COPY forms, ATTACH, DETACH, SET, RESET, PRAGMA (table_info and enable_profiling), CALL, CHECKPOINT, EXPLAIN, LOAD, INSTALL, USE, EXPORT, VACUUM, BEGIN, ALTER, WITH…DELETE, WITH…INSERT, and PIVOT without IN.
    - These parse as SELECT: DESCRIBE, SHOW and SUMMARIZE (as SHOW_REF), FROM-first, VALUES, TABLE t, and PIVOT…IN.
  - **Multi-statement strings.**
    - 'SELECT 1; SELECT 2' gives 2 statements.
    - Any non-SELECT anywhere makes the whole call fail with the error above.
    - A trailing ';' or empty statements count as 1; '' gives 0.
    - A syntax error gives error_type "parser", with position as a string byte offset.
  - **Function nodes** look like {"class":"FUNCTION","type":"FUNCTION","function_name":…,"schema","catalog","children"}.
    - Window functions have class WINDOW and a function_name.
    - Table functions are {"type":"TABLE_FUNCTION","function":{FUNCTION node}}.
    - Names come back lowercased.
    - A named WINDOW is inlined into the window expression.
  - **Binding needs a cast.** An untyped `?` fails with 'first argument must be a VARCHAR', and the JSON result scans as a map, so both sides are cast to VARCHAR.
  - **query() refuses non-SELECTs.** On 1.5.6 it raises 'Expected a single SELECT statement' itself.
  - **Extensions.** autocomplete, core_functions, icu, json and parquet are statically linked. sqlite_scanner and ducklake were installed in ~/.duckdb, so autoload could have pulled them in.

  Why: Step one of ticket 04. The probe's notes are in [research/probe-04-readonly-sql.md](research/probe-04-readonly-sql.md). Where: `.scratch/mcp/spec.md Implementation decisions (for the orchestrator)`.
- **More functions on the deny list than the ticket names.** Spec said: query, query_table, enable_logging, disable_logging, checkpoint, force_checkpoint, nextval and setseed. Decision: Besides query, query_table, enable_logging, disable_logging, checkpoint, force_checkpoint, nextval and setseed, the check also refuses:
  - json_execute_serialized_sql: it runs a serialized SELECT whose calls the AST walk can't see.
  - enable_profiling and disable_profiling: table functions that can write profile output.
  - enable_peg_parser and disable_peg_parser: they change the parser.
  - truncate_duckdb_logs and write_log.

  Why: The probe listed DuckDB 1.5.6's table and scalar functions. These change state from a SELECT, and json_execute_serialized_sql would hide any denied call. The ADR amendment says a DuckDB upgrade should look for new ones. Where: `event_store/storage/logs_sql_readonly.go stateChangingFunctions`.
- **Autoload off at open, on every install.** Spec said: Turn them off once EventStore has loaded the extensions it needs. Decision: NewDuckDBWriter turns autoinstall and autoload off right after sql.Open. UseBucket no longer sets them; it sets extension_directory and loads httpfs by name. Why: The built-in extensions are loaded already at open, and an explicit LOAD doesn't need autoload (UseBucket already worked that way). One place covers installs without a bucket, which used to keep DuckDB's defaults. TestABucketGivesDuckDBMoreThreadsThanCPUsForRemoteReads still loads the real httpfs. Where: `event_store/storage/duckdb.go, duckdb_bucket.go`.
- **How a refusal names what isn't allowed.** Decision: The name in the message depends on the case:
  - **A statement that isn't a SELECT:** its first keyword, after comments and '(' (DROP, CALL, PRAGMA, PIVOT…).
  - **When that word starts a SELECT** (SELECT, WITH, FROM, VALUES, TABLE, DESCRIBE, SHOW, SUMMARIZE): 'a statement other than SELECT'.
  - **Two or more SELECTs:** 'more than one statement'.
  - **A denied function:** 'name()'.

  When several denied functions appear, the first one found is reported, walking object keys in sorted order so the choice is the same each time.

  Why: json_serialize_sql doesn't say which statement it rejected. Finding out by preparing the SQL would break the rule that nothing reaches prepare, and splitting it needs a lexer. Where: `storage/logs_sql_readonly.go statementKind`.
- **Parse errors and empty SQL.** Decision: SQL that doesn't parse is refused with DuckDB's message, rebuilt from json_serialize_sql's error type, message and position as '<Type> Error: msg' plus the LINE and caret. A test compares it with DuckDB's own error for the same SQL; long lines are not cut down the way DuckDB does it. SQL with no statement (blank or only comments) gets the SQLError 'The SQL has no statement to run.' Why: The explorer draws DuckDB's LINE and caret (errorParts.ts). Running unparseable SQL to get DuckDB's message would break the rule that nothing runs before the check passes. Where: `storage/logs_sql_readonly.go duckDBMessage`.
- **The check runs on the pool before the read starts.** Spec said: on a connection that runs nothing else. Decision: checkReadOnly uses s.db.QueryRowContext, which runs only the json_serialize_sql statement, before beginRead, the events-archive hold and the temporary view. Why: A refused query costs nothing and holds nothing up. The pooled connection runs only the parse statement. Where: `storage/logs_sql.go RunSQL`.
- **ADR 0008 and object-store docs amended too.** Decision: The autoload line in ADR 0008 and in docs/logs/object-store.md now says autoload is off on every install. ### 05, Logs tools

- **Logs answer is text lines, not JSON.** Spec said: Logs are one line each: time, level, service, a message cut at about 500 characters, a few Attributes and the id. Decision: query_logs answers Logs as plain text: a header line, one line per Log, and a cursor line. Tables stay compact JSON. Why: One Log per line is the most compact form for a model. Message and string values are JSON-quoted, so the string "200" reads apart from the number 200, which the Query language treats differently. Where: `console/app/mcp/mcp_tools/log_line.rb, query_logs.rb`.
- **Log id placed fourth in the line.** Spec said: time, level, service, message, a few Attributes and the id. Decision: Each line is time, level, service, id, message, then Attributes, instead of putting the id last. Why: An Attribute can be named anything, id included, so an id at the end after name=value pairs could be misread. A fixed position can't be, and the header line names the order. Where: `McpTools::LogLine`.
- **At most 8 Attributes per line, values cut at 100 chars.** Decision: LogLine shows the first 8 Attributes in EventStore's order, then "+N more". get_log gives the whole Log. Why: The spec says "a few Attributes" without a number.
- **The cursor line names the absolute from and to.** Decision: The answer states the from and to it read, and the cursor line says to pass them with the cursor. Why: A relative range such as 1h moves forward on the next call, which would drop Logs at the old end of the window. Passing the same from and to keeps the pages over one window. Where: `QueryLogs#logs_answer`.
- **Short pages with a cursor are answered as they come.** Decision: query_logs makes one EventStore call and answers what it gets: fewer Logs than the limit, or none, still come back with the cursor line. Why: The explorer keeps fetching until it has a full page, but one bounded call per tool call keeps the ChartRuns hold short. The cursor line tells the agent there is more.
- **query is optional in query_logs.** Decision: An empty or missing query reads every Log, as the explorer does. Why: The ticket lists query as an argument but doesn't say it is required. get_issue's trace_logs hint always passes it.
- **list_fields defaults to 24h.** Spec said: Ranges default to 1h. Decision: list_fields' range defaults to 24h, not 1h, as get_chart_data overrides its default too. Why: EventStore counts Attributes per UTC day, so 1h early in the UTC day would read an almost empty day. 24h always covers yesterday and today.
- **get_log's link and time handling.** Decision: get_log links to the explorer over the Log's own second. The time argument is parsed as ISO 8601 and sent as UTC with nanoseconds. A time that won't parse is a ToolError. Why: There is no explorer URL for one Log, and a one-second window shows that Log among very few. Without the check, a bad time would reach EventStore as a 400 and come back as "EventStore is unavailable".
- **Log id check moved into EventStore.get_log.** Decision: LOG_ID moved from LogsController to EventStore. get_log returns nil for a non-UUID id without asking EventStore, and the controller's own check is gone. Why: The brief says to move shared logic out of controllers rather than copy it. A bad id would otherwise reach EventStore as a 400 and come back as "unavailable". The controller's existing tests still pass. Where: `console/app/services/event_store.rb, console/app/controllers/logs_controller.rb`.
- **Busy refusal wording.** Decision: Changed Base's ChartRuns::Busy message to "Console is busy running other Queries and charts. Run this again in a moment." and updated base_test. Why: query_logs and run_sql share the cap with charts. This matches the explorer's own wording.
- **Explorer link tested against explorerState.ts with a shared fixture.** Decision: One JSON fixture is checked from both sides: Rails asserts the exact URL Links#explorer builds, and vitest asserts the state stateFromSearch reads from it. Why: The orchestrator asked for the link to be built exactly as explorerState.ts reads it, and tested. A fixture both languages check ties the two together. Where: `console/test/fixtures/files/explorer_links.json, console/app/frontend/lib/logs/mcpLinks.test.ts`.
- **query_language_reference has no Console link.** Decision: It answers the doc text alone. Why: There is no Console page for the language reference.
- **Copy test fails with a message, not a diff.** Decision: The copy test compares the two files with plain assert and a message saying to copy the doc. Why: assert_equal printed both 141-line documents on failure.
- **Cut cells in Table.compact, not per tool.** Spec said: Tables are a header plus at most 100 rows. Logs cut the message at about 500 characters. Decision: I cut cells in Table.compact, which query_logs, run_sql and get_chart_data all use. Why: All three tools hit the same problem, and one fix point means one test, not three copies. Where: `console/app/mcp/mcp_tools/table.rb`.
- **Long arrays and objects become cut JSON strings.** Decision: An array or object cell whose JSON is longer than 500 characters is answered as that JSON cut with "…", so it comes back as a string. Shorter ones stay as they are. Why: run_sql's attrs_* maps and JSON Attributes can be as large as a message. LogLine.value_of already cuts arrays and objects by their JSON, so this follows the same rule. Where: `Table.cell_of`.
- **Cell cut length matches the message cut.** Decision: CELL_CHARS is set to LogLine::MESSAGE_CHARS (500). Table uses LogLine.cut instead of a second copy of the cutting code. Why: The finding asked for about 500 characters, as LogLine does. Reusing LogLine.cut keeps one copy.
- **Descriptions mention the cut.** Decision: The three table tools now build their description from Table::SHAPE, which mentions the 500-character cut. Why: An agent can then tell that a value ending in "…" was cut, and that get_log returns the whole Log.
