# Prior explore: rails-console

> Extracted from workflow run `wf_25055e4a-726` (solidtrace-logs-discovery, 2026-09-13, Fable subagents). Reference only: claims were not re-verified and design implications were never decided.


## Summary

The Console is a Rails 8.1 + Inertia/React app where every user-facing page is a controller action that calls `render inertia: "Folder/Page", props: {...}` with `layout "dashboard"`, and all org-scoped routes live inside a single `scope "/:org_slug"` block in config/routes.rb. Multi-tenancy is enforced purely by a per-controller `set_organization` before_action doing `current_user.organizations.find_by!(slug: params[:org_slug])` (assigned to `@current_org`, which InertiaShare then shares to every page as `current_org`); Pundit is wired in ApplicationController but is only actually used by OrganizationUsersController, so authorization today is effectively "scope through the association". Props are built by hand-written PORO serializers in app/serializers (`initialize(record)` + `as_json(*)` + `to_json(*)`) — no jbuilder/AMS. Rails talks to the Go EventStore over HTTP through app/services/event_store.rb (rest-client, chainable query-builder returning PORO `Event` objects). The two tiers exchange work through a dedicated `message_queue` SQLite database (MessageQueueRecord abstract class): Go writes `event_store_messages` (msgpack+zstd) drained every second by EventStoreMessageProcessorJob, and Rails writes `console_messages` (MessagePacker::WithCompression::VeryFast) polled every 5s by Go's ArchiveConsumer keyed on `message_type`. Alerting is Integration (org-owned, JSON `settings`) -> Notification rows (msgpack payload, pending/sent state machine) -> IntegrationNotificationProcessorJob (Solid Queue `limits_concurrency`, 10s initial delay, 1-minute debounce/rate limit) -> IntegrationNotifier.deliver_batch -> Notifiers::{Slack,Pagerduty,Email}. Recurring work is declared in config/recurring.yml (Solid Queue recurring tasks). The frontend is Vite + React 19 + Tailwind 4 with a Base UI-based shadcn registry (style `base-lyra`, iconLibrary hugeicons), ~20 ui primitives present, no charting library and no popover/command/calendar/sheet/scroll-area — all of which a logs explorer would need. Tests are Minitest + FactoryBot + WebMock, organized by layer under console/test, run through bin/ci.

## Conventions

- Every Ruby file starts with `# frozen_string_literal: true`; style is rubocop-rails-omakase + rubocop-performance (bracket spacing `[ a, b ]`, trailing commas in multiline hashes).
- New page recipe: (1) add the route inside `scope "/:org_slug"` in config/routes.rb (settings-type resources go inside the nested `scope "/settings"`); (2) create app/controllers/logs_controller.rb inheriting ApplicationController with `layout "dashboard"` and `before_action :set_organization` implemented as `@current_org = current_user.organizations.find_by!(slug: params[:org_slug])`; (3) `render inertia: "Logs/Index", props: { ... }`; (4) create app/frontend/pages/Logs/Index.tsx as a default-exported component wrapped in `<DashboardLayout>`; (5) add a Sidebar nav entry. No manifest/registration step — pages are auto-globbed.
- Path helpers always need the scope param: `logs_path(org_slug: @current_org.slug)`; redirects after mutations use `redirect_to ..., notice: "..."`, and validation failures use `redirect_to ..., inertia: { errors: record.errors.to_hash }` (InertiaRails is configured with `always_include_errors_hash = true`).
- Props are built by hand-written serializers in app/serializers named `<Thing>Serializer`, constructed as `Serializer.new(record, option: true)` with `as_json(*)` returning a symbol-keyed hash, ISO8601 timestamps, and an optional `to_json(*)` delegate; collections are mapped inline in the controller.
- Filter/list actions read plain query params, apply them conditionally, and echo a `filters:` hash back to the page; pagination is manual offset/limit with a `{ current_page, total_pages, total_count }` prop.
- Strong params are explicit, including each key of a JSON `settings` column (`params.require(:integration).permit(:provider, settings: [ :webhook_url, ... ])`).
- Background work: jobs inherit ApplicationJob, `queue_as :default`, live in app/jobs (namespaced subdirs like Maintenance:: map to app/jobs/maintenance/). Periodic work is registered in config/recurring.yml by `class:` (Solid Queue recurring), not cron. Solid Queue runs via `bin/jobs` (Procfile.dev), config/queue.yml has a single `*` worker, 3 threads.
- Cross-tier work uses the outbox tables, never direct HTTP from Go to Rails: Rails -> Go is `ConsoleMessage.create!(message_type:, payload:)` (msgpack+zstd VeryFast), Go -> Rails is `event_store_messages` rows drained by EventStoreMessageProcessorJob's `case message.message_type`. Both models subclass MessageQueueRecord (separate `message_queue` DB; migrations under db/message_queue_migrate, generated with `--database=message_queue`).
- Alerts are never sent inline from a request: enqueue a Notification row + `IntegrationNotificationProcessorJob.set(wait: Notification::GROUPING::INITIAL_DELAY).perform_later(integration.id)`, and let IntegrationNotifier.deliver_batch dispatch to Notifiers::*.
- Frontend: TypeScript strict with `noUnusedLocals`/`noUnusedParameters`; import via the `@/` alias (app/frontend); all shared interfaces exported from app/frontend/types/index.ts; pages read shared state with `usePage<SharedProps>().props` and bail with `if (!current_org) return null`.
- Forms use `useForm` from @inertiajs/react with `post/put` to a literal template-string URL built from `current_org.slug`; feedback via sonner `toast` (global Toaster) or Rails flash surfaced by FlashToasts.
- UI is shadcn in the Base UI (`@base-ui/react`) `base-lyra` style with hugeicons inside ui primitives, while page-level code uses lucide-react icons; class merging via `cn()` from @/lib/utils; dates via date-fns (`format`, `formatDistanceToNow`); numbers via Intl.NumberFormat compact; tables use the shadcn Table primitives with uppercase tracking-wider muted headers.
- Theming is CSS-variable based (oklch) in app/frontend/css/globals.css with a `.dark` class toggled by ModeToggle + an inline localStorage script in the dashboard layout — do not hardcode colors, use bg-card/text-muted-foreground/--chart-N.
- Tests: Minitest, one file per class under test/{controllers,models,jobs,services,mailers,lib,system}, FactoryBot factories in test/factories (fixtures are disabled), `include IntegrationTestHelper` + `sign_in_as(@user)` for controller tests, WebMock for the Go HTTP boundary, ActiveJob::TestHelper + assert_enqueued_with for jobs. Run through bin/ci.
- Domain/terminology changes are expected to be recorded in CONTEXT.md (and ADRs in docs/adr/) per AGENTS.md; feature issues live as markdown under .scratch/<feature-slug>/.

## Pitfalls

- Org scoping is copy-pasted `set_organization` in six controllers with no shared concern and no Pundit policy check — a Logs controller that forgets it leaks cross-org data, and InertiaShare silently renders a page with `current_org: null` (Sidebar returns null, so the bug looks cosmetic). There is also no Pundit `authorize`/`policy_scope` on Issues/Projects/Integrations, and no `after_action :verify_authorized`, so nothing enforces adding a LogPolicy.
- There is no project-level or role-level authorization at all: any member (role member or admin) sees every project in the org. Log data is often more sensitive than stack traces; the existing model gives you no place to hang per-project log access.
- The Go read API has no auth (`GET /api/:project_id/events...`), so all log reads must be proxied through Rails or the Go side needs an auth layer added; EventStore.make_request also swallows every error and returns a default ([]/0/nil), so a dead Go tier renders an empty log page with no error surfaced to the user.
- Serializers hit the Go tier per row: IssueSerializer#as_json calls `@issue.events.count` and `@issue.events.first`, meaning an N+1 of HTTP round-trips on the Issues index. Naively copying that shape for a logs list (e.g. per-row counts/facets) would be disastrous at log volumes.
- The whole Inertia model serializes props as JSON in the HTML response — dumping thousands of log rows or a raw payload blob per row into props will blow up page size. Pagination/partial reloads (`only: [...]`) and server-side aggregation are mandatory.
- IntegrationNotifier.deliver_batch is hardcoded to Issues: it reads `n.payload["issue_id"]`, loads `Issue.where(id: ...)`, and always sends `event: "issue_created_batch"`; every Notifiers::* constructor takes an Issue positionally and calls `issue.project.organization`. Log monitors reusing Notification need this generalized (polymorphic subject) or they will crash on nil.
- Rate limiting in IntegrationNotificationProcessorJob is per-integration and global (1 notification/minute across all event types), so noisy log monitors will starve/delay issue alerts sharing the same integration; `limits_concurrency ... on_conflict: :discard` can also drop a run entirely (it relies on the tail-check re-enqueue).
- EventStoreMessageProcessorJob runs `every second` and does `find_each` over all processable rows with no locking — adding high-volume log message types to the same table risks double processing across workers and starving issue notifications. Failed messages are retried until attempts >= 5 then silently stall forever (no dead-letter surface).
- MessagePacker::WithCompression (marker byte + zstd) must stay byte-compatible with Go pkg/msgpacker; the Rails Notification model uses a *different*, uncompressed MessagePackCoder (app/models/concerns/message_pack_coder.rb) — easy to pick the wrong coder for a new table.
- `routes.rb` declares an `api/v1` namespace (issues, projects, project_keys, auth) whose controllers do not exist under app/controllers/api — those routes 500/NameError. Don't model a new Logs API on them; Api::BaseController is an empty stub.
- No charting library at all (no recharts/visx/chart.js) and no shadcn `chart`, `popover`, `command`, `calendar`, `sheet`, `scroll-area`, `resizable`, `toggle-group`, `switch`, `skeleton`, `form`, `pagination`, `sidebar`, `avatar`, `progress`, `accordion`, `collapsible`, `hover-card`, `slider`, `radio-group` components. A logs explorer (histogram, time-range picker, query autocomplete palette, resizable detail pane, virtualized table) needs several new deps; also no virtualization lib (@tanstack/react-virtual) and no @tanstack/react-table.
- The ui kit is Base UI (`@base-ui/react`, components.json style `base-lyra`, iconLibrary hugeicons), NOT Radix — stock shadcn/ui docs snippets and `npx shadcn add` from the default registry will pull Radix-based files that don't match (e.g. this Select takes an extra `items` prop). A stale `@radix-ui/react-checkbox` dep exists but the checkbox component uses Base UI.
- Icon usage is split: ui/* primitives use @hugeicons/react while pages use lucide-react — pick per-layer or the bundle carries both.
- Sidebar active-state matching is string `url.includes(...)` logic (e.g. Projects is `url.includes('/projects') && !url.includes('/issues')`), so a `/logs` route nested under projects would mis-highlight; the checks need updating when new paths are added.
- There is no real-time transport: cable.yml exists but Action Cable/solid_cable is not wired into the React app, so live log tailing requires new infrastructure (SSE from Go or polling).
- SQLite everywhere with a 5s busy_timeout and 3 Solid Queue threads; log-monitor evaluation jobs writing frequently to the primary DB can cause write contention. Also `bin/ci` still runs `bin/importmap audit` although importmap-rails is commented out of the Gemfile.
- DuckDB `events` view unions events_hot with parquet; a logs table would need its own hot/archive pair and its own Rails-scheduled archive job mirroring Maintenance::EventStoreArchiveJob (which archives only `Date.yesterday` with no catch-up if the job is missed).

## Open questions

- Is Logs an org-level page (`/:org_slug/logs`, like Issues) or project-scoped (`/:org_slug/projects/:slug/logs`)? Sidebar/breadcrumbs and the project selector differ, and the Go query API is keyed by project_id so an org-level view needs multi-project fan-out or a new Go endpoint.
- Do log queries go through Rails (reusing app/services/event_store.rb, keeping the single auth door) or does the React page call the Go tier directly? Direct calls need auth on the Go read API, which is currently missing.
- Where does the KQL-like parser live — Rails (so it can be reused by monitors and validated in strong params) or Go (so it compiles straight to DuckDB SQL)? This determines whether the query language is a Rails service object or a Go package.
- Should log monitors be a new AR model (`LogMonitor` with query, threshold, window, integration_id) reusing Notification/IntegrationNotificationProcessorJob, or a new Integration provider? The current Notification pipeline assumes an Issue subject and one shared 1/min rate limit per integration.
- Is monitor evaluation a Rails recurring job that queries Go, or a Go-side evaluator pushing results via event_store_messages? The recurring.yml granularity ('every second'/'every minute') and SQLite write contention favor the Go side for high-frequency checks.
- Charting: adopt recharts (shadcn `chart` component assumes it) or hand-roll SVG histograms against the existing --chart-N tokens? Also whether to add @tanstack/react-virtual + react-table for a large log table.
- Should the repeated `set_organization` be extracted into a shared `OrganizationScoped` concern (and real Pundit policies added) as part of this feature, or left as-is to match existing style?
- Retention/archival policy for logs (Parquet partitions, TTL per project, storage quota) and who schedules it — is it another ConsoleMessage command to Go, and does it need a settings UI?
- Ingest path for logs: a new Go endpoint (OTLP/HTTP JSON/Vector-compatible) authenticated by the existing Sentry public key in project_keys, or new log-specific keys/tokens with their own Rails UI?
- Terminology: CONTEXT.md currently reserves 'Event' for Sentry payloads and explicitly avoids 'log line'. New nouns (LogRecord? LogStream? Dataset?) should be agreed and written into CONTEXT.md before implementation.
