# Prior research: duckdb

> Extracted from workflow run `wf_25055e4a-726` (solidtrace-logs-discovery, 2026-09-13, Fable subagents). Reference only: claims were not re-verified and design implications were never decided.


## Summary

SolidTrace's Go module pins github.com/duckdb/duckdb-go/v2 v2.5.4, which links duckdb-go-bindings v0.1.24 = DuckDB engine v1.4.3 LTS ("Andium", released 2025-12-09); the 1.4 LTS line reaches community end-of-life on 2026-09-16, and the current duckdb-go lines are v2.5.6 (DuckDB 1.4.5 LTS) and v2.10505.0 (DuckDB 1.5.5). The single most consequential fact for a logging design is that the VARIANT type (binary, auto-shredded semi-structured data) is new in DuckDB 1.5.0 and does not exist in 1.4.3 (no VARIANT in the bundled duckdb.h; the LTS docs have no variant page), so on the pinned engine "schemaless" attributes must be modelled with JSON (physically a VARCHAR with validation, queried via yyjson-backed json_extract/->/->> with JSONPath), MAP(VARCHAR,VARCHAR) (per-row varying keys, bracket access returns a scalar), or explicit typed columns/STRUCTs promoted from json_structure/json_transform. The duckdb-go Appender is confirmed from source: it buffers 2048-row chunks, rows are invisible until Flush/Close, the engine auto-commits every 204,800 rows, and it accepts time.Time for TIMESTAMP/TIMESTAMP_TZ, duckdb.UUID/[]byte(16) for UUID (not strings), duckdb.Map for MAP, map[string]any/Go structs for STRUCT, slices for LIST, and json.Marshal's any value for JSON columns. DuckDB is single-process, MVCC + optimistic concurrency, appends never conflict, and one writer plus many readers in one process is the supported model, but every resource/security setting (memory_limit, threads, enable_external_access, lock_configuration) is GLOBAL to the instance and duckdb-go routes all opens of the same path through DuckDB's instance cache, so there is no per-connection sandbox or per-query memory limit; query cancellation works via Go context (duckdb-go calls duckdb_interrupt on ctx.Done()) and DuckDB has no built-in query timeout. Parquet tiering is well supported: COPY (SELECT ... ORDER BY ts) TO ... (FORMAT parquet, PARTITION_BY (...), ROW_GROUP_SIZE 122880 default), hive partition-key filters prune directories, row-group min/max zonemaps prune on timestamp filters, Bloom filters (since 1.2, dictionary-encoded columns, equality predicates) prune on high-cardinality equality filters, union_by_name reads every file's footer and costs memory, parquet_metadata_cache defaults to false, and a VIEW is re-executed (and thus re-globbed) on every query. Text search has no incremental index: LIKE/contains/regexp_matches are full scans (regexp is rewritten to LIKE/prefix/suffix when possible), and the FTS extension's index does not update when the base table changes, so the practical design is time + structured prefilters followed by scanning compressed VARCHAR. Time-series helpers (time_bucket, date_trunc, generate_series for gap-filling, approx_count_distinct, quantile_cont, approx_quantile, approx_top_k, ASOF JOIN, FILTER clauses) are all present in 1.4.

- **Engine version / LTS lifetime** (verified): Release calendar: 1.4.0 LTS 'Andium' released 2025-09-16, end of life 2026-09-16; 1.4.3 LTS 2025-12-09; 1.4.4 LTS 2026-01-27; 1.4.5 LTS 2026-06-17; 1.5.0 'Variegata' 2026-03-09 (EOL 2026-09-01). 'Starting with v1.4.0, every other DuckDB version is going to be a Long-Term Support (LTS) edition... a year after the release.' The docs at duckdb.org/docs/lts/ are the 1.4 LTS docs; duckdb.org/docs/current/ describes 1.5.x. — source: https://duckdb.org/release_calendar
- **VARIANT type availability** (verified): VARIANT is new in DuckDB 1.5.0: 'DuckDB now natively supports the VARIANT type... Unlike the JSON type, which is physically stored as text, VARIANT stores typed, binary data.' It is NOT in 1.4.3: the bundled duckdb.h in duckdb-go-bindings v0.1.24 contains no VARIANT type, and https://duckdb.org/docs/lts/sql/data_types/variant returns 404. The 1.4.0 announcement lists no VARIANT. — source: https://duckdb.org/2026/03/09/announcing-duckdb-150
- **VARIANT capabilities (1.5+)** (verified): VARIANT 'stores typed, binary data where each row is self-contained with its own type information'; DuckDB 'automatically detects the common structure hidden in your semi-structured data and shreds it'. Functions: variant_typeof(v), variant_extract(v, 'name'), dot access data.name; Parquet read/write with auto-shredding 'based on the structure of the first row group'. Example: CREATE TABLE events (id INTEGER, data VARIANT); INSERT INTO events VALUES (1, 42::VARIANT), (2, 'hello world'::VARIANT); SELECT variant_typeof(data) FROM events; — source: https://duckdb.org/docs/current/sql/data_types/variant
- **JSON storage** (verified): 'Logically, the JSON type is similar to a VARCHAR, but with the restriction that it must be valid JSON. Physically, the data is stored as a VARCHAR.' Casting VARCHAR->JSON only validates; whitespace and key order are preserved (so '{ "a": 5 }'::JSON != '{"a":5}'::JSON). There is no columnar shredding of the JSON type on 1.4.x. — source: https://duckdb.org/docs/current/data/json/json_type.html
- **JSON extraction functions and path syntax** (verified): json_exists(json, path); json_extract(json, path) alias json_extract_path, operator -> ('If path is a LIST, the result will be a LIST of JSON'); json_extract_string(json, path) alias json_extract_path_text, operator ->> (returns VARCHAR); json_value(json, path) returns NULL if not scalar. Two path notations: JSONPointer '/duck/0' and JSONPath '$.duck[0]', with '$.duck[#-1]' (backward index), '$.species[*]' (wildcard), '$."duck.goose"[1]' (quoted keys); 0-based. Arrow operators have LOW precedence (lambda syntax): write ((j->'field') = 42) and WHERE (j->>'field') IS NOT NULL. Performance: 'If multiple values need to be extracted from the same JSON, it is more efficient to extract a list of paths' in one call, e.g. json_extract(j, ['$.a', '$.b']). — source: https://duckdb.org/docs/current/data/json/json_functions.html
- **JSON schema inference / promotion** (verified): json_structure(json): 'Return the structure of json. Defaults to JSON if the structure is inconsistent' e.g. {"family":"VARCHAR","species":["VARCHAR"]}; json_group_structure(json) aggregate: 'combined json_structure of all json in the aggregation'; json_type(json[, path]) returns one of ARRAY, BIGINT, BOOLEAN, DOUBLE, OBJECT, UBIGINT, VARCHAR, NULL; json_keys(json[, path]) LIST of VARCHAR; json_valid; json(json) minify; json_transform(json, structure)/from_json and *_strict variants, e.g. SELECT json_transform(j, '{"family": "VARCHAR", "coolness": "DOUBLE"}'). These are what a 'discover fields -> promote to typed column' pipeline would use on 1.4.x. — source: https://duckdb.org/docs/lts/data/json/json_functions
- **MAP vs STRUCT** (verified): MAP: 'MAPs must have a single type for all keys, and a single type for all values' and 'MAPs do not need to have the same keys present for each row, and thus are suitable for use cases where the schema is unknown beforehand or varies per row'. Literal MAP {'key1': 10, 'key2': 20} or MAP(['key1','key2'],[10,20]). STRUCT: 'Each row in the STRUCT column must have the same keys'; access a.x, a['x space'], struct_extract(a,'x'). So for arbitrary log attributes on 1.4.x: MAP(VARCHAR,VARCHAR) for flat string attrs, JSON for nested/typed, STRUCT only for known schemas. — source: https://duckdb.org/docs/current/sql/data_types/map.html and https://duckdb.org/docs/lts/sql/data_types/struct
- **MAP access semantics on 1.4 LTS** (verified): LTS docs: map[key] bracket notation 'Returns the value for a given key or NULL if the key is not contained in the map' (scalar). element_at(map,key)/map_extract(map,key) return a LIST ([42]); map_extract_value(map,key) returns scalar 42; map_entries(map) -> 'a list of struct(k, v)' e.g. [{'key': 100, 'value': 42}]; map_keys, map_values, map_contains(map,key), cardinality(map). — source: https://duckdb.org/docs/lts/sql/functions/map
- **Unnesting maps for top-values queries** (likely): unnest(list) creates one row per element; unnest(struct) creates one column per member; unnest may be used as a table function in FROM. Combined with map_entries this gives per-key value counts, e.g. SELECT e.key, e.value, count(*) AS n FROM logs, unnest(map_entries(attrs)) AS t(e) WHERE ts >= now() - INTERVAL 1 HOUR GROUP BY 1, 2 ORDER BY n DESC; and for a single key SELECT attrs['host'] AS v, count(*) FROM logs GROUP BY 1 ORDER BY 2 DESC LIMIT 20 (bracket returns scalar). The docs do not show a MAP-specific unnest example; the composition is inferred from the documented pieces. — source: https://duckdb.org/docs/current/sql/query_syntax/unnest.html
- **Appender semantics (engine)** (verified): 'Values added to the Appender are cached before being inserted into the database, for performance reasons.' 'The cache is flushed automatically when the Appender is closed or goes out of scope, and it can also be flushed manually.' It 'always appends to a single table in the database file, using that connection's transaction context.' 'By default, the appender performs commits every 204,800 rows'; wrap AppendRow calls in BEGIN TRANSACTION / COMMIT to control this. 'Constraints such as NOT NULL, PRIMARY KEY, and UNIQUE are checked when the cache is flushed rather than as each row is added' and on violation 'the entire append operation fails and no rows are inserted.' Rows are invisible to readers until flushed. — source: https://duckdb.org/docs/lts/data/appender
- **Appender (duckdb-go v2.5.4) API and buffering** (verified): appender.go: NewAppenderFromConn(driverConn, schema, table); AppendRow(args ...driver.Value); Flush() ('Flush the data chunks to the underlying table and clear the internal cache... Unless you have a good reason to call this, call Close'); Close() flushes then destroys. appendRowSlice() pushes a full chunk when a.rowCount == GetDataChunkCapacity() (= mapping.VectorSize(), i.e. DuckDB's vector size, 2048 rows). The Go README: 'Flush: Optional, if you want to access the appended rows immediately.' Appender calls take no context and cannot be cancelled. — source: https://github.com/duckdb/duckdb-go/blob/main/README.md (verified against ~/go/pkg/mod/github.com/duckdb/duckdb-go/v2@v2.5.4/appender.go)
- **Appender Go type mapping (duckdb-go v2.5.4 source)** (verified): vector_setters.go/types.go: TIMESTAMP, TIMESTAMP_S/_MS/_NS, TIMESTAMP_TZ accept only time.Time (castToTime rejects everything else; value converted with ti.UTC() and stored as UnixMicro for TIMESTAMP/TIMESTAMP_TZ). UUID accepts duckdb.UUID ([16]byte), *duckdb.UUID, or []uint8 of length 16 - NOT a string (the repo's events_hot.uuid is VARCHAR, so it appends a string today). MAP accepts only duckdb.Map (type Map map[any]any); initMap wires setFn to setMap (an 'unsupported' TYPE_MAP branch exists only in the generic setVectorVal fallback). STRUCT accepts map[string]any or a Go struct via reflection. LIST accepts any slice. JSON-aliased columns (type.go aliasJSON = "JSON") are VARCHAR vectors whose setter runs json.Marshal(val) on whatever you pass, so passing a Go string yields a quoted JSON string literal; pass a map[string]any/[]any (or json.RawMessage) to store an object. Unsupported for append: UHUGEINT, BIT, ANY, BIGNUM. Test TestAppenderWithJSON appends json.Unmarshal'd map[string]any into UBIGINT, TINYINT[], STRUCT(...), STRUCT(...)[] columns. — source: https://github.com/duckdb/duckdb-go (files vector_setters.go, vector.go, types.go, type.go, appender_test.go at v2.5.4 in the local module cache)
- **Repo's current DuckDB usage** (verified): event_store/storage/duckdb.go opens with sql.Open("duckdb", dbPath), then SET temp_directory / SET memory_limit from config; the writer does conn.Raw -> duckdb.NewAppenderFromConn(dConn, "", "events_hot"), builds tags := make(duckdb.Map), AppendRow(event.EventUUID, ..., event.Timestamp, ..., tags) per event and returns appender.Flush(); the view is CREATE VIEW events AS ... FROM read_parquet('%s', hive_partitioning = true, union_by_name = true) UNION ALL events_hot; archive uses CREATE TEMP TABLE move_batch AS ... then COPY move_batch .... — source: /home/shankar/Personal/solid_trace/event_store/storage/duckdb.go
- **INSERT vs Appender performance** (verified): 'Performing row-by-row inserts (even with prepared statements) is detrimental to performance and will result in slow load times.' 'Unless your data is small (<100k rows), avoid using inserts in loops.' Preferred: scanner extensions, bulk Parquet/CSV load, then 'the Appender' (C, C++, Go, Java, Rust). C docs: 'Appenders are the most efficient way of loading data into DuckDB from within the C interface'. No official rows/sec figure is published. — source: https://duckdb.org/docs/current/guides/performance/import.html
- **Concurrency model** (verified): 'One process can both read and write to the database' OR 'Multiple processes can read from the database, but no processes can write.' Within one process DuckDB uses 'a combination of MVCC (Multi-Version Concurrency Control) and optimistic concurrency control'; 'Multiple threads can also simultaneously update separate tables or separate subsets of the same table'; 'Appends will never conflict, even on the same table'; conflicts only when 'two threads attempt to edit (update or delete) the same row at the same time' (error 'Transaction conflict: cannot update a table that has been altered!', rerun the transaction). Multi-process writing 'is not supported automatically and is not a primary design goal'. So a long-running SELECT on a connection does not block Appender flushes from another connection; readers see their snapshot. — source: https://duckdb.org/docs/lts/connect/concurrency
- **Checkpointing / WAL in a long-lived process** (likely): checkpoint_threshold / wal_autocheckpoint: 'The WAL size threshold at which to automatically trigger a checkpoint', default '16.0 MiB', scope GLOBAL. CHECKPOINT 'synchronizes data in the write-ahead log (WAL) to the database data file'; 'The default CHECKPOINT command will fail if there are any running transactions'; 'FORCE CHECKPOINT aborted any in-progress transactions. From v1.4, it waits until it can grab the checkpoint lock'. Checkpoint partially reclaims deleted-row space (row groups with ~25% deletes). DuckDB 1.5.0 added non-blocking checkpointing ('During checkpointing, it's now possible to run concurrent reads, writes, insertions with indexes and deletes', +17% TPC-H throughput), implying that on 1.4.3 a checkpoint holds an exclusive lock and concurrent queries wait while it runs. — source: https://duckdb.org/docs/current/sql/statements/checkpoint.html and https://duckdb.org/2026/03/09/announcing-duckdb-150
- **1.4.0 LTS features relevant to storage** (verified): 1.4.0 added AES-256-GCM database encryption (ENCRYPTION_KEY covering db, WAL and temp files), MERGE INTO, a k-way merge sort rework, 'In-Memory Checkpointing' with '5-10x compression gains and space reclamation after deletes', and CTEs materialize by default. — source: https://duckdb.org/2025/09/16/announcing-duckdb-140
- **Resource settings are instance-global** (verified): Configuration table: memory_limit/max_memory 'The maximum memory of the system' default '80% of RAM' GLOBAL; threads/worker_threads default '# CPU cores' GLOBAL; temp_directory GLOBAL; max_temp_directory_size default '90% of available disk space' GLOBAL; preserve_insertion_order default true GLOBAL; parquet_metadata_cache 'Cache Parquet metadata - useful when reading the same files multiple times' default false GLOBAL; enable_object_cache 'Legacy setting - does nothing'; max_expression_depth default 1000. SET docs: GLOBAL = 'across the entire DuckDB instance', SESSION = 'only for the current session', LOCAL 'Not yet implemented', and when unspecified 'For most options this is GLOBAL'. No query-timeout setting exists in the configuration reference. Therefore there is no per-connection/per-query memory or thread cap. — source: https://duckdb.org/docs/current/configuration/overview.html and https://duckdb.org/docs/lts/sql/statements/set
- **Larger-than-memory / tuning** (verified): Set preserve_insertion_order = false when 'importing or exporting datasets (from/to the Parquet or CSV formats), which are much larger than the available memory' (lets DuckDB re-order results without ORDER BY). Default row group size is 122,880 rows; using k threads needs at least k x 122,880 rows. Spilling to temp_directory is supported for GROUP BY, JOIN, ORDER BY and windows, but list()/string_agg() cannot offload and multiple blocking operators may still OOM. 'SET threads = X' if HyperThreading over-launches threads. — source: https://duckdb.org/docs/lts/guides/performance/how_to_tune_workloads
- **Query cancellation from Go** (verified): duckdb-go v2.5.4 statement.go executeBound(): starts a goroutine 'go func() { select { case <-ctx.Done(): mapping.Interrupt(s.conn.conn) ... case <-mainDoneCh: } }()' around mapping.ExecutePending, so cancelling/timing out the Go context calls duckdb_interrupt ('Interrupt running query') on that connection; interrupted queries surface as ErrorTypeInterrupt ('INTERRUPT Error'). This is the only timeout mechanism; use context.WithTimeout per user query. Appender/Flush has no context. — source: https://github.com/duckdb/duckdb-go (statement.go, errors.go at v2.5.4; duckdb_interrupt in https://duckdb.org/docs/lts/clients/c/connect)
- **Same DB file opened twice in one process** (verified): C API: duckdb_create_instance_cache - 'The instance cache is necessary if a client/program (re)opens multiple databases to the same file within the same process', and duckdb_get_or_create_from_cache 'retrieves an existing database instance'. duckdb-go v2.5.4 duckdb.go uses GetInstanceCache = sync.OnceValue(mapping.CreateInstanceCache) and mapping.GetOrCreateFromCache(GetInstanceCache(), getDBPath(dsn), &db, config, ...) on every open, so a second sql.Open of the same path (e.g. with access_mode=read_only for sandboxing) returns the SAME instance and cannot carry different global settings; separate read-only processes are also disallowed while the Go writer holds the file read-write. — source: https://duckdb.org/docs/lts/clients/c/connect (verified against duckdb-go v2.5.4 duckdb.go)
- **Securing untrusted SQL** (verified): Settings: SET enable_external_access = false ('ATTACH cannot attach to a database in a file. COPY cannot read from or write to files'); SET disabled_filesystems = 'LocalFileSystem'; SET allowed_directories = ['/tmp'] / SET allowed_paths = [...]; SET autoload_known_extensions = false; SET autoinstall_known_extensions = false; SET allow_community_extensions = false; allow_unsigned_extensions default false; resource limits SET threads = 4; SET memory_limit = '4GB'; SET max_temp_directory_size = '4GB'; then SET allowed_configs = ['memory_limit','threads']; SET lock_configuration = true (must set limits before locking; 'Security-related configuration settings generally lock themselves'). Warning: 'Treat SQL in DuckDB like code in Bash or Python. Do not execute SQL from untrusted sources without proper sandboxing' - these are defense-in-depth, not a sandbox. All are GLOBAL, so enabling them disables COPY TO parquet for the archiver in the same instance. — source: https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview.html
- **Validating user SQL as SELECT-only** (likely): json_serialize_sql: 'Serialize a set of semicolon-separated (;) select statements to an equivalent list of json serialized statements.' json_deserialize_sql reverses it; json_execute_serialized_sql runs one at a time. Invalid SQL returns a JSON object like {"error": true, "error_type": "parser", "error_message": "syntax error at or near \"TOTALLY\"", "error_subtype": "SYNTAX_ERROR", "position": "0"}. Usage: SELECT json_serialize_sql($user_sql) - gives a parse-level AST to enforce a single SELECT and inspect referenced tables/functions before execution. Behaviour for non-SELECT statements is not documented (expected: error). — source: https://duckdb.org/docs/lts/data/json/sql_to_and_from_json
- **Scoping a query to one project (macros / temp objects)** (verified): CREATE MACRO name(params) AS TABLE SELECT ... defines a table macro ('may return a table of arbitrary size and shape'); default params (b := 5), overloads, CREATE OR REPLACE TEMP MACRO is connection-scoped; macros 'are expanded (i.e., replaced with the original expression)' at bind time (no recursion). E.g. CREATE MACRO project_logs(pid) AS TABLE SELECT * FROM logs WHERE project_id = pid. Go README: 'Temporary objects and state, such as temporary tables, are scoped to connections... To disable keeping idle connections alive, use db.SetMaxIdleConns(0).' A wrapping CTE is the simplest: WITH logs AS (SELECT * FROM logs_all WHERE project_id = $1) <user SELECT>. — source: https://duckdb.org/docs/lts/sql/statements/create_macro and https://github.com/duckdb/duckdb-go/blob/main/README.md
- **Parquet COPY options (1.4 LTS)** (verified): COPY (SELECT ...) TO 'path' (options). General: FORMAT (auto from extension), PARTITION_BY VARCHAR[] ('Hive partitioning scheme'), OVERWRITE_OR_IGNORE BOOL false, OVERWRITE BOOL false ('all existing files inside targeted directories will be removed'), APPEND BOOL false ('in the event a filename pattern is generated that already exists, the path will be regenerated'), FILENAME_PATTERN (may contain {uuid}/{uuidv4}/{uuidv7} or {i}), FILE_EXTENSION, FILE_SIZE_BYTES, PER_THREAD_OUTPUT false, RETURN_FILES false, RETURN_STATS false, WRITE_PARTITION_COLUMNS false, USE_TMP_FILE auto, PRESERVE_ORDER. Parquet: ROW_GROUP_SIZE BIGINT default 122880, ROW_GROUP_SIZE_BYTES (default row_group_size x 1024), ROW_GROUPS_PER_FILE, COMPRESSION default snappy (uncompressed, snappy, gzip, zstd, brotli, lz4), COMPRESSION_LEVEL 3 (zstd only), PARQUET_VERSION V1, FIELD_IDS, KV_METADATA. Partitioned write: COPY orders TO 'orders' (FORMAT parquet, PARTITION_BY (year, month)) yields orders/year=2021/month=1/data_1.parquet; 'One file is written per thread to each directory'; partitioned_write_max_open_files default 100; 'at least 100 MB of data per partition' recommended; 'Writing data into many small partitions is expensive'. — source: https://duckdb.org/docs/lts/sql/statements/copy and https://duckdb.org/docs/current/data/partitioning/partitioned_writes.html
- **Parquet layout guidance** (verified): Aim for 'row groups of 100K-1M rows each' (single giant row group = one thread); row groups below 5,000 rows gave 'runtimes more than 5-10x larger' (8.77 s at 960-row groups vs 0.87 s at 122,880+); keep 'Parquet files between 100 MB and 10 GB'; have at least as many row groups across files as CPU threads; queries on Parquet are 'approximately 1.1-5.0x slower' than on a DuckDB table; prefer Snappy/LZ4/zstd over gzip. Write sorted with COPY (SELECT ... ORDER BY col) TO 'file.parquet' (FORMAT parquet, ...). — source: https://duckdb.org/docs/current/guides/performance/file_formats.html
- **Row-group statistics and pruning** (verified): DuckDB 'supports projection pushdown into the Parquet file itself' and 'filter pushdown into the Parquet reader', skipping row groups using 'built-in zonemaps' (min/max statistics) when present. For native tables DuckDB 'automatically creates zonemaps (also known as min-max indexes) for the columns of all general-purpose data types' per row group; 'the more ordered the data within a column, the more valuable the zonemap indexes will be' (ordering a datetime column: 2.5x smaller storage, 1.5x faster). ART indexes do not help analytical scans, slow inserts/checkpoints and are not buffer-managed. parquet_metadata() exposes row_group_id, row_group_num_rows, stats_min, stats_max, stats_null_count, min_is_exact, max_is_exact, bloom_filter_offset, bloom_filter_length. — source: https://duckdb.org/docs/current/guides/performance/indexing.html and https://duckdb.org/docs/lts/data/parquet/overview
- **Parquet Bloom filters** (verified): DuckDB 1.2.0 added 'both reading and writing of Parquet Bloom filters'. Written for dictionary-encoded columns of integer types (TINYINT..UBIGINT), FLOAT/DOUBLE, VARCHAR and BLOB; 'Nested types (lists, structs, arrays) are currently not supported'. COPY options DICTIONARY_SIZE_LIMIT (default 10% of row group size, i.e. 12,288 of 122,880 rows) and BLOOM_FILTER_FALSE_POSITIVE_RATIO (default 0.01). Used for 'constant-comparison filter predicates in the query (e.g., WHERE a = 42)'. Benchmark: 0.002 s vs 0.1 s for an absent value; ~47 bytes per row group overhead. Probe with parquet_bloom_probe(filename, column_name, value). — source: https://duckdb.org/2025/03/07/parquet-bloom-filters-in-duckdb.html
- **Hive partitioning reads** (verified): 'Filters on the partition keys are automatically pushed down into the files' so WHERE year = 2022 AND month = 11 reads only matching directories; auto-detection of key=value paths; hive_types autodetects DATE, TIMESTAMP and BIGINT partition values (disable with hive_types_autocast = 0), or specify hive_types = {'release': DATE}. Example: SELECT * FROM read_parquet('orders/*/*/*.parquet', hive_partitioning = true). Note pruning applies to filters on the partition column (event_date), not on the row-level timestamp column - those rely on row-group min/max after opening each footer. — source: https://duckdb.org/docs/current/data/partitioning/hive_partitioning.html
- **read_parquet over many files / union_by_name / filename** (verified): Default schema unification is 'by position' from the first file; union_by_name unifies by name with missing columns NULL, and 'Using the union_by_name option increases memory consumption' because the schema of every file must be read; it cannot be combined with the schema parameter. filename is a virtual column 'automatically since v1.3.0' (SELECT *, filename FROM read_parquet('test/*.parquet')); file_row_number is available; globs and lists read_parquet(['a/*.parquet','b/*.parquet']) are supported. parquet_metadata_cache (default false) caches footers 'when reading the same files multiple times'. DuckDB 1.3 also added an in-memory 'external file cache' (SET enable_external_file_cache = false to disable; duckdb_external_file_cache()). — source: https://duckdb.org/docs/current/data/multiple_files/combining_schemas.html and https://duckdb.org/docs/current/data/parquet/overview.html and https://duckdb.org/2025/05/21/announcing-duckdb-130
- **VIEW over hot UNION ALL parquet; glob refresh** (likely): 'The view is not physically materialized. Instead, the query is run every time the view is referenced in a query.' CREATE OR REPLACE VIEW replaces in place. Because the view body (including read_parquet('<glob>')) is re-bound per query, the glob is re-expanded on each query and the current practice of recreating the view after each archive is not required for new files to appear (it is only needed if the glob string or schema handling changes). Filter pushdown through UNION ALL to each side (hot table zonemaps, Parquet row-group stats/partition keys) is standard DuckDB optimizer behaviour but is not explicitly documented on this page. — source: https://duckdb.org/docs/current/sql/statements/create_view.html
- **Text search operators** (verified): LIKE (% and _; 'LIKE pattern matching always covers the entire string'), ILIKE ('case-insensitive according to the active locale'), ~~/!~~/~~*/!~~*, SIMILAR TO (regex, whole string), GLOB. Regex functions use 'the RE2 library'; regexp_matches 'Returns true if string contains the regexp pattern'; regexp_extract, regexp_full_match, regexp_replace; 'regexp_matches operator will be optimized to the LIKE operator when possible' (anchored ^hello -> prefix, world$ -> suffix, '.' -> '_'); 'To achieve best performance, the c option (case-sensitive matching) should be passed if applicable'; flags i, c, l (literal), g, s, m/n/p. — source: https://duckdb.org/docs/current/sql/functions/regular_expressions.html and https://duckdb.org/docs/current/sql/functions/pattern_matching.html
- **Text scan throughput** (uncertain): No primary DuckDB source states a GB/s figure for VARCHAR scans. Secondary: MotherDuck's DuckDB 1.3 post reports '5-25% faster LIKE '%text%' and CONTAINS string scans' via a unified memchr-based implementation. String storage uses per-segment auto-selected compression: 'Dictionary encoding... particularly efficient when storing text columns with many duplicate entries' and 'FSST compression is an extension to dictionary compression, that... extracts repetitions within strings' (URLs, emails); enable_fsst_vectors (default false) lets scans emit compressed vectors. Treat substring search as a full scan bounded by time/structured prefilters. — source: https://duckdb.org/2022/10/28/lightweight-compression.html (and https://motherduck.com/blog/announcing-duckdb-13-on-motherduck-cdw/ for the 1.3 number)
- **FTS extension** (verified): PRAGMA create_fts_index(input_table, input_id, *input_values, stemmer='porter', stopwords='english', ignore='(\\.|[^a-z])+', strip_accents=1, lower=1, overwrite=0); PRAGMA drop_fts_index(input_table); creates schema fts_<database>_<table> (e.g. fts_main_documents) with macro match_bm25(input_id, query_string, fields := NULL, k := 1.2, b := 0.75, conjunctive := 0). Critical: 'The FTS index will not update automatically when the input table changes'; the workaround is 'recreating the index'. It is therefore unusable as an incremental index on an append-only log table (would require periodic full rebuilds). — source: https://duckdb.org/docs/current/core_extensions/full_text_search.html
- **Time-series helpers** (verified): time_bucket(bucket_width, timestamp[, offset]) 'Truncate ... to a grid of width bucket_width. The grid is anchored at 2000-01-01[ + offset]' (2000-01-03 for week widths), e.g. time_bucket(INTERVAL '10 minutes', TIMESTAMP '1992-04-20 15:26:00', INTERVAL '5 minutes') -> 1992-04-20 15:25:00; time_bucket(bucket_width, timestamp[, origin]); TIMESTAMPTZ variant anchored at origin (timezone-aware). date_trunc(part, ts) e.g. date_trunc('hour', TIMESTAMP '1992-09-20 20:38:40') -> 1992-09-20 20:00:00. Gap filling: generate_series(TIMESTAMP '2001-04-10', TIMESTAMP '2001-04-11', INTERVAL 30 MINUTE) is closed-range; range(...) is half-open; e.g. SELECT b, coalesce(n,0) FROM generate_series($from, $to, INTERVAL 1 MINUTE) AS g(b) LEFT JOIN (SELECT time_bucket(INTERVAL 1 MINUTE, ts) b, count(*) n FROM logs WHERE ... GROUP BY 1) c USING (b) ORDER BY b. epoch_ms(ts), make_timestamp(micros) also available. — source: https://duckdb.org/docs/current/sql/functions/timestamp.html
- **Approximate and quantile aggregates** (verified): approx_count_distinct(x) 'using HyperLogLog'; approx_quantile(x, pos) 'using T-Digest'; approx_top_k(arg, k) 'a LIST of the k approximately most frequent values of arg using Filtered Space-Saving'; reservoir_quantile(x, q, sample_size=8192); quantile_cont(x, pos) interpolated, quantile_disc(x, pos) actual value, both accept a LIST of positions e.g. quantile_cont(x, [0.25, 0.5, 0.75]); median(x) = quantile_cont(x, 0.5); histogram(arg) returns a MAP of bucket->count; arg_max(arg, val); mode(x); count(*), count(arg), countif(arg); FILTER clause e.g. sum(amount) FILTER (WHERE region != 'north'). Note list()/string_agg() cannot spill to disk. — source: https://duckdb.org/docs/current/sql/functions/aggregates.html
- **ASOF JOIN** (verified): FROM holdings h ASOF JOIN prices p ON h.ticker = p.ticker AND h.when >= p.when (inequality must be the last condition); ASOF LEFT JOIN keeps unmatched left rows with NULLs; USING form ASOF JOIN prices p USING (ticker, "when") where the last USING column is the >= inequality. Semantics: match 'the most recent price before the holding's timestamp'. — source: https://duckdb.org/docs/current/guides/sql_features/asof_join.html
- **duckdb-go driver notes** (likely): Config via DSN or NewConnector(dsn, func(execer driver.ExecerContext) error { bootQueries ... }) e.g. "/path/to/foo.db?access_mode=read_only&threads=4"; Arrow interface opt-in with -tags="duckdb_arrow" and 'Arrow connections are not safe for concurrent use'; 'All allocations live in the host process. Especially for long-running applications, it is crucial to call the corresponding Close-functions.' README (main) also says JSON columns 'Cannot scan directly into string or []byte; use Composite type instead' and 'Both TIMESTAMP and TIMESTAMP_TZ store as instants without offset info; use duckdb.Typed()' - these two notes are from the current main README and may postdate v2.5.4 (Typed was added in v2.10503.0). — source: https://github.com/duckdb/duckdb-go/blob/main/README.md

## Design implications

- Decide the engine version first: the pinned duckdb-go v2.5.4 = DuckDB 1.4.3, whose LTS line goes EOL on 2026-09-16. Staying on 1.4 means no VARIANT (upgrade at least to v2.5.6 / 1.4.5 for fixes); moving to duckdb-go v2.10505.0 (DuckDB 1.5.5) unlocks VARIANT (auto-shredded binary semi-structured data with Parquet shredding) and non-blocking checkpoints, both directly relevant to a log store. The Go Appender/driver API is the same across both lines, so the ingester code is unaffected.
- On 1.4.x, model a log row as: fixed typed columns (project_id BIGINT, ts TIMESTAMP, level, service/source, message VARCHAR) + attrs MAP(VARCHAR,VARCHAR) for flat string attributes (Appender takes duckdb.Map, bracket access attrs['k'] returns a scalar, keys can vary per row) + raw JSON (VARCHAR-backed) for the full nested payload queried with ->>/json_extract lists. Provide a Rails-managed 'promoted fields' mechanism: run json_group_structure/json_keys over a sample to discover keys, then ALTER TABLE ADD COLUMN and backfill via json_transform, so hot query paths hit zonemap-able typed columns instead of JSON parsing.
- Keep the Appender path exactly as today (batch -> AppendRow -> Flush), but note that on the Go side timestamps must be time.Time (converted to UTC micros), UUID columns need duckdb.UUID/[16]byte (the current VARCHAR uuid is fine but a real UUID column would be smaller and zonemap-able with UUIDv7), and a JSON column must receive a map[string]any/[]any (or json.RawMessage), not a Go string, or it will be stored as a quoted string. Rows become visible at Flush; the engine auto-commits every 204,800 rows, so the 1 s flush cadence is fine for near-real-time tailing.
- Order matters for pruning: append logs in arrival order (roughly time-ordered) so hot-table zonemaps on ts work, and archive with COPY (SELECT ... FROM events_hot WHERE event_date = ? ORDER BY project_id, ts) TO '<parquet>' (FORMAT parquet, PARTITION_BY (event_date), ROW_GROUP_SIZE 122880, COMPRESSION zstd). Consider PARTITION_BY (project_id, event_date) for multi-tenant pruning if per-project daily volume stays >=100 MB, otherwise keep event_date only and rely on Bloom filters (dictionary-encoded VARCHAR/BIGINT columns, equality predicates) plus row-group min/max on project_id.
- Rewrite the query layer so every user filter on time also emits a predicate on the partition column (event_date BETWEEN ...) because hive pruning only applies to partition keys; row-level ts filters only prune row groups after each footer is read. Turn on SET parquet_metadata_cache = true (GLOBAL) so repeated dashboard queries do not re-read thousands of footers, and reconsider union_by_name = true (it forces reading every file's schema and raises memory) in favour of writing every Parquet file with the same explicit column list.
- The 'events' VIEW is re-executed and re-globbed on every query, so recreating it after each archive is unnecessary; the same VIEW pattern (hot UNION ALL read_parquet) is appropriate for logs, and a single CREATE OR REPLACE VIEW per schema change is enough.
- Text search must be scan-based: the FTS index is not incremental (full rebuild only), so the product should not promise inverted-index search. Implement 'contains' with time range + structured prefilters first, then contains()/ILIKE on message, and translate KQL-style regex to regexp_matches(..., 'c') where possible so DuckDB can rewrite to LIKE/prefix/suffix. Budget for full scans over the selected window; sample results (LIMIT) early and stream. Optional future: maintain a small per-day trigram/token side table yourself if needed.
- Sandboxing raw SQL from users cannot rely on DuckDB settings alone: enable_external_access/lock_configuration/memory_limit/threads are GLOBAL and would also disable the archiver's COPY TO; duckdb-go's instance cache returns the same instance for a second sql.Open of the file, and read-only processes are forbidden while the Go writer holds the file. Practical design for the KQL/query-builder feature: generate SQL yourself (preferred, Axiom-like), and for a raw-SQL escape hatch (a) parse with json_serialize_sql to enforce a single SELECT and whitelist referenced relations/functions, (b) wrap in WITH logs AS (SELECT * FROM logs_all WHERE project_id = $1) ... or a per-project TEMP MACRO / TEMP VIEW on a dedicated connection (db.SetMaxIdleConns(0) caveat), (c) enforce LIMIT and run with context.WithTimeout (duckdb-go interrupts the query on ctx.Done()), and (d) run user queries on a small pool separate from the ingest connection. If true isolation is required, run untrusted SQL in a separate process over the Parquet tier only, with enable_external_access=false + allowed_directories=[parquet_path] locked.
- Dashboards and monitors map cleanly to built-ins: time_bucket(INTERVAL $w, ts) + generate_series gap-fill for charts; approx_count_distinct, approx_top_k(attrs['k'], 10) and unnest(map_entries(attrs)) for 'top values' facets; quantile_cont(x,[0.5,0.95,0.99]) / approx_quantile for latency panels; FILTER clauses for multi-series counts in one scan; ASOF JOIN for enriching logs with deploy/release timelines. Precompute per-minute rollups in Rails/Solid Queue jobs if monitors evaluate frequently.
- Operationally: keep memory_limit and temp_directory set (already done), consider SET threads to leave CPU for Fiber and Pebble, expect 1.4.x checkpoints (every 16 MiB of WAL) to briefly block concurrent queries, and prefer larger Appender batches over more frequent flushes so WAL churn stays low. Treat DuckDB's rule of one writer process as binding: Rails must never open the DuckDB file; all reads go through the Go HTTP API (which still needs auth).

## Open questions

- Do you upgrade to DuckDB 1.5.x (duckdb-go v2.105xx) before shipping logs? It changes the answer on VARIANT (recommended for schemaless attributes) and on checkpoint blocking, and the 1.4 LTS support window ends 2026-09-16.
- Exact behaviour of automatic checkpoints on 1.4.3 while long SELECTs are running (does the auto-checkpoint wait, skip, or block new queries?) is not spelled out in the docs; worth a small load test with a 30 s query plus continuous Appender flushes.
- Whether json_serialize_sql rejects non-SELECT statements with an error object (docs say it serializes 'select statements' but do not show the failure case) and whether it exposes enough of the AST to whitelist functions such as read_parquet/read_csv/getenv.
- Real ingest throughput of the duckdb-go Appender with a MAP + JSON column per row on your hardware (no official numbers exist); also whether appending a JSON column via json.Marshal per row is a CPU bottleneck versus storing the pre-serialized payload in a VARCHAR column.
- How well the UNION ALL view pushes ts/project_id filters into read_parquet across thousands of daily files, and the footer-read cost with union_by_name=true versus a fixed schema; measure with EXPLAIN ANALYZE at 1k+ files.
- Whether PRAGMA create_fts_index can target a VIEW (or must be a base table) if you ever want periodic rebuilt indexes over a hot window.
- Real-world VARCHAR scan speed for contains()/ILIKE on your message column sizes (no primary GB/s figure exists); decide the maximum searchable window per query from measurement.
- Whether to include project_id in PARTITION_BY (better pruning, many small files) or rely on Bloom filters and ORDER BY project_id, ts within daily partitions.
