## Summary

SolidTrace keeps all process/tooling docs in the repo root: `AGENTS.md` is a 4-line index that points at `docs/agents/{issue-tracker,triage-labels,domain}.md`; those three files define the whole agent workflow. Issues/specs live as plain markdown under `.scratch/<feature-slug>/` (spec at `spec.md`, one file per ticket under `issues/`), triaged with five canonical `Status:` strings, and conversation appends under a `## Comments` heading. The domain model is a single-context glossary in `CONTEXT.md` (terms + `_Avoid_:` synonyms + Relationships + Example dialogue + Flagged ambiguities) with ADRs in `docs/adr/NNNN-slug.md` — that directory does not exist yet, so a logging feature would author ADR `0001`. The skills that drive all of this are vendored in `.agents/skills/` and symlinked into `.claude/skills/`; `domain-modeling/CONTEXT-FORMAT.md` and `domain-modeling/ADR-FORMAT.md` are the authoritative templates, and `to-tickets/SKILL.md` carries the local ticket template. Dev runs via `bin/dev` (foreman + `Procfile.dev`: Rails on 4001, Vite, `bin/go-dev` building EventStore on 4000, Solid Queue `bin/jobs`). Tests are `bin/test` (Rails Minitest then `go test ./...`); the Go suite is not hermetic because `event_store/integration_test.go` shells out to `bin/rails db:reset` in `console/`. Load tests are k6 scripts in `load_testing/` driven by `bin/load-test`, with scenarios defined in three places (a `FINGERPRINT_INTERVALS` map, a `case` whitelist in the runner, and README/README tables) — and `bin/load-test` currently points at a stale path `test/load/k6/`. CI (`.github/workflows/ci.yml`) is Ruby-only and broken: every step invokes `bin/console/<tool>` while the binstubs actually live at `console/bin/<tool>`, `scan_js` is commented out, the `system-test` job uses an unsupported `build:` key on a service container, and there is no Go job at all. Grepping the whole repo for logs/logging/metrics/tracing/OpenTelemetry/dashboards/query-language turns up essentially nothing: the feature is greenfield, and `CONTEXT.md` currently lists "log line" as a term to *avoid* for **Event**.

## Conventions

- Issue tracker path pattern: one directory per feature at `.scratch/<feature-slug>/`; the spec is `.scratch/<feature-slug>/spec.md`; implementation tickets are one file per ticket at `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, numbered from `01`, never a single combined tickets file. `.scratch/` is committed (not gitignored).
- Every issue file carries a `Status:` line near the top. The five triage Status labels, verbatim: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Tickets generated by /to-tickets default to `ready-for-agent`.
- Conversation/history on an issue appends to the bottom of the file under a `## Comments` heading. Anything an AI writes during triage must be prefixed with the line `> *This was generated by AI during triage.*`.
- Local ticket template (from .agents/skills/to-tickets/SKILL.md): `# <NN>: <Ticket title>`, then `**What to build:**` (end-to-end user-visible behaviour, not a layer list), `**Blocked by:**` (numbers/titles, or "None (can start immediately)"), `**Status:** ready-for-agent`, then `- [ ]` acceptance criteria. Avoid file paths and code snippets in tickets — they go stale.
- The one existing issue file uses a richer de facto format worth matching for a large feature: H1 title, bold `**Source:**` (pointer to the review/spec section), `**Severity:**`, `**Area:**`, then `## Problem`, `## Impact`, `## Proposed fix`, `## Acceptance criteria` (checkboxes), `## Out of scope`. Add the missing `Status:` line that the docs require.
- Tickets are vertical tracer-bullet slices: each cuts a complete path through schema/API/UI/tests, is demoable on its own, and fits one context window; prefactoring goes first; wide mechanical refactors use expand–contract batches instead.
- Spec template (.agents/skills/to-spec/SKILL.md): `## Problem Statement`, `## Solution`, `## User Stories` (long numbered "As a <actor>, I want <feature>, so that <benefit>" list), `## Implementation Decisions`, `## Testing Decisions` — written in the CONTEXT.md vocabulary, no file paths.
- ADRs: `docs/adr/NNNN-slug.md`, 4-digit sequential (the directory does not exist yet, so the first logging ADR is `docs/adr/0001-<slug>.md`). Body is a title plus 1-3 sentences saying context/decision/why; Status frontmatter, Considered Options and Consequences are optional and only when they add value. Only write an ADR when the decision is hard to reverse, surprising without context, and the result of a real trade-off.
- CONTEXT.md is a glossary and nothing else — no implementation detail, no spec content. New terms go under `## Language` as `**Term**:` + one or two sentences defining what it IS + an `_Avoid_:` line listing rejected synonyms; relationships are added as bullets under `## Relationships`; unresolved naming clashes go under `## Flagged ambiguities`. Terms are added lazily, the moment they are resolved, not batched.
- Introducing **Log** requires resolving a live conflict: CONTEXT.md currently defines **Event** with `_Avoid_: log line, message`. Either redefine Event's avoid-list or record the Log/Event boundary explicitly (and note it under Flagged ambiguities), per docs/agents/domain.md's instruction to surface contradictions rather than silently override.
- Running tests: `bin/test` from the repo root runs both suites (`cd console && rails test`, then `cd ../event_store && go test ./...`). Rails-only: `cd console && bin/rails test` / `bin/rails test:system`; full local CI chain: `cd console && bin/ci` (driven by `console/config/ci.rb`). Go-only: `cd event_store && go test ./...`.
- Rails tests are Minitest with FactoryBot (`include FactoryBot::Syntax::Methods` in test_helper.rb), no fixtures, parallelization commented out; layout is test/{models,controllers,jobs,mailers,system,lib}. System tests use `console/test/system/smoke_test.rb`. Go tests are table-style `*_test.go` next to the package (ingest, storage, pkg/msgpacker) plus a root `integration_test.go`.
- Dev workflow: `bin/dev` (foreman + Procfile.dev) starts Rails on 4001, Vite, EventStore on 4000 via `bin/go-dev`, and Solid Queue. `bin/go-dev` rebuilds the Go binary with `-gcflags="all=-N -l"` each start. `bin/clear-ports` frees 4000/4001. `bin/reset-db` wipes ./storage, deletes schema files and re-runs db:reset/prepare/seed — per .agent/rules/project.md, migrations may be edited in place pre-launch as long as bin/reset-db is run afterwards.
- Go config convention: every new setting needs three edits in `event_store/config/config.go` — a default in `Load()`, a pointer field with a `yaml:"snake_case"` tag on `fileConfig`, and a nil-checked apply clause in `applyFileConfig` — and a documented example in `deploy/event_store.yml`. The file is chosen by `EVENT_STORE_CONFIG` (default `event_store.yml` in cwd).
- Ruby style is rubocop-rails-omakase + rubocop-performance with `# frozen_string_literal: true` required (except db/migrate). Go style is gofmt + Effective Go (MixedCaps, small interfaces, errors returned not panicked) per .agents/skills/effective-go.
- Frontend rules (.agent/rules/system_prompt.md, always-on for *.js/*.tsx): use the active shadcn/Radix primitives, never hand-roll modals/dropdowns; skinny controllers with logic in service objects; no N+1 (eager load by default); schema-first with FKs, unique constraints and indexes; strictly separate server state from UI state.
- Rails routing convention: all tenant pages live under `scope "/:org_slug"`, project-scoped resources nest under `resources :projects, param: :slug`; a JSON API mirror lives under `namespace :api { namespace :v1 }`. Pages are Inertia components under `console/app/frontend/pages/<Resource>/`, controllers set `layout "dashboard"`.
- Go->Rails messaging goes through the msgpack+zstd SQLite outboxes (`event_store_messages` for ingest-derived facts, `console_messages` for Rails->Go commands), never direct HTTP from Go to Rails.

## Pitfalls

- CI is currently non-functional and must not be treated as a safety net: every step in `.github/workflows/ci.yml` shells out to `bin/console/brakeman`, `bin/console/bundler-audit`, `bin/console/rubocop`, `bin/console/rails` — no `bin/console/` directory exists (the binstubs are at `console/bin/*`). `scan_js` is fully commented out, the `system-test` job declares `services.event_store.build:` which GitHub Actions service containers do not support (only `image:`), and there is no Go job at all (also flagged in review.md §10).
- `event_store/integration_test.go` shells out to `bin/rails db:reset` inside `console/`, so `go test ./...` fails on a clean checkout without a working Ruby toolchain. New log ingest tests should not deepen this coupling; prefer package-level tests in `ingest/`, `storage/`, `pipeline/`.
- `bin/load-test` sets `K6_SCRIPT="$ROOT_DIR/test/load/k6/event_ingestion.js"` but the scripts live in `load_testing/`, so the runner cannot work as written. `load_testing/README.md` and `README.md` also reference `test/load/k6/` throughout, and README's benchmark table is all placeholder dashes.
- Adding a k6 scenario requires edits in four places that can silently drift: `FINGERPRINT_INTERVALS` in `load_testing/lib/config.js`, the `case` whitelist in `bin/load-test`, the usage/help text in `bin/load-test`, and the scenario tables in both READMEs.
- `event_store/Dockerfile` does not build: base is `golang:1.24-bookworm` while `go.mod` requires 1.25.5, and `CGO_ENABLED=0` breaks DuckDB and mattn/go-sqlite3 (both cgo-only). Any logging work that ships a new binary or image inherits this.
- The read/query API has no authentication at all (`event_store/main.go` registers routes with zero middleware) and `deploy/angie/angie.conf` publishes port 4000 on all interfaces. A log query API added the same way would be a second cross-tenant data-disclosure surface; see `.scratch/prod-readiness/issues/002-query-api-authentication.md` for the agreed fix shape (internal shared-secret header + edge path allowlist + project-scoped payload fetch).
- Events acknowledged with 200 can be lost: shutdown never closes `pebbleChan` so up to 150k buffered events are dropped on restart; `pebble.NoSync` is on; `pipeline/pebble_ingester.go` drops events when the DuckDB channel is full (diverging Pebble and DuckDB); `DuckDBIngester.flush()` discards the whole batch on write error with no retry. A log pipeline copying this shape copies all four.
- `DuckDBWriter.ArchiveEventsForDate` is explicitly marked `// TODO: Need to refactor this completely. AI slop.` (event_store/storage/duckdb.go:440) and builds SQL by string interpolation of the date. Its COPY-then-commit is non-atomic: if COPY succeeds and Commit fails, the Parquet file survives while rows stay in events_hot, and because the view globs the parquet dir on boot, those rows are returned twice. Do not clone this for a logs archive.
- No retention, TTL, prune or DeleteRange exists anywhere in the Go service; Pebble, the Parquet archive, and both outbox tables (`event_store_messages`, `console_messages`, ~170k rows/day) grow forever. Logs are far higher-volume than errors, so a logging feature that does not ship retention will kill single-VM installs quickly.
- Go writes Rails' primary SQLite directly (`event_store/storage/sqlite.go`), reimplementing `assign_number` and the status/kind enums as magic integers, and every ingested event takes a read (new fingerprints a write transaction) on the same single-writer SQLite file Rails uses. That is the real ingest ceiling; a log ingest path that also touches Rails SQLite per record would make it worse. Prefer the outbox.
- No metrics endpoint exists despite `prometheus/client_golang` already being a transitive dep and Pebble exposing rich `Metrics()`. Channel depths, batch sizes and drop counts are exactly what a log pipeline needs to be observable.
- `fiber.New` sets no `BodyLimit` (4MB default) and there is no rate limiting or per-project quota — acute for log ingest, where batched payloads are large and clients are chatty.
- Issue-list UX already suffers from the schema gap (no times_seen/first_seen_at/last_seen_at, no pagination, 2xN HTTP round-trips per render, `title LIKE '%q%'` full scans). A logs UI built on the same synchronous-Rails-to-Go-per-row pattern will not render.
- `.scratch/prod-readiness/issues/` is currently untracked in git and contains only `002-...` (3-digit, no `Status:` line, no `001`, no `spec.md`), so the one available example deviates from the documented convention in three ways. Follow `docs/agents/issue-tracker.md`, not the example, where they disagree.
- `console/app/models/project_key.rb` hardcodes the DSN to `localhost:3000` with project id 1; the k6 config defaults to `PUBLIC_KEY=testkey123` from db/seeds.rb. Any log SDK/DSN onboarding copy will inherit the same broken snippet unless fixed.

## Open questions

- What feature slug should the logging effort use — e.g. `.scratch/logging/` vs `.scratch/logs-v1/` — and should it start with a `spec.md` (per /to-spec) or a `review.md`-style source-of-truth doc like `.scratch/prod-readiness/review.md`, from which tickets are derived?
- Should the plan also fix the documented-vs-actual drift in the tracker (missing `001`, 3-digit numbering, missing `Status:` line, untracked issues/ directory), or leave prod-readiness alone and simply follow docs/agents/issue-tracker.md for the new feature?
- How should **Log** relate to **Event** in CONTEXT.md, given Event's current `_Avoid_: log line, message`? Options: Log as a sibling top-level term with Event narrowed to 'Sentry error payload'; or a shared parent term (e.g. Record/Signal) with Event and Log as specialisations. This also decides whether Dataset/Source is a new tenant-scoped noun or a property of Project.
- Which logging decisions warrant ADRs under the skill's three-part test? Candidates: DuckDB (not ClickHouse) as the log analytics engine; schemaless ingest via a DuckDB MAP/JSON/STRUCT column vs schema-on-write; a custom KQL-like language vs SQL passthrough; logs sharing the Pebble+DuckDB+Parquet pipeline vs getting their own. The plan should name which of these get docs/adr/0001..000N.
- Should log ingest be a new route on the existing Fiber app on port 4000 (inheriting the unauthenticated-read-API and no-BodyLimit problems) or a separate listener/socket that the angie edge treats differently? This determines whether issue 002's auth work is a blocker for logging.
- Does logging get its own DuckDB database/table (`logs_hot` + a `logs` view + its own Parquet partitions) or share `events_hot`? Affects the archive job, retention design, and config keys in event_store.yml.
- Should CI be repaired (bin/console/* paths, add a Go job, un-comment scan_js) as part of the logging effort, or tracked as a separate prerequisite ticket? Without it, no logging ticket can claim 'CI green' as an acceptance criterion.
- What scenario axes should the log-ingest k6 scenarios cover (payload size, fields-per-record cardinality, number of distinct sources/datasets, batch size per request) and should the existing `bin/load-test` grow a `--kind logs` flag or should a separate `bin/log-load-test` be added?
- Are Monitor and Dashboard Console-owned (Rails models + Solid Queue evaluation, reusing the Integration notifier path) or EventStore-owned (Go evaluating saved queries on a timer)? The glossary entries and the ADR both depend on this.
