## Summary

The Go EventStore is a single Fiber v2 process that owns three storage engines (Pebble for raw blobs, DuckDB for analytics, SQLite for issue/fingerprint writes) plus two SQLite-backed outboxes that bridge it to Rails. Auth is a single read-only SQLite lookup: `auth.ProjectAuth.ValidateKey(publicKey)` selects `project_id` from Rails' `project_keys` table (`solid_trace.sqlite3` opened with `?mode=ro`), and `handler.IngestHandler.extractSentryKey` pulls the key from `X-Sentry-Auth`, then `Authorization`, then `?sentry_key=` via the regex `sentry_key=([^,\s]+)`. Note the `:project_id` path segment is decorative — the effective project comes from the key, never from the URL. The outbox is bidirectional and lives in a *separate* SQLite file (`message_queue.sqlite3`): `storage.MessageQueueWriter.EnqueueMessage(type, payload)` writes msgpack+zstd (SpeedFastest, marker byte 0=raw/1=zstd, 10KB threshold) rows into `event_store_messages` for Rails (`issue_created`, `issue_received_event`), while `storage.MessageQueueReader` polls `console_messages` for Rails→Go commands (only `archive_events` today, 5s ticker, batch 10, attempts<5, status enum pending/processing/processed/failed matching the Rails `ConsoleMessage`/`EventStoreMessage` enums). Tests are plain stdlib `testing`: `t.TempDir()` for Pebble/DuckDB/parquet dirs, `logger.Init()` at the top of every test (or in `TestMain`), hand-rolled fakes for repository interfaces in `ingest/service_test.go`, and a full black-box `integration_test.go` (`package main_test`) that shells out to `bin/rails db:reset` in `../console` with `RAILS_ENV=test`, seeds a `project_keys` row, wires the real channels/ingesters with short flush timeouts, builds a fresh `fiber.App` with the route table duplicated from main.go, and drives it through `app.Test(req, 2000)` with `time.Sleep` for pipeline settling. Health is a single `GET /health` that pings Pebble and DuckDB and returns 200/503 — there are no metrics, no `/metrics`, no Prometheus registry, and no request logging middleware. Deployment is Docker Compose with `network_mode: host` everywhere; Angie (nginx fork) listens on :80 → Rails console and :4000 → the Go process over a unix socket at `/var/run/solid-trace/event_store.sock` (the Go process binds the socket when `ingest_socket` is set, chmod 0660, else falls back to TCP `:4000`). The bundled DuckDB engine is **v1.4.3** (duckdb-go v2.5.4 → duckdb-go-bindings v0.1.24, whose Makefile pins `DUCKDB_VERSION=v1.4.3`).

## Conventions

- Package layout by role: auth/, config/, handler/, ingest/, models/, pipeline/, storage/, pkg/<lib>. A logging feature should add handler/logs.go, ingest/log_service.go, pipeline/log_*_ingester.go, storage/logs_duckdb.go rather than a new top-level tree.
- Module path is github.com/solidtrace/event_store; all internal imports use that prefix (no internal/ dir, no vendoring).
- Logging is via the global logf logger `logger.L` with key-value pairs: logger.L.Info("msg", "key", val) / .Fatal on startup failures. Never fmt.Println; always call logger.Init() before use (tests included).
- Errors are wrapped with fmt.Errorf("context: %w", err); storage constructors return (*T, error) and callers logger.L.Fatal in main.go.
- SQLite DSNs are always built as path + "?_busy_timeout=5000&_journal_mode=WAL&_synchronous=NORMAL" for writers, and path + "?mode=ro" for the auth reader.
- Timestamps written to SQLite use time.Now().Format("2006-01-02 15:04:05.000000") to match Rails' string datetime format.
- Config keys are snake_case YAML, mirrored as pointer fields in fileConfig, with a nil check per field in Load() before overriding the Go default. Never read env vars for config except EVENT_STORE_CONFIG and DEBUG.
- Handlers are structs with a New<Name>Handler(deps...) constructor taking already-built storage/auth objects; routes are registered explicitly in main.go (no router groups, no middleware chain today).
- Auth in a handler is three lines: extract key -> 401 if empty -> ValidateKey -> 401 if err or 0. Trust the returned project_id, never the :project_id URL param.
- Outbox message types are lowercase snake_case string literals defined as constants near the consumer (archiveMessageType) or inline at the enqueue site; payloads are structs with `msgpack:"field"` tags or plain maps.
- Any new Go->Rails message_type requires a matching `when` branch in console/app/jobs/event_store_message_processor_job.rb; any new Rails->Go command requires a ConsoleMessage.create! plus a consumer goroutine started in main.go.
- Tests are stdlib `testing` only (no testify): t.TempDir() for all on-disk state, logger.Init() first, table-free explicit assertions with t.Fatalf/t.Errorf, fakes hand-written as structs implementing the production interface.
- Pipeline components follow the Run()/Stop() goroutine pattern with a context.CancelFunc and a time.Ticker, started with `go x.Run()` in main.go and `defer x.Stop()`.
- Deployment assumes host networking + unix sockets under /var/run/solid-trace, data under /storage (hot) and /storage_cold (archives), config bind-mounted read-only at /etc/solid-trace/event_store.yml.

## Pitfalls

- auth.ProjectAuth.ValidateKey does an uncached SQLite query per ingest request against the Rails DB file. At log volumes (10-100x error volume) this becomes the hot path bottleneck and also couples log ingest availability to the Rails SQLite file. Needs an in-memory key cache before shipping logs.
- ValidateKey returns (0, err) on a real DB error, and handler code treats err and projectID==0 identically as 401 — a corrupt/locked DB surfaces to shippers as an auth failure, which log agents will retry forever rather than back off.
- The :project_id URL param is never compared against the project_id resolved from the key. Any valid key can post to any project's URL; the path segment is cosmetic. Do not build log routing on the path param.
- No auth at all on the read/query API (GET /api/:project_id/events*, /api/events/:uuid). A log query API added the same way would be world-readable to anything that can reach :4000 — and logs leak far more PII than error events.
- No rate limiting, no per-project quotas, no body-size limit override (fiber default BodyLimit is 4MB) and no backpressure signalling. Ingest channels are buffered (50k/100k) and the pipeline drops or blocks silently when full; a log firehose will hit this immediately.
- Angie has no client_max_body_size directive on the :4000 server block, so nginx/angie's 1MB default will 413 bulk log batches before Fiber ever sees them.
- event_store/Dockerfile builds with CGO_ENABLED=0 while the binary imports mattn/go-sqlite3 and duckdb-go (both cgo). This image is stale/broken relative to the current dependency set — do not assume it builds; also go.mod says go 1.25.5 while the Dockerfile pins golang:1.24-bookworm.
- ingest/service + storage/sqlite.go are hard-wired to the error model (issues, issue_fingerprints, project_issue_counters, fingerprint classification). A log pipeline must NOT go through ingest.Service; it needs its own service or the issue coupling leaks into logs.
- models.Event and the DuckDB events_hot table are fixed-schema (fixed columns + a single MAP(VARCHAR,VARCHAR) tags column). Schemaless log attributes with mixed types (ints, floats, bools, nested objects) do not fit MAP(VARCHAR,VARCHAR) without lossy stringification; this is the central design decision the logging feature must resolve (separate logs_hot table with MAP/STRUCT/JSON or per-project evolving columns).
- The single DuckDB file/connection is shared by ingest appends, the archive COPY, and all read queries. Long analytical log queries will contend with the 1s ingest flush and with view recreation during archive. No read replica, no separate DuckDB instance for logs.
- recreateEventsView rebuilds the `events` view over read_parquet globs; a growing number of log parquet partitions makes glob planning progressively slower and there is no manifest/metadata catalog.
- The archive consumer marks a message processing/processed with no transaction around the COPY + hot-table delete, and retries up to 5 attempts; a partially-completed archive can double-write a parquet partition on retry.
- Outbox consumers poll on a fixed 5s ticker with no jitter and no leader election; running more than one event_store process against the same message_queue.sqlite3 will double-process messages (FetchPendingMessages has no row locking / claim step that is atomic with the read).
- MessageQueueReader/Writer open separate connections to the same SQLite file; busy_timeout is only 5s, and WAL writes from Rails jobs + Go consumers can still surface SQLITE_BUSY under load.
- No metrics of any kind: no /metrics, no Prometheus registry (prometheus/client_golang is only an indirect dep via pebble), no request logging middleware, no ingest counters or channel-depth gauges. /health only pings Pebble and DuckDB — it does not check SQLite, the outbox, or pipeline lag, so a wedged ingester still reports healthy.
- logger.L is a package-level var set by Init(); forgetting logger.Init() in a new test or goroutine path causes a nil-pointer panic rather than a no-op.
- integration_test.go shells out to `bin/rails db:reset` in ../console and writes to fixed relative paths ../storage/sqlite/test/*.sqlite3 (not TempDir), so tests are not hermetic, cannot run in parallel, and require a working Rails toolchain. It also relies on time.Sleep for pipeline settling, which is flaky under load.
- Docker Compose uses network_mode: host for every service while angie.conf proxies to `http://console:80` — the compose service-name upstream cannot resolve under host networking, so the deploy config as committed is internally inconsistent (only the unix-socket :4000 block is reliable).
- Pebble keys are the raw 16-byte UUIDv7 with no project prefix, so there is no efficient per-project scan or per-project deletion in the blob store — a log retention/GDPR-delete feature would need a different key layout (e.g. project_id || timestamp || uuid).
- The Go->Rails outbox rows are never pruned by Go; growth of event_store_messages is Rails' responsibility, and a chattier logs feature will amplify it.

## Open questions

- Should logs share the existing DuckDB file/`events_hot` lineage or get a dedicated logs.duckdb + logs_hot table and its own parquet tree? This drives config keys, the view-recreation logic, and read/write contention.
- How are schemaless log attributes typed in DuckDB 1.4.3 — MAP(VARCHAR,VARCHAR) (lossy, consistent with events), MAP(VARCHAR,JSON), a JSON column, or dynamically-added columns per project? DuckDB 1.4.3 supports JSON type, MAP, STRUCT and variant-ish patterns, but column pruning/index behavior differs sharply between them.
- Do logs need durable raw-blob storage in Pebble at all, or can they go straight to DuckDB? The current Pebble hop exists to serve the single-event detail view by UUID; logs may not need it, which would halve the write amplification.
- Should log ingest reuse the Sentry public key or get a separate ingest token type (Vector/Fluent Bit/OTel shippers do not speak X-Sentry-Auth)? If separate, does project_keys grow a `kind` column or does a new table appear?
- What is the KQL-like query engine's home — a Go parser (participle/ANTLR are NOT currently direct dependencies; antlr4-go is only an indirect transitive dep) compiled to DuckDB SQL, or a Rails-side parser posting SQL to Go? No query-language code exists anywhere today.
- Read-path auth is unresolved: the query API has none. Does the logging query API get the same treatment (Rails proxies via app/services/event_store.rb and Go stays unauthenticated behind the socket), or does Go finally get real auth?
- What backpressure contract do log shippers get — 429 with Retry-After, 503, or silent drop? The current pipeline has no answer and log agents behave badly without one.
- Retention/TTL: who deletes old log parquet partitions, Rails via a console_messages command or a Go-internal sweeper, and is retention per project or global?
- Does the daily-archive granularity (one partition per day) work for logs, or is hourly partitioning needed for query pruning at log volumes?
- Is the Dockerfile expected to be fixed (CGO_ENABLED=1, go 1.25) as part of this work, or is deployment currently done outside Docker?
- Should a second event_store process ever run (for query isolation)? If so, the outbox consumer needs an atomic claim and the unix socket topology needs rethinking.
