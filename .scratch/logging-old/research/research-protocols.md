# Prior research: protocols

> Extracted from workflow run `wf_25055e4a-726` (solidtrace-logs-discovery, 2026-09-13, Fable subagents). Reference only: claims were not re-verified and design implications were never decided.


## Summary

Four ingest protocols were researched against primary sources. (1) Sentry Structured Logs travel in the existing envelope as an item with header {"type":"log","item_count":N,"content_type":"application/vnd.sentry.items.log+json"} whose payload is {"items":[{timestamp (epoch seconds float), trace_id, span_id?, level (trace|debug|info|warn|error|fatal), body, severity_number?, attributes:{key:{value,type}}}]} with attribute types string|integer|double|boolean (Relay also accepts "array"); SDKs flush at 100 logs or 5 s, max 100 logs per envelope, and the envelope is authenticated exactly like events (X-Sentry-Auth / ?sentry_key / envelope "dsn" header), so SolidTrace's existing POST /api/:project_id/envelope route already receives them — but the current Go IngestEnvelope only reads the first item and ignores the `length` header, so log items are silently dropped today. Ruby >=5.24.0 (on by default since 7.0.0), JS >=9.41.0 (enableLogs, default on since 10.71.0), Python >=2.35.0 (enable_logs, later default), Go >=0.33.0 (default on since 0.47.0) all emit this item. (2) OTLP/HTTP logs are POST /v1/logs on port 4318 with Content-Type application/x-protobuf or application/json, optional Content-Encoding: gzip; JSON uses lowerCamelCase, int64 as decimal strings, traceId/spanId as hex, enums as integers, AnyValue as {stringValue|boolValue|intValue|doubleValue|arrayValue|kvlistValue|bytesValue}; responses are 200 with optional partialSuccess{rejectedLogRecords,errorMessage}, 400 with Status, 429/503 with Retry-After. go.opentelemetry.io/proto/otlp v1.11.0 needs only grpc + protobuf + grpc-gateway (grpc and protobuf are already indirect deps of event_store), while collector/pdata pulls in a much larger tree. (3) Vector's http sink with codec json defaults to character-delimited ',' framing wrapped in [ ] with Content-Type application/json (or application/x-ndjson with newline_delimited framing), batches 10 MB/1 s, supports gzip/zstd, bearer/basic auth, and its default timestamp key is "timestamp" in RFC 3339; Fluent Bit's http output defaults to format json (a JSON array), json_date_key "date", json_date_format double (epoch float seconds) with iso8601/epoch/epoch_ms alternatives and compress gzip; Axiom's contract is POST /v1/ingest/{dataset} with application/json | application/x-ndjson, Bearer auth, gzip/zstd/br/deflate, _time as the canonical timestamp and optional timestamp-field/timestamp-format query params. A single POST /api/:project_id/logs accepting a JSON array or NDJSON (sniffed by first non-whitespace byte, not by Content-Type), gzip/zstd, and a timestamp-detection order of _time > timestamp > time > ts > dt > @timestamp > date with RFC3339/epoch s/ms/us/ns heuristics covers Vector, Fluent Bit, and Axiom-style shippers with 3-5 lines of config each. (4) Syslog is not worth v1: leodido/go-syslog v4 (parsers only, active in 2026, Go 1.22+) is the right parser if added later, while gopkg.in/mcuadros/go-syslog.v2 (server + parsers) has had no commits since March 2020; a TCP/UDP listener also complicates the per-project auth model. Vector/Fluent Bit can front syslog and forward over the HTTP contract in the meantime.

## Findings

- **Sentry logs: envelope item header** (verified): The Sentry envelope item type for structured logs is "log". Required item headers per the spec example: {"type":"log","item_count":5,"content_type":"application/vnd.sentry.items.log+json"}. The envelope-items spec constrains: "An envelope MUST contain at most one envelope item containing logs. SDKs MAY mix logs from different traces in the same envelope item." — source: https://develop.sentry.dev/sdk/telemetry/logs/
- **Sentry logs: payload schema** (verified): Payload is a JSON object with an items array (spec example, verbatim): {"version":2,"ingest_settings":{"infer_ip":"auto","infer_user_agent":"auto"},"items":[{"timestamp":1544719860.0,"trace_id":"5b8efff798038103d269b633813fc60c","span_id":"b0e6f15b45c36b12","level":"info","body":"User John has logged in!","severity_number":9,"attributes":{"sentry.message.template":{"value":"User %s has logged in!","type":"string"},"sentry.message.parameter.0":{"value":"John","type":"string"}}}]}. Required per log: timestamp (number, Unix epoch seconds), trace_id (32-char hex), level (one of trace, debug, info, warn, error, fatal), body (string). Optional: span_id (16-char hex), severity_number (OpenTelemetry integer 1-24), attributes. Spec: the log item "SHOULD include version and ingest_settings properties to instruct Relay to infer IP address and user agent" — version/ingest_settings are optional top-level keys a receiver must tolerate. — source: https://develop.sentry.dev/sdk/telemetry/logs/
- **Sentry logs: attribute value types** (verified): The SDK spec lists attribute types string, integer, double, boolean, each encoded as {"value":..., "type":"..."}. Relay's schema (relay-event-schema/src/protocol/attributes.rs) accepts AttributeType variants serialized as "boolean", "integer", "double", "string", "array", plus Unknown(String) forwarded as-is; integer values must be I64/U64 and double must be F64. Relay's OurLog struct has fields timestamp, trace_id, span_id, level, body, severity_number, attributes and an 'other' map for forward compatibility; OurLogLevel is Trace|Debug|Info|Warn|Error|Fatal|Unknown(String). Relay test fixture: {"timestamp":1544719860.0,"trace_id":"5b8efff798038103d269b633813fc60c","span_id":"eee19b7ec3c1b174","level":"info","body":"Example log record","attributes":{"string.attribute":{"value":"some string","type":"string"}}}. — source: https://raw.githubusercontent.com/getsentry/relay/master/relay-event-schema/src/protocol/attributes.rs
- **Sentry logs: default attributes, batching and size limits** (verified): SDKs always attach sentry.sdk.name, sentry.sdk.version, sentry.environment (if defined), sentry.release (if defined), sentry.replay_id (if replay active); backend SDKs add server.address; mobile add os.name/os.version/device.*; parameterized logs add sentry.message.template and sentry.message.parameter.X; integrations set sentry.origin (manual API calls MUST NOT). Buffering: flush at 100 logs or 5 seconds; maximum 100 logs per envelope (hard limit since spec 1.15.0); hard queue limit 1000 queued logs (since 1.12.0). Envelope-level limits: 200 MiB whole envelope post-decompression; 1 MiB per item for events, spans, logs, metrics. sentry.trace.parent_span_id was replaced by top-level span_id in spec 1.11.0. — source: https://develop.sentry.dev/sdk/telemetry/logs/
- **Sentry logs: sendDefaultPii and breadcrumbs** (verified): Spec: "SDKs MAY attach user information as attributes, guarded by sendDefaultPii" for user.id, user.name, user.email; since spec 2.1.0 these are sent regardless when the user explicitly set them. Relay marks body and attributes as PII-scrubbable fields. Breadcrumbs are not an envelope item type — they remain part of the event payload (relay has a separate breadcrumb.rs; the envelope-items page lists no breadcrumb item); the logs spec contains no statement that logs replace or feed breadcrumbs, so they are independent streams. — source: https://develop.sentry.dev/sdk/telemetry/logs.md

- **Sentry envelope auth and transport** (verified): Envelope endpoint: {BASE_URI}/api/{PROJECT_ID}/envelope/. Auth header: X-Sentry-Auth: Sentry sentry_version=7, sentry_client=<client>, sentry_key=<public key>, sentry_secret=<secret, only if DSN had one>; alternative query string ?sentry_version=7&sentry_key=...; or the envelope header "dsn" carrying the full DSN ("If multiple forms of authentication are given, the endpoint validates that the information matches and otherwise rejects the request"). Envelope headers: dsn, sdk, sent_at (RFC 3339). Item header length is the payload byte count; "When omitted, the payload implicitly goes to the next newline"; length is mandatory when the payload contains newlines. Request Content-Type application/x-sentry-envelope (text/plain etc. also accepted). Accepted Content-Encoding: gzip, deflate, br, zstd. Consequence: log items arrive on the same authenticated route as events; no new auth path is needed. — source: https://develop.sentry.dev/sdk/foundations/transport/authentication/
- **SolidTrace current envelope parsing gap** (verified): event_store/ingest/service.go IngestEnvelope does strings.SplitN(string(envelope), "\n", 3), reads only the first item header, returns nil for any type other than "event"/"transaction", and never honours the item 'length' header. A Sentry SDK envelope containing a log item (alone, or after an event item) is therefore silently dropped, and a multi-item envelope whose first item is an event would lose the following log item. Handler passes c.Body() straight through (event_store/handler/ingest.go:72). — source: /home/shankar/Personal/solid_trace/event_store/ingest/service.go

- **Recommended canonical HTTP contract for SolidTrace** (likely): POST /api/:project_id/logs. Auth: accept Authorization: Bearer <sentry public key> AND X-Sentry-Auth / ?sentry_key= (reuse auth/project.go) so Vector (auth.strategy bearer or request.headers) and Fluent Bit (Header Authorization Bearer ...) both work unchanged. Body: a JSON array of objects, a single JSON object, or NDJSON; decide by the first non-whitespace byte ('[' => array, '{' => NDJSON/one-per-line, tolerating Fluent Bit json_stream concatenation by using a streaming json.Decoder loop) rather than trusting Content-Type (Fluent Bit sends application/json for json, Vector sends application/json or application/x-ndjson). Message detection: message > msg > body > log > event. Limits mirroring Axiom: 10,000 events/request, 1 MiB per event, field name <= 200 bytes. ## Design implications

- Fix the envelope parser first: rewrite ingest.Service.IngestEnvelope to iterate over all items (honouring the item 'length' header, falling back to next-newline when absent) and dispatch by type — 'event'/'transaction' to the existing event path, 'log' to a new log path — otherwise every Sentry SDK log item is silently discarded today. The 'log' item's content_type is application/vnd.sentry.items.log+json and item_count gives the number of records for pre-sizing.
- Sentry logs need no new auth or route: they arrive on POST /api/:project_id/envelope with X-Sentry-Auth / ?sentry_key / envelope 'dsn' header, so the existing auth/project.go check applies. Because Ruby 7.x, JS 10.71+, Python 2.68+ and Go 0.47+ enable logs by default, existing SolidTrace users will start sending log items as soon as they upgrade SDKs — the Go side must at minimum not error on them (it currently ignores them, but only if they are the first item).
- Define one internal canonical log record in Go (pkg/logs or models): timestamp (int64 ns UTC), observed_at, project_id, level (trace/debug/info/warn/error/fatal), severity_number (OTLP 1-24), body/message TEXT, trace_id (32 hex), span_id (16 hex), service/host/environment/release columns pulled from well-known keys, and attributes as MAP(VARCHAR,VARCHAR) plus a typed side-map or JSON column for numeric attributes so that KQL-like numeric filters/aggregations work. Three adapters map onto it: Sentry log item (attributes {value,type} where type in string/integer/double/boolean/array), OTLP LogRecord (AnyValue oneof, hex traceId, int64-as-string), and the generic JSON contract (heuristic key detection).
- Add POST /api/:project_id/logs (generic JSON array | NDJSON, sniffed by first byte; gzip+zstd; Bearer or X-Sentry-Auth; timestamp detection _time > timestamp > time > ts > dt > @timestamp > date; RFC3339 or epoch s/ms/us/ns by magnitude; 10k events / 1 MiB per event limits; Axiom-style {ingested, failed, failures} response; 429 + Retry-After on backpressure) so Vector (codec json, default framing) and Fluent Bit (Format json default, or json_lines) work with 3-5 config lines and no timestamp options.
- Add POST /api/:project_id/v1/logs (and accept /v1/logs with Bearer key or X-Sentry-Auth header so exporters that only allow a base endpoint + headers still work) using go.opentelemetry.io/proto/otlp v1.11.0 for protobuf (grpc + protobuf are already indirect deps of event_store; grpc-gateway is the only notable addition). For OTLP/JSON, do not rely on protojson alone because it expects base64 traceId/spanId and lowerCamelCase handling of int64-as-string only partially; either hand-write a small OTLP/JSON decoder for the logs subset (ResourceLogs > ScopeLogs > LogRecord with AnyValue) or pull go.opentelemetry.io/collector/pdata (requires go 1.26, adds featuregate/json-iterator/multierr/slim proto). Respond 200 with an empty ExportLogsServiceResponse (or partialSuccess{rejectedLogRecords,errorMessage}) in the same encoding as the request, 400 with google.rpc.Status for undecodable bodies, 429/503 with Retry-After on backpressure. Skip OTLP/gRPC in v1.
- Pipeline reuse: logs should bypass Pebble raw-blob-per-event (Sentry SDKs already batch 100 per envelope, Vector 10 MB/1 s, Fluent Bit per-flush) and go straight from the adapter to a logsChan -> DuckDB Appender into a new logs_hot table with the same events/read_parquet UNION ALL view and daily Parquet partition archive that events_hot uses; do not write logs to the SQLite outbox or create Rails issues per line. Keep Rails responsible only for retention settings, tokens and UI.
- Level/severity normalisation must be a shared function: Sentry level string -> severity_number (trace=1, debug=5, info=9, warn=13, error=17, fatal=21), OTLP severity_number -> level bucket, generic strings (warning, err, critical, panic, emerg...) -> nearest of the six; store both so KQL `where level == "error"` and range filters on severity_number both work.
- Do not build a syslog listener in v1; document Vector `sources: type: syslog` / Fluent Bit `[INPUT] Name syslog` fronting the HTTP contract. If added later, use github.com/leodido/go-syslog/v4 (maintained, parsers only) and avoid gopkg.in/mcuadros/go-syslog.v2 (no commits since 2020).
- Because the read API has no auth today, adding logs makes that gap worse (logs typically contain more PII than error events); the logs work should land together with read-side auth, and the Sentry 'body' and 'attributes' fields are marked PII-scrubbable in Relay — SolidTrace should at least offer per-project attribute-key drop lists (equivalent to beforeSendLog) on the Rails side.

## Open questions

- Fiber v2's c.Body() decompresses gzip/deflate/br automatically when Content-Encoding is set; whether the pinned Fiber v2.x version also handles zstd (needed for Vector's default zstd on the axiom sink and optional zstd on http sink, and Fluent Bit compress zstd) was not verified and should be checked in go.mod/go.sum.
- Sentry Relay's exact per-attribute limits for logs (max attribute count, key length, value length) were not found on develop.sentry.dev or in the fetched Relay schema files (relay-server processor/ourlog.rs path returned 404); only the 1 MiB per-item and 100-logs-per-envelope limits are documented.
- Whether SolidTrace should treat OTLP 'resource' attributes (service.name, host.name, deployment.environment) as first-class columns mirroring events_hot(environment, server_name, release) or fold them into the attributes map — a schema decision, not a protocol question.
- For OTLP/JSON decoding in Go the trade-off between a hand-written subset decoder, protojson with a pre-pass that base64-encodes hex traceId/spanId, or adopting collector/pdata (go 1.26 requirement) needs a spike; none was benchmarked here.
- Axiom's public docs no longer expose exact request-size or events-per-request limits for the ingest endpoint beyond '10,000 events per batch' and '1 MB field size' on the limits page; the recommended SolidTrace limits are modelled on those but should be validated against DuckDB Appender batch memory.
- Sentry Python: docs state logs are enabled by default and 2.68.x moved auto-capture of stdlib logging to LoggingIntegration(capture_sentry_logs=...); the exact parameter name/default for the logging-level threshold (sentry_logs_level) was not confirmed from the integration page.
