# Prior research: betterstack

> Extracted from workflow run `wf_25055e4a-726` (solidtrace-logs-discovery, 2026-09-13, Fable subagents). Reference only: claims were not re-verified and design implications were never decided.


## Summary

Better Stack Logs (now branded "Telemetry") is a ClickHouse-backed log platform whose ingest is deliberately schemaless: POST any JSON object, JSON array, NDJSON, or MessagePack to a per-source ingesting host with `Authorization: Bearer $SOURCE_TOKEN`; an optional top-level `dt` field (UNIX s/ms/ns or RFC 3339) overrides receipt time, and everything else is stored verbatim in a single `raw` JSON column alongside `dt`. Shippers (Vector http sink, Fluent Bit http output to `/fluentbit` in msgpack, OTLP/HTTP at `/v1/logs|traces|metrics`, platform SDKs) all converge on that same endpoint shape. Querying has three tiers: (1) the Live tail filter language (`key:value` contains, `=`/`!=`, `=~` regex, `>`/`<` numerics, AND/OR, fulltext, explicitly NO `*`/`?` wildcards) which works over raw JSON with zero config; (2) ClickHouse SQL via `remote(t<id>_<source>_logs)` for recent data and `s3Cluster(primary, t<id>_<source>_s3)` for historical data, where every field access is `JSONExtract(raw, 'a', 'b', 'Nullable(String)')`; (3) a KQL-like PQL (`{{source}} | where ... | summarize ... by time = {{time}}`) that compiles to SQL. Dashboards are charts (`line_chart`, `bar_chart`, `number_chart`, `table_chart`, `scatter_chart`, `heatmap_chart`) whose SQL must return `time`/`value`/optional `series` columns and uses `{{source}}`, `{{time}}`, `{{start_time}}`, `{{end_time}}`, `{{interval_seconds}}` macros plus user variables with `[[ optional ]]` blocks; alerts hang off a chart query (`chart_alerts` with `alert_type`, `operator`, `value`, `query_period`, `aggregation_interval`, `check_period`, `recovery_period`). The main "harder than Axiom" cost is that fast dashboards over a field require configuring per-source "Extract metrics" (logs-to-metrics) expressions into a separate NVMe-backed metrics table with its own `label()`/`countMerge`/`avgMerge` schema; raw-JSON queries over object storage are documented as "much slower at scale", and users must manually UNION hot and S3 tables, pick `sampling`, and stay under 4 concurrent log queries. Retention is per source (`logs_retention`, `metrics_retention` in days), sources group into Source Groups, and there are no request-rate limits (10 MiB compressed per request, 10 MiB per record, 100 KiB recommended).

## Findings

- **Ingest: endpoint and auth** (verified): HTTP ingest is `POST https://$INGESTING_HOST` (path `/`), header `Authorization: Bearer $SOURCE_TOKEN`, `Content-Type` one of `application/json`, `application/x-ndjson`, `application/msgpack`. Each Source has its own `ingesting_host` and `token` (from the Sources API). Response codes: 202 success, 402 quota exceeded, 403 invalid source token, 406 invalid JSON/MessagePack, 413 payload exceeds limit. — source: https://betterstack.com/docs/logs/ingesting-data/http/logs/
- **Ingest: accepted body shapes (verbatim examples)** (verified): Single event: `curl -X POST https://$INGESTING_HOST -H "Authorization: Bearer $SOURCE_TOKEN" -H "Content-Type: application/json" -d '{"message":"logs is ready","nested":{"values":123}}'`. Multiple events as JSON array: `[{"message":"A"},{"message":"B"}]`. NDJSON: `-H "Content-Type: application/x-ndjson" -d $'{"message":"A"}\n{"message":"B"}'`. MessagePack binary also accepted. Plain-text bodies are NOT listed as an accepted content type on the HTTP page; plaintext lines arrive via shippers as a `message` string field. — source: https://betterstack.com/docs/logs/ingesting-data/http/logs/
- **Ingest: the `dt` timestamp convention** (verified): Optional top-level `dt` field overrides reception time. Accepted: UNIX seconds `1672490759`, milliseconds `1672490759123`, nanoseconds `1672490759123456000`; RFC 3339 strings `2022-12-31T13:45:59.123456Z` or `2022-12-31 13:45:59.123456+02:00`; MessagePack timestamp extension type. If `dt` is unparseable it is kept as a plain string field and the event is stamped with receipt time. Arbitrary nesting of other fields is allowed (`{"nested":{"values":123}}`). — source: https://betterstack.com/docs/logs/ingesting-data/http/logs/
- **Ingest: size and rate limits** (verified): Max single request 10 MiB compressed (413 documented at 20 MiB); max single record 10 MiB uncompressed; recommended under 100 KiB per record; 'there is no limit to the number of requests you can send'. Sampling is not done at the ingest endpoint; it is a knob on the Better Stack collector config (remotely adjustable) or done in VRL by dropping events. — source: https://betterstack.com/docs/logs/ingesting-data/http/logs/
- **Ingest: Vector shipper payload shape** (verified): Vector uses a plain `http` sink to the same endpoint, with a remap transform to rename Vector's `timestamp` to `dt`: `transforms: better_stack_transform: {type: remap, inputs: ['*'], source: '.dt = del(.timestamp)'}`; `sinks: better_stack: {type: http, method: post, inputs: [better_stack_transform], uri: 'https://$INGESTING_HOST/', encoding: {codec: json}, compression: gzip, auth: {strategy: bearer, token: '$SOURCE_TOKEN'}}`. — source: https://betterstack.com/docs/logs/vector/
- **Ingest: Fluent Bit shipper payload shape** (verified): Fluent Bit config verbatim: `[OUTPUT] name http / match * / tls On / host $INGESTING_HOST / port 443 / uri /fluentbit / header Authorization Bearer $SOURCE_TOKEN / header Content-Type application/msgpack / format msgpack / retry_limit 5`. Note the dedicated `/fluentbit` path (Fluent Bit's msgpack framing differs from the generic msgpack body). — source: https://betterstack.com/docs/logs/fluent-bit/
- **Ingest: OpenTelemetry (OTLP/HTTP)** (verified): OTLP endpoints: `https://$INGESTING_HOST/v1/logs`, `/v1/traces`, `/v1/metrics`, header `Authorization: Bearer $SOURCE_TOKEN`, gzip recommended. Collector exporter: `exporters: otlphttp/betterstack: {endpoint: 'https://$INGESTING_HOST', headers: {Authorization: 'Bearer $SOURCE_TOKEN'}}` with `logs/betterstack`, `traces/betterstack`, `metrics/betterstack` pipelines. Traces HTTP page: `POST /v1/traces` accepts `application/json` or `application/x-protobuf`, standard OTLP `resourceSpans` -> `scopeSpans` -> spans with `traceId` (32 hex), `spanId` (16 hex), `startTimeUnixNano`/`endTimeUnixNano` strings; spans without `endTimeUnixNano` are skipped. Logs correlate to traces via an optional `span: {trace_id, span_id}` object in the log JSON. — source: https://betterstack.com/docs/logs/open-telemetry/
- **Ingest: automatic JSON extraction from strings** (verified): If a string field contains only JSON (`{"message": "{\"text\": \"Hello\"}"}`) it is expanded in place and addressable as `message.text`. If a string is prefix text + JSON (e.g. a syslog line ending in a JSON object), the original string stays in `message` and the parsed JSON is placed under a sibling with `_json` suffix, e.g. `message_json.metadata.*`. Nested structures are addressed with dot notation. — source: https://betterstack.com/docs/logs/using-logtail/string-and-json-format/
- **Ingest: per-source VRL transforms** (verified): Each source can have a Vector Remap Language script (Sources -> Configure -> Transform; API fields `vrl_transformation_logs`, `vrl_transformation_spans`) that runs at ingest: `del(.password)`, `if .level == "debug" { del(.) }` to drop events, `. = redact(., filters: [email_pattern])`. Failed transforms do not drop the event; it is stored untransformed with `_ingest.error` / `_ingest.transform_error` fields. — source: https://betterstack.com/docs/logs/using-logtail/transforming-ingested-data/logs-vrl/
- **Storage: physical ClickHouse layout** (verified): Per-source tables addressed via ClickHouse table functions: `remote(t123456_your_source_logs)` (recent logs), `remote(t123456_your_source_spans)`, `remote(t123456_your_source_metrics)` plus `_metrics_5m` / `_metrics_1h` pre-aggregates, and `s3Cluster(primary, t123456_your_source_s3)` for historical data in object storage. Logs table exposes `dt` (timestamp) and `raw` (the full JSON log line); in the S3 table rows are discriminated by `_row_type = 1` (logs) / `_row_type = 3` (spans). Example: `SELECT dt, raw FROM remote(t123456_your_source_logs) ORDER BY dt DESC LIMIT 100 FORMAT JSONEachRow`. — source: https://betterstack.com/docs/logs/query-api/v2/live-tail/
- **Storage: wide events vs metrics (two-tier model)** (verified): Wide events are 'any time-based JSON with arbitrary structure smaller than 10MB stored in object storage' (a log line or an OTel span). Metrics are 'a set of highly compressed time-based data points with a pre-defined schema stored on local NVMe SSD drives'. Docs state querying raw events 'requires a lot more resources to process the raw wide events from object storage and will be thus much slower at scale', and recommend 'Define metrics for trends you need to chart frequently or trends you want to track long-term over large data sets' to get 'sub-second queries'. — source: https://betterstack.com/docs/logs/wide-events-time-series/
- **Storage: querying non-indexed JSON fields in SQL** (verified): Field access is always `JSONExtract(raw, 'level', 'Nullable(String)')` for top-level and `JSONExtract(raw, 'context', 'request', 'status', 'Nullable(String)')` for nested paths; `JSONExtractCaseInsensitive` has the same signature and matches `level`/`Level`. Canonical dashboard query over raw logs: `SELECT {{time}} as time, count(*) as value, JSONExtract(raw, 'level', 'Nullable(String)') AS series FROM {{source}} WHERE time BETWEEN {{start_time}} AND {{end_time}} GROUP BY time, series`. Grafana example: `SELECT toStartOfMinute(dt) AS time, JSONExtract(raw, 'status', 'Nullable(UInt16)') AS status_code, count(*) AS requests FROM remote(t123456_your_source_logs) WHERE dt >= $__fromTime AND dt < $__toTime GROUP BY time, status_code ORDER BY time ASC`. — source: https://betterstack.com/docs/logs/using-logtail/explore-logs/
- **Storage: the 'make it fast' step = Extract metrics (logs-to-metrics)** (verified): Per source, Sources -> Configure -> Extract metrics tab, '+ Metric' / '+ Label'. A metric is a JSON dot-path (`context.user.email`) or a ClickHouse SQL expression over `raw`, e.g. `JSONExtract(raw, 'request', 'duration_ms', 'Nullable(Float64)')`, `toFloat32OrNull(extract(JSONExtractString(raw, 'message'), 'in (\d+(\.\d+)?)ms'))`, `LENGTH(raw)`, with a type and chosen aggregations (avg, p95, min, max, sum, count). Labels are capped at 4,096 chars. Extracted metrics land in the metrics table (unified schema: `name`, `series_id`, `tags` map, `time`, counts `logs_count`/`spans_count`/`events_count`, states `value_avg`/`value_min`/`value_max`/`bucket_sum`) and are read back with `label('response_status')`, `sum(logs_count)`, `avgMerge(value_avg)`, `histogramQuantile(0.95)`. Labels are always strings ('toUInt16OrNull(label(...))' needed for numeric compare). Docs do not state whether extraction applies retroactively. — source: https://betterstack.com/docs/logs/dashboards/logs-to-metrics/
- **Storage: unified metrics schema (Feb '26 migration)** (verified): Old schema had one column per extracted field (`response_status`, `p95`, `_row_type = 'logs'`); new schema is row-based: 'Metrics stored as named values with labels in a tags map'. Migration example: before `SELECT response_status, request_method FROM {{source}} WHERE response_status >= 500`; after `SELECT label('response_status'), label('request_method') FROM {{source}} WHERE toUInt16OrNull(label('response_status')) >= 500`. Rule: 'No nested aggregate functions' and match merge function to state suffix (`sumMerge(bucket_sum)`). — source: https://betterstack.com/docs/logs/unifying-metrics-schema/
- **Storage: retention, sources, source groups** (verified): Source attributes (GET/POST `https://telemetry.betterstack.com/api/v2/sources`): `name`, `platform` (http, nginx, docker, kubernetes, opentelemetry, prometheus, python, go, ruby, ... 40+), `token`, `ingesting_host`, `ingesting_paused`, `logs_retention` (days), `metrics_retention` (days), `live_tail_pattern` (`{column}` template), `data_region` (`us_west` | `germany` | `singapore`), `source_group_id`, `table_name`, `custom_bucket`, `vrl_transformation_logs`, `vrl_transformation_spans`. Example response: `logs_retention: 7, metrics_retention: 14`. Source Groups (`/api/v1/source-groups`) have `id`, `name`, `sort_index`, `team_name`; the product term is 'Source group', not 'Collection'. Own-bucket option stores files in ClickHouse Native format in an S3-compatible bucket, auto-deleted after `logs_retention` unless 'Keep data after retention' is enabled. — source: https://betterstack.com/docs/logs/api/create-a-source/
- **Query UX: Live tail filter language** (verified): Simple queries are fulltext across all columns: `"hello world"`, `Started`, `404`. Compound queries use operators — all types: `=`, `!=`; strings: `:` contains, `!:` not contains, `=~` regex, `!~` not regex; numerics: `>=`, `<=`, `>`, `<`. Boolean `AND` (explicit or implicit by whitespace) and `OR`. Values: bare `hello`, quoted `"Hello World"`, numeric `500`. Nested keys via dots; keys containing dots are escaped/quoted: `"resource.attributes.service\.name"=mysql`. Explicit fulltext column: `fulltext:"Record Not Found"`. Regex literals `/Started (GET|POST)/`, `message=~/Failed (GET|POST)/`, flag `i`: `platform=~/Kubernetes|Docker/i`. Pattern exclusion: `_pattern!=6476bd6e...`. Explicit statement: asterisks and question marks are NOT supported for wildcard matching. No documented range syntax beyond combining `>=`/`<=`. — source: https://betterstack.com/docs/logs/using-logtail/live-tail-query-language/
- **Query UX: Live tail columns and message format** (verified): Live tail rows render from a per-source template of `{column}` tokens, e.g. `LEVEL: {level}, PID: {context.system.pid}`; aliases `{syslog.parameters.nested.object.id as my_id}`; bracket access for dotted keys `{context["thread.id"]}`; fallback chains `{context.runtime.thread_id|context.system.pid}`. Custom columns accept a JSON dot path (`user.email`), bracket form, or a ClickHouse SQL expression (`coalesce()`, `JSONExtract*()`, `upper()`) over `raw`. 'Explore values' on any field charts its distribution over time. — source: https://betterstack.com/docs/logs/using-logtail/formatting-logs/
- **Query UX: SQL API (ClickHouse HTTP interface)** (verified): Read-only SQL API is ClickHouse's HTTP interface on a per-region host, e.g. `curl -u $USERNAME:$PASSWORD -H 'Content-type: plain/text' -X POST 'https://eu-nbg-2-connect.betterstackdata.com?output_format_pretty_row_numbers=0' -d "SELECT dt, raw FROM remote(t123456_your_source_logs) ORDER BY dt DESC LIMIT 100 FORMAT JSONEachRow"`. Output via ClickHouse `FORMAT` (JSONEachRow, JSON, Pretty, CSV, TSV). Limits: 'up to 4 concurrent queries for logs' and '20 concurrent queries for metrics'. Historical data must be UNION ALL'ed manually: `SELECT dt, raw FROM remote(...) UNION ALL SELECT dt, raw FROM s3Cluster(primary, t123456_your_source_s3)`; `s3Cluster(primary, t..._s3, sampling = 0.5)` reads 50% of files for approximate results. Grafana connects with the ClickHouse plugin (host without port, port 443, HTTP protocol, secure) using the same credentials and `$__fromTime`/`$__toTime` macros. — source: https://betterstack.com/docs/logs/query-api/v2/dashboards/
- **Query UX: Legacy Query API v1 (Live-tail-style HTTP)** (verified): `GET https://telemetry.betterstack.com/api/v1/query` with `source_ids` (comma list), `query` (Live tail syntax), `batch` 50-1000 (default 100), `from`/`to` ISO8601 (default 30-min window), `order` `newest_first|oldest_first`; returns rows with `dt`, `message`, `level`, `source_id`, plus `pagination.next`. Deprecated 15 Aug 2024 in favour of v2 SQL API. — source: https://betterstack.com/docs/logs/query-api/
- **Query UX: PQL (KQL-like pipeline language)** (verified): PQL is 'a pipelined query language designed for writing readable queries that compile to SQL'. Queries start with `{{source}}` and chain with `|`. Operators: `as`, `count`, `extend`, `join`, `project`, `sort`, `summarize`, `take` (alias `limit`), `top`, `where` (alias `filter`). Built-ins: `count()`, `countif()`, `iff()`, `isnull()`, `isnotnull()`, `not()`, `now()`, `strcat()`, `tolower()`, `toupper()`; unknown functions pass through to ClickHouse. Examples verbatim: `{{source}} | where level == "error" | take 50`; `{{source}} | summarize value = sum(logs_count) by time = {{time}}, series = level | where time >= {{start_time}} and time <= {{end_time}}`; over raw logs: `{{source}} | project time = {{time}}, level = COALESCE(JSONExtractCaseInsensitive(raw, 'level', 'Nullable(String)'), 'null') | where time >= {{start_time}} and time <= {{end_time}} | summarize value = count() / {{sampling}} by time, level`. — source: https://betterstack.com/docs/logs/dashboards/pql-queries/
- **Dashboards: query modes and chart types** (verified): A chart's query is one of: Drag & drop (pick metrics, no SQL), Log filtering (Live tail query, last 10 minutes only), PromQL (beta), PQL, SQL (ClickHouse), plus Static text (Markdown). Chart types in dashboard JSON: `line_chart`, `bar_chart`, `number_chart`, `table_chart`, `scatter_chart`, `heatmap_chart`. Dashboard JSON top-level: `name`, `refresh_interval` (seconds, 0 = load only), `date_range_from`/`date_range_to` (`now-3h`, `now`), `sections[]`, `charts[]`; chart: `chart_type`, `name`, `x`,`y`,`w`,`h` on a 12-column grid, `settings` (`unit`, `y_axis_scale`), `chart_queries[]` (`query_type: sql_expression`, `sql_query`), `chart_alerts[]`. — source: https://betterstack.com/docs/logs/dashboards/json/
- **Dashboards: SQL contract and macros** (verified): Time-series SQL must return `time` (bucketed via `{{time}}`), `value` (numeric), optional `series` (string). Macros: `{{source}}` (selected source table), `{{time}}` (bucket expression for SELECT/GROUP BY), `{{start_time}}`/`{{end_time}}` (WHERE bounds), `{{interval_seconds}}` (bucket length), `{{sampling}}`. Verbatim dashboard chart SQL: `SELECT {{time}} AS time, label('status') AS series, countMerge(events_count) AS value FROM {{source}} WHERE {{time}} BETWEEN {{start_time}} AND {{end_time}} GROUP BY time, series ORDER BY time`. Prometheus counters expose `avgMerge(rate_avg)` per-second, multiply by `{{interval_seconds}}` for per-bucket counts. — source: https://betterstack.com/docs/logs/dashboards/sql-queries/
- **Dashboards: variables** (verified): Custom variables are `{{variable_name}}` (required; query fails if empty) or wrapped `[[ ... {{variable_name}} ... ]]` (optional block removed when empty; SQL only). Types: String, Number, Date, DateTime, Boolean, Source, SQL expression, Static list, Dynamic list (SQL expression such as `label('environment')`), Query per value; multi-select for lists; defaults in the right sidebar. Verbatim example: `SELECT {{time}} AS time, countMerge(rows) as count FROM {{source}} WHERE time BETWEEN {{start_time}} AND {{end_time}} AND request_user_agent ILIKE '%' || {{user_agent}} || '%' [[ AND level = {{log_level}} ]]`. — source: https://betterstack.com/docs/logs/dashboards/variables/
- **Alerts: defined on chart queries** (verified): Alerts are attached to a dashboard chart (Live tail query or SQL query) via the Alerts panel. Types: Threshold, Percentage change ('relative'), Anomaly detection. Parameters: run frequency, confirmation period (default 1 min failing before incident), recovery period (default 1 min healthy before resolve), missing-data handling (treat as zero / previous value / trigger / skip). Dashboard JSON verbatim: `{"name": "Spike in errors", "alert_type": "relative", "operator": "increases_by", "value": 50.0, "query_period": 3600, "recovery_period": 7200, "escalation_target": "current_team", "aggregation_interval": 300, "check_period": 600}`. Firing creates an Uptime incident routed by escalation policy (email, call, SMS, push) with templated cause using `{{alert_name}}`, `{{current_value}}` and query columns. — source: https://betterstack.com/docs/logs/dashboards/alerts/
- **Where Better Stack is slower/harder than Axiom** (likely): (a) Two-schema burden: searching raw logs needs `JSONExtract(raw, ..., 'Nullable(T)')` with explicit types; charting the same field quickly needs a separately configured logs-to-metrics extraction whose results are read with a different vocabulary (`label()`, `countMerge`, `avgMerge`, `sum(logs_count)`), and the Feb '26 migration forced users to rewrite dashboard SQL. (b) Docs state raw wide-event queries from object storage are 'much slower at scale'. (c) Hot vs cold is user-visible: `remote(t.._logs)` vs `s3Cluster(primary, t.._s3)` must be UNION ALL'ed by hand and `sampling=` chosen for long ranges; concurrency capped at 4 log queries. (d) Live tail filter language has no wildcards and no aggregation; aggregations require switching to SQL/PQL in the dashboards product. (e) Log-filter charts are limited to the last 10 minutes. (f) The marketing comparison itself concedes 'APL offers capabilities that SQL does not. Pipeline-style transformations, complex temporal aggregations, and streaming queries compose naturally in APL in a way that requires verbose subqueries in SQL'. Better Stack's counter-claim is '100% of ingested logs are immediately searchable with no indexing decisions and no tiering', which is true for search but not for fast dashboards. — source: https://betterstack.com/community/comparisons/better-stack-vs-axiom/

## Design implications

- Ingest contract to copy: `POST /api/:project_id/logs` (or a per-source token host-less path) accepting `application/json` (object or array), `application/x-ndjson`, and gzip bodies; treat a top-level `dt` as the event time with the same permissive parsing (UNIX s/ms/ns by magnitude, RFC 3339), keep an unparseable `dt` as a string, and fall back to receipt time. Reuse the Fiber ingest.Service -> pebbleChan -> Pebble raw-JSON-blob path unchanged: Pebble already plays the role of Better Stack's `raw` column keyed by UUIDv7.
- Auth by a Source token rather than the Sentry public key: add a `log_sources` table in Rails (name, token, project_id, source_group_id, logs_retention days, ingesting_paused, live_tail_pattern) and mirror Better Stack's field names so the Rails admin surface is a straightforward CRUD; the Go side reads it the same way auth/project.go reads project keys from SQLite.
- Shipper compatibility falls out for free if the endpoint speaks generic JSON/NDJSON with a Bearer token: Vector `http` sink with `.dt = del(.timestamp)`, Fluent Bit `http` output with `format json_lines` + `json_date_key dt` (the SolidTrace docs can prescribe JSON rather than Better Stack's msgpack `/fluentbit`), and OTLP/HTTP `/v1/logs` can be a thin translator to the same envelope. Skip msgpack ingest in v1.
- DuckDB schema: emulate the 'dt + raw' model with a `logs_hot(uuid, source_id, dt TIMESTAMP, level VARCHAR, message VARCHAR, raw JSON)` table and let users query arbitrary fields with DuckDB's `raw->>'$.context.request.status'` / `json_extract_string` plus `json_extract` typed variants. This is the exact analogue of `JSONExtract(raw, ...)` and needs no config. Consider DuckDB's `json_structure`/`json_group_structure` on a sample to auto-discover field names for the query builder, which Better Stack does not offer in SQL.
- Avoid Better Stack's biggest friction, the separate metrics schema: instead of a per-source 'Extract metrics' step producing a `label()`/`countMerge` table, materialise hot columns lazily in DuckDB (`ALTER TABLE logs_hot ADD COLUMN x AS (raw->>'$.x')` style generated columns, or a Rails-managed list of 'promoted fields' that the Go DuckDBIngester extracts at flush time into typed columns) so the same field name works in both search and charts. The Parquet archive job can write promoted fields as real Parquet columns and `union_by_name=true` already tolerates schema drift across partitions.
- Hot/cold split should be invisible: keep the existing `events`-style view (`logs_hot UNION ALL read_parquet(... hive_partitioning=true, union_by_name=true)`) so users never write the `remote()` + `s3Cluster()` UNION that Better Stack requires; expose an optional `sampling` knob only for long ranges (DuckDB `USING SAMPLE` on the Parquet scan) rather than making it part of the table name.
- Query language: implement the Live tail subset first because it is small and well specified — fulltext bare terms and quoted strings, `key:value` contains, `=`, `!=`, `!:`, `=~ /re/i`, `!~`, `>`, `>=`, `<`, `<=`, implicit AND, explicit `AND`/`OR`, dotted paths with `\.` escape — and compile it to DuckDB SQL over `raw`. Then layer a PQL/KQL-like pipeline (`where | summarize ... by bin(dt, 1m) | project | sort | take`) that also compiles to SQL; Better Stack's operator list (`where, summarize, extend, project, sort, take, top, count, join`) is a good minimum. Add `*` wildcards, which Better Stack explicitly lacks.
- Dashboards: store charts as JSON in Rails (Better Stack's `chart_type`, `x,y,w,h` 12-col grid, `settings.unit`, `chart_queries[{query_type, query}]`, `chart_alerts[]`) and have the Go query API accept macros `{{source}}`, `{{time}}`, `{{start_time}}`, `{{end_time}}`, `{{interval_seconds}}` plus user variables with `[[ optional ]]` blocks; enforce the `time`/`value`/`series` result contract so the shadcn/Recharts renderer is generic across line/bar/number/table/heatmap.
- Alerts: follow the chart-attached model — a Solid Queue job evaluates a chart query on `check_period`, over `query_period`, with `aggregation_interval`, threshold/relative operators, confirmation and recovery periods, and missing-data policy — since SolidTrace already has Rails jobs and the console_messages outbox for Go round-trips.
- Query API: expose a read-only `POST /api/:project_id/logs/query` that takes either the filter language or raw DuckDB SQL restricted to the project's view, returning `JSONEachRow`-style NDJSON, and add the auth that the current read API lacks; set a concurrency cap per project like Better Stack's 4 concurrent log queries to protect the single DuckDB instance.
- Retention is per source in days (`logs_retention`) — implement as a Rails-owned setting consumed by the existing daily archive job (drop Parquet partitions older than N days per source, and skip archive when `ingesting_paused`).

## Open questions

- Whether logs-to-metrics extraction in Better Stack is applied retroactively to already-stored raw events or only from definition time forward (docs do not say) — matters for deciding whether SolidTrace's promoted fields need a backfill job over Parquet.
- Exact behaviour of Better Stack's fulltext index (is `:` contains a tokenised inverted index or a substring scan over `raw`?) — could not be verified from docs; affects whether SolidTrace needs DuckDB FTS extension or plain ILIKE on `raw`.
- How Better Stack exposes hot-table vs S3 retention boundaries (how many days remain in `remote(..._logs)` before moving to `s3Cluster`) — not documented on the pages read.
- The Alerts API request body (page /docs/logs/api/alerts/create/ returned 404); only the dashboard-JSON `chart_alerts` shape was verified.
- Whether the HTTP ingest endpoint accepts `text/plain` bodies at all (the docs list only json, x-ndjson, msgpack); the collector/syslog paths were not investigated.
