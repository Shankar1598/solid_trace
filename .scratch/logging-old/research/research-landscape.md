# Prior research: landscape

> Extracted from workflow run `wf_25055e4a-726` (solidtrace-logs-discovery, 2026-09-13, Fable subagents). Reference only: claims were not re-verified and design implications were never decided.


## Summary

Across Parseable, OpenObserve, Quickwit, SigNoz, Loki, VictoriaLogs, Logchef, HyperDX/ClickStack and the DuckDB-based tools (logdk, Tailpipe), the same handful of decisions recur. On disk, every Parquet/columnar system partitions by tenant/stream then by UTC day (VictoriaLogs YYYYMMDD partitions, HyperDX PARTITION BY toDate, Tailpipe tp_table/tp_partition/tp_index/year/month, Parseable stream/date) and separates a hot in-memory or WAL tier that is queryable immediately from immutable, periodically compacted files; DuckDB's own guidance is 100 MB-10 GB per Parquet file and 100K-1M rows per row group, and Tailpipe publicly abandoned raw hive-partitioned Parquet for DuckLake after a time-range query had to open 1,463 files. For schemaless fields, nobody stores raw JSON as the query surface: OpenObserve/Parseable flatten nested JSON to underscore-joined columns with schema inference (with real conflicts around underscores and type changes -> Parseable renames to body_timestamp_utf8), SigNoz/HyperDX keep typed Map columns (attributes_string/number/bool) and promote hot keys to MATERIALIZED columns (attribute_string_<key> + _exists), VictoriaLogs and Quickwit/tantivy store per-field columns or (path,type,value) terms dynamically, and Loki keeps a tiny indexed label set plus unindexed structured metadata. On indexing, the modern consensus for single-node scale is brute-force columnar scan plus cheap per-block skipping (min/max zonemaps, bloom filters on tokens or exact values) instead of a full inverted index: VictoriaLogs uses one bloom per (block,column) over tokens, HyperDX/ClickStack a tokenbf_v1(32768,3,0) skip index on lower(Body), DuckDB >=1.2 reads/writes Parquet bloom filters automatically for dictionary-encoded columns; only Quickwit (tantivy) and OpenObserve (opt-in tantivy per field, ~25% storage) build inverted indexes. Query UX converges on a three-tier model: a simple filter language (LogchefQL key=value / ~ / and-or, HyperDX Lucene-ish level:Error, SigNoz key = 'v' AND ..., VictoriaLogs LogsQL word filters + pipes) compiled to SQL, an escape hatch to raw SQL/WHERE, and a field sidebar that is just a top-N-values facet query scoped to the current filter and time range (VictoriaLogs exposes it literally as /select/logsql/facets and /field_values, Loki as /detected_fields). Dashboards are uniformly panel = query + chart type + layout position with dashboard-level time range and variables; alerts are query + aggregation + threshold operator + evaluation window (rolling/cumulative) + frequency + silence/cooldown + match type (at least once / all the times / on average / in total / last) + destinations. Live tail is overwhelmingly server-side or client-side polling (SigNoz SSE from a 5 s ticker using id > $lastId, HyperDX 1 s setInterval advancing a 15-min window, VictoriaLogs HTTP-streamed tail that checks every 1 s with a 5 s delivery delay, OpenObserve/Parseable auto-refresh); only Loki uses a websocket. For SolidTrace (Go + DuckDB + Parquet, 1-20k lines/s) the copyable pattern is: hot DuckDB table + daily Parquet partitions with row-group/file-size discipline and a manifest, typed MAP/JSON columns with promotion of hot keys to real columns, brute-force scans accelerated by Parquet bloom filters and zonemaps rather than DuckDB FTS (which cannot update incrementally), a small KQL-like filter grammar compiled to DuckDB SQL, a facet endpoint driving the sidebar, and polling/SSE live tail keyed on UUIDv7.

## Findings

- **Parseable: ingest/storage layout** (likely): Ingestion nodes convert payloads to Arrow files staged on local disk; 'Each ingestion batch received via API is concurrently appended to the same file within a one-minute window'; a background job converts staged Arrow to Parquet and uploads to object storage, writing 'parquet, manifests, and snapshots'. Query engine is Apache DataFusion with PostgreSQL-compatible SQL; the planner consults a manifest (which columns/time ranges live in which Parquet files) instead of listing storage. Docs storage page shows layout bucket/streams/<stream>/year=2024/month=01/day=15/data.parquet. Index is 'on demand' ('Parseable allows indexing specific chunks of data, on demand'); default is columnar Parquet scan with in-memory/NVMe 'smart cache' on query nodes. — source: https://www.parseable.com/docs/architecture
- **Parseable: schemaless fields** (verified): 'Nested JSON objects are automatically flattened' with underscore joining (foo.bar -> foo_bar, queried as 'select foo_bar from <dataset>'). Parseable adds p_timestamp (event-received time). When a field's type differs between events 'the field is automatically renamed with a type suffix (e.g., body_timestamp_utf8, span_kind_int64)'. Fields starting with '@' are replaced with '_'; key collisions reject the event. Max payload 10 MiB; X-P-Stream header names the dataset and auto-creates it. Custom partitioning: a single column per dataset (e.g. log_level=ERR dirs), recommended only for 'at least few TBs'. — source: https://www.parseable.com/docs/ingestion
- **Parseable: query UX, dashboards, alerts** (likely): Logs UI: left field sidebar grouped (Core, Error, Service, Span, Host, Container, HTTP, Process, Telemetry) with 'Search field names' and per-value counts; 'Add filter' produces filter pills above a 'Logs over time' histogram split by level; 'Saved views' persist dataset, filters, fields and time range; live view is auto-refresh (polling). Dashboards: 'tiles' each = SQL query + one of 8 chart types (timeseries, line, bar, area, pie, donut, query value, gauge), draggable with 1/4..full widths, dashboard-level fixed time range. Alerts: dataset + monitored field + optional filter (status = 500) + optional groupBy + severity (Low/Medium/High/Critical) + targets (Webhook, Slack, Alertmanager); types Standard Threshold, Anomaly Detection, Forecasting. — source: https://www.parseable.com/docs/user-guide/logs
- **Parseable: Parquet limits (traps)** (verified): Parseable's own write-up lists Parquet's limits for logs: 'Thousands of tiny files increase object-store requests, metadata work and query-planning overhead'; 'Parquet files are immutable after they are written... It must buffer records, write useful row groups, close files and compact undersized files'; 'Renaming a field, changing its type or interpreting nested structures can require explicit migration or a table/catalog layer'; 'Exact lookup by an unsorted random identifier may still scan significant data unless the system supplies suitable sorting, Bloom filters, secondary indexes or cached metadata'; 'Parquet statistics ... are not a replacement for a full-text index'; 'Parquet does not provide ACID transactions, snapshots, deletion tracking or table-level retention'. — source: https://www.parseable.com/blog/observability-apache-parquet
- **OpenObserve: storage layout** (verified): One Memtable per organization/stream_type; WAL written 'by timestamp in hourly buckets' under data/wal/logs, then Parquet under data/wal/files before upload to object storage every ZO_FILE_PUSH_INTERVAL=10 seconds. Ingester serves three layers (Memtable, Immutable, un-uploaded Parquet in wal); Querier is stateless with a leader partitioning file lists to workers; Compactor 'merges small files into big files' and enforces retention. Parquet is zstd-compressed. Queries are split into time partitions executed sequentially with a first 'mini-partition' of ZO_MINI_SEARCH_PARTITION_DURATION_SECS=60 to return early results; results can stream over one HTTP/2 connection ('Streaming Search') or websocket (ZO_WEBSOCKET_ENABLED, default off). — source: https://openobserve.ai/docs/architecture/
- **OpenObserve: schema and indexes per field** (verified): Schema is inferred at ingest; nested JSON is flattened with '_' (actor.ip -> actor_ip) to depth ZO_INGEST_FLATTEN_LEVEL (default 3; 0 = unlimited), overridable per stream ('Flatten Level'); beyond the limit the field holds unparsed JSON as a string. GitHub issue #7832 documents that underscore flattening 'loses information and may lead to conflicts'. Stream settings expose per-field index types: Full Text Search (utf8 text; '~25% storage overhead'), Secondary Index (repeated values like status codes), Bloom Filter (high-cardinality trace_id/request_id), Key-Value Partition (low-cardinality env/service), Prefix Partition, Hash Partition; 'Once applied, it cannot be changed'. Also: user-defined schema, 'Store Original Data', 'Enable Distinct Values' (tracks unique values to speed filters), max query range (ZO_DEFAULT_MAX_QUERY_RANGE_DAYS), retention default 3650 days. Field types: utf8, int64, uint64, float64, boolean. — source: https://openobserve.ai/docs/user-guide/data-processing/streams/data-type-and-index-type-in-streams/
- **OpenObserve: inverted index (tantivy) usage** (verified): Tantivy inverted index is opt-in per field (ZO_ENABLE_INVERTED_INDEX default true enables the feature). Full-text index tokenizes fields like body/message; secondary index treats the whole value as one token. The index is used only by specific operators: match_all('error') for FTS fields, '=' or 'IN (...)' for secondary-index fields; str_match() for other string matching. Limitation: match_all() unsupported outside a subquery when the subquery contains aggregation/grouping. Result cache: ZO_INVERTED_INDEX_RESULT_CACHE_ENABLED (default false), ZO_INVERTED_INDEX_RESULT_CACHE_MAX_ENTRIES (10000). — source: https://openobserve.ai/docs/user-guide/performance/tantivy-index/
- **OpenObserve: query UX, dashboards, alerts** (verified): Logs page has a 'SQL mode' toggle: non-SQL mode = field-based filters and functions (match_all etc.) without full SQL; SQL mode = full SQL. Sidebar field list with top values, histogram toggle, 'Quick Mode' (limit fields), 'Search Around' (context), saved views, VRL functions, auto-refresh interval (polling). Dashboards: folders -> dashboards -> tabs -> panels; panel = one visualization (20 chart types incl. table with pivot) over a query (builder or custom SQL/PromQL); variables; JSON import/export. Alerts: Scheduled (period/look-back window, frequency in minutes or cron) vs Real-time; condition via builder sentence ('Alert if total events >= 3', 'avg of cpu_usage is >= 80'), custom SQL, or PromQL; silence/cooldown; 'Compare with Past' multi-window; destinations email/webhook/actions with templates. — source: https://openobserve.ai/docs/user-guide/analytics/alerts/
- **Quickwit: index layout and split lifecycle** (verified): Index = splits (UUID-named bundles of tantivy segment + hotcache) on object storage or local disk, tracked by a metastore (file/S3 for single node, PostgreSQL for clusters). Each split records min/max of timestamp_field and tag_fields values so queries prune splits by time range and tags (tags only if field cardinality < 1,000). Indexer emits a split when split_num_docs_target (default 10000000) or commit_timeout_secs (default 60) is hit. Default merge policy stable_log: merge_factor 10, max_merge_factor 12, min_level_num_docs 100000, maturation_period 48h; it 'merges splits with a similar size, and with a close time span' to keep time-pruning power. docstore_compression_level 8 (zstd), docstore_blocksize 1000000. Retention: period + schedule (default hourly), drop when now() - split.time_range.end >= period. Hotcache lets a searcher open a split in <60 ms on high-latency storage. — source: https://quickwit.io/docs/configuration/index-config
- **Quickwit/tantivy: dynamic JSON fields** (verified): doc_mapping.mode: dynamic (default; unmapped fields go through dynamic_mapping with defaults indexed:true, stored:true, tokenizer:raw, record:basic, expand_dots:true, fast:true), lenient (drop unmapped), strict (error). Explicit json field type defaults fast:false. tantivy indexes JSON by emitting terms that are triplets (json_path, value_type, value); path segments joined by \x01 and terminated by \x00; numbers tried as u64 then i64 then f64 per document ('no effort to try to sniff a consistent field type at the scale of a segment'); strings tried as RFC3339 dates then text. Arrays are a bag of terms (cross-element matches are possible). 'Json field do not support range queries'. Query language: field:value, wildcards, phrase with ~slop, field:IN [a b], ranges [a TO b], exists field:*, nested product.attributes.color:red, escaped dots k8s\.component\.name. — source: https://github.com/quickwit-oss/tantivy/blob/main/doc/src/json.md
- **SigNoz: logs storage schema (ClickHouse)** (verified): signoz_logs.logs_v2 columns include timestamp UInt64, observed_timestamp UInt64, id String (ksuid for pagination), trace_id, span_id, trace_flags UInt32, severity_text LowCardinality(String), severity_number UInt8, body String, attributes_string Map, attributes_number Map, attributes_bool Map, resources_string (deprecated) / resource JSON, scope_name, scope_version, scope_string Map, ts_bucket_start (30-minute buckets), plus a distributed_logs_v2_resource side table (labels String, fingerprint String, seen_at_ts_bucket_start Int64). Converting an attribute to a 'selected field' creates materialized columns: `attribute_string_method` String MATERIALIZED attributes_string['method'] and `attribute_string_method_exists` Bool MATERIALIZED if(mapContains(...)); naming attribute_<dataType>_<key> with dots -> $$ (attribute_string_response$$time). Docs recommend always filtering on resource attributes for performance. — source: https://signoz.io/docs/userguide/logs_clickhouse_queries/
- **SigNoz: query builder and search syntax** (verified): Query Builder v5 filter bar accepts typed expressions, e.g. `service.name = 'frontend' AND http.status_code >= 400`; operators include =, !=, <, >, IN, NOT_IN, LIKE (case-sensitive), ILIKE, CONTAINS, EXISTS, parentheses; multiple filters are joined with AND by default; string values need single quotes; bare quoted phrase ('database connection timeout') is a full-text body search (logs only). - **Grafana Loki: labels vs content, structured metadata** (verified): 'In Loki, the content of each log line is not indexed. Instead, log entries are grouped into streams which are indexed with labels.' Guidance: 'Prefer fewer labels, which have bounded values', '10 - 15 labels at a maximum', never label level/message/exception/timestamp/ip; 'High cardinality causes Loki to build a huge index and to flush thousands of tiny chunks'. Structured metadata = key/values stored in chunks (not the index) for high-cardinality data (pod name, trace id), queried as label filters `{job="example"} | pod="myservice-abc1234-56789"`; requires schema v13 + tsdb; limits 64KB per line and 128 entries per line. Bloom filters index structured metadata only, 'by design not supported in single binary deployment', intended for >75TB/month. — source: https://grafana.com/docs/loki/latest/get-started/labels/structured-metadata/
- **Grafana Loki: chunk sizing and LogQL** (verified): Best practices: chunk_target_size 1.5MB compressed (1572864), chunk_block_size 262144 uncompressed, chunk_idle_period 30m, max_chunk_age 2h, chunk_encoding snappy/lz4 over gzip for throughput; per-stream logs must be in increasing time order; max_label_names_per_series 15. LogQL = stream selector {label="x", l2=~"re"} then pipeline: line filters |= != |~ !~ (put first for performance), parsers | json | logfmt | pattern | regexp, label filters | duration > 10s and status >= 500, | line_format, | label_format, | drop/keep. API: GET /loki/api/v1/tail is a WebSocket (query, delay_for <= 5s, limit default 100, start); /labels, /label/<name>/values, /series, /detected_fields (inferred types + cardinality), /detected_labels, /patterns, /index/volume. — source: https://grafana.com/docs/loki/latest/configure/bp-configure/
- **VictoriaLogs: data model and stream fields** (verified): Schemaless single-level JSON; special fields _msg (required; fallback -defaultMsgValue; rename via _msg_field), _time (RFC3339 or unix; ingestion time if missing; _time_field), _stream / _stream_id from fields chosen via _stream_fields query arg at ingest ('Log entries received from a single application instance form a log stream'). Nested JSON flattened with dot notation; arrays/numbers/bools converted to strings. Rule: 'Never add non-constant fields to streams if these fields may change with every log entry' (ip, user_id, trace_id); watch vl_streams_created_total. All other fields are automatically indexed; trace_id:="value" is faster than searching _msg. Limits: up to 2000 fields per entry, field names <= 128 bytes, record optimal 10KB, max 2MB. — source: https://docs.victoriametrics.com/victorialogs/keyconcepts/
- **VictoriaLogs: on-disk columnar layout + bloom filters instead of inverted index** (verified): Layout <-storageDataPath>/partitions/YYYYMMDD/{indexdb,datadb}/<partId>/ with parts.json listing active parts. Parts go in-memory -> small (flushed every -inmemoryDataFlushInterval, default 5s) -> big via merges. Blocks are per-stream and capped 'at roughly 2 MiB of uncompressed data'. Part files: metadata.json, index.bin, metaindex.bin, timestamps.bin, values.bin0..N, bloom.bin0..N, message_values.bin, message_bloom.bin, column_names.bin (field name -> numeric column id), column_idxs.bin, columns_header.bin, columns_header_index.bin; up to 128 shards (fields beyond 128 share a shard). 'There is one bloom blob per (block, column)' over tokens ('a run of letters, digits, or underscores'), ~2 bytes per unique token. Constant columns stored once. Retention default 7d (-retentionPeriod), plus -retention.maxDiskSpaceUsageBytes / -retention.maxDiskUsagePercent. — source: https://victoriametrics.com/blog/victorialogs-internals-columnar-storage-on-disk/
- **VictoriaLogs: LogsQL and facet/tail endpoints** (verified): LogsQL: bare word `error` searches _msg; phrase "ssh: login fail"; prefix err*; field:value; exact :=; regex ~"..."; ranges response_size:>10KiB; _time:5m / _time:[2023-02-01Z, 2023-03-01Z); stream filter {app="nginx"}; AND/OR/NOT with implicit AND; pipes | stats count() ..., | fields, | sort by (_time) desc, | limit 10, | extract "user=<user>", | unpack_json. HTTP: /select/logsql/tail?query= streams JSON lines, checks every 1s (refresh_interval), delivers with 5s delay (offset), start_offset for backfill; tail queries cannot use stats/uniq/top/sort/limit/offset pipes. /select/logsql/hits (per-bucket counts, field= grouping, fields_limit), /field_names, /field_values?field=&limit=, /stream_field_names, /streams, /facets (max_values_per_field, max_value_len, keep_const_fields=1), /stats_query. — source: https://docs.victoriametrics.com/victorialogs/querying/
- **Logchef: stack and LogchefQL** (verified): Logchef (mr-karan) is Go + Vue, single binary, AGPLv3; it is a query/control plane over existing ClickHouse tables or VictoriaLogs ('without moving or reshaping your data'); metadata in SQLite by default, Postgres optional. LogchefQL: `status=200`, `level!="debug"`, `message~"timeout"` (case-insensitive contains via positionCaseInsensitive), `path!~"internal"`, numeric >,<,>=,<=, `(service="auth" or service="users") and level="error"`, nested `log_attributes.user_id="12345"` -> `log_attributes['user_id']` (Map) or JSONExtractString, quoted names `log_attributes."user.name"`, pipe `level="error" | timestamp level body` selects columns. Compiled SQL automatically adds a time-range filter, ORDER BY timestamp DESC, LIMIT 100. Modes: LogchefQL vs native SQL/LogsQL; AI NL->query. Live tail 'stream matching rows as they arrive' — native streaming for VictoriaLogs, polling-based on ClickHouse. Field Values Sidebar; histogram with drag-to-zoom; scheduled alerts with email/webhook. — source: https://logchef.app/guide/search-syntax/
- **HyperDX / ClickStack: schema, search, live tail** (verified): otel_logs: Timestamp DateTime64(9) CODEC(Delta(8), ZSTD(1)), SeverityText LowCardinality(String), ServiceName LowCardinality(String), Body String, ResourceAttributes/ScopeAttributes/LogAttributes Map(LowCardinality(String), String) CODEC(ZSTD(1)), eight __hdx_materialized_* columns from ResourceAttributes, attribute-key/item skip indexes, `INDEX idx_lower_body lower(Body) TYPE tokenbf_v1(32768, 3, 0)`, PARTITION BY toDate(Timestamp), ORDER BY (toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp), TTL. Search is Lucene-like: `*Error*`, `Error NOT Exception` / `Error -Exception`, `Error OR Exception`, quoted phrases, `level:Error, service:app`, `Duration:>1000`, `duration:*`; optional toggle to raw SQL WHERE; natural-language time ('1 hour ago'). Live tail is client polling: `LIVE_TAIL_REFRESH_INTERVAL_MS = 1000`, setInterval advancing a 15-minute window ([sub(end,{minutes:15}), end]); react-query keeps maxPages 5 and gcTime 30s in live mode. — source: https://clickhouse.com/docs/use-cases/observability/clickstack/ingesting-data/schemas
- **DuckDB-based log tools: logdk and Tailpipe** (verified): logdk (Zig + DuckDB): 'dataset' maps to one DuckDB table; schema 'auto-adjusts' (adding a column, making nullable, changing type); POST /api/1/datasets/NAME/events accepts object or array; async flush 'every 10000 events or every 5 seconds, per-dataset'; UI compiled into binary; no TLS. Tailpipe (Go + DuckDB, open source SIEM): plugins write Parquet into a prescribed hive layout tp_table=<t>/tp_partition=<p>/tp_index=<i>/year=/month= (earlier tp_date=), files named ducklake-<uuid>.parquet, DuckDB views created by discovering partitions; docs warn 'defining a tp_index ... may decrease [performance] as it can result in many small parquet files'. Tailpipe migrated to DuckLake (metadata DB tracking schema/partitions/statistics) because 'a time-range query that previously read 1,463 files now reads just 2 files: a 700x reduction' on 20M CloudTrail rows. — source: https://tailpipe.io/blog/tailpipe-meets-ducklake
- **DuckDB: Parquet sizing, hive partitioning, bloom filters, FTS** (verified): Performance guide: Parquet row groups of 100K-1M rows (below 5,000 rows 'more than 5-10x larger' runtimes), files 'between 100 MB and 10 GB', at least as many row groups as CPU threads, prefer snappy/lz4/zstd over gzip; Parquet has zonemaps for projection/filter pushdown but lacks DuckDB's HLL stats. Hive: read_parquet('orders/*/*/*.parquet', hive_partitioning = true) pushes partition-key filters down and skips files; hive_types / hive_types_autocast; COPY ... (FORMAT parquet, PARTITION_BY (year, month)) cannot use expressions. Parquet bloom filters: DuckDB >= 1.2.0 writes them automatically for dictionary-encoded integer/float/VARCHAR/BLOB columns (not nested types) with ROW_GROUP_SIZE default 122,880, DICTIONARY_SIZE_LIMIT 10% of row group, BLOOM_FILTER_FALSE_POSITIVE_RATIO 0.01, and uses them for constant-comparison predicates (WHERE a = 42), ~50x faster for absent values, ~47 bytes per row group. FTS extension: PRAGMA create_fts_index / match_bm25 on tables; 'The FTS index will not update automatically when the input table changes' (must be recreated). — source: https://duckdb.org/2025/03/07/parquet-bloom-filters-in-duckdb.html
- **DuckDB MAP semantics** (verified): MAP requires a single key type and single value type per column, no duplicate keys; bracket access map['key'] returns NULL when missing while map_extract/element_at return an empty list; MAPs are comparable/orderable. Parquet MAP storage and performance notes are not covered on the page. — source: https://duckdb.org/docs/current/sql/data_types/map.html

## Design implications

- Storage layout (copy VictoriaLogs/HyperDX/Tailpipe): keep hot data in DuckDB (logs_hot) and archive to Parquet partitioned as project_id=<id>/event_date=YYYY-MM-DD/ exactly like events_hot today, but enforce DuckDB's sizing rules when COPYing: target 100K-1M rows per row group (ROW_GROUP_SIZE) and >=100 MB files; at 1-20k lines/s a day is 86M-1.7B rows, so one COPY per day produces files that are too big for a single-threaded write and too slow to materialize — write hourly Parquet files inside the day partition (e.g. event_date=.../hour=HH/part-<uuidv7>.parquet) and add a compaction step that merges undersized files, mirroring Quickwit's stable_log merge (merge similar-size, close-time splits) and OpenObserve's compactor.
- Do not rely on glob discovery (read_parquet('*/*/*.parquet')) at scale: Tailpipe hit 1,463 file opens per time-range query and moved to DuckLake; Parseable consults a manifest. Keep a Parquet manifest table in DuckDB/SQLite (file path, project_id, min/max timestamp, row count, min/max of promoted columns) and build the UNION ALL over only the files whose time range intersects the query, i.e. generate read_parquet([list of files]) per query in Go rather than a static view.
- Schemaless fields: keep the Map approach already used in events_hot (tags MAP(VARCHAR,VARCHAR)) but type-split like SigNoz/OTel (attributes_string, attributes_number, attributes_bool, resources_string) so numeric comparisons and percentiles work without casts; add a 'promoted fields' table (Rails admin) and materialize hot keys as real columns in logs_hot/Parquet (attribute_string_<key> plus an _exists flag), regenerating the Parquet writer's SELECT accordingly. Avoid underscore flattening as the primary representation (OpenObserve issue #7832: lossy, collides) — flatten only for display/autocomplete with dots preserved.
- Full-text: do not use DuckDB's FTS extension (index cannot update incrementally, tables only). Follow VictoriaLogs/HyperDX: brute-force columnar scans over the message column plus cheap skipping. DuckDB >= 1.2 writes Parquet bloom filters automatically for dictionary-encoded VARCHAR columns and uses them for equality predicates, so exact-match filters on trace_id/request_id/user_id in promoted columns get skip-scans for free; keep timestamp sorted within files so zonemaps prune row groups. Optionally add a per-file token bloom (tokenbf-style, per row group) stored in the manifest for substring/word search if scan latency on multi-day ranges proves too high.
- Stream/tenant modelling: adopt Loki/VictoriaLogs 'stream fields' — a small bounded set (project_id, environment, service, host, level) becomes real, low-cardinality columns that order/partition data and drive the sidebar; everything else lives in the maps. Reject high-cardinality keys from the stream set the way VictoriaLogs warns (ip, user_id, trace_id).
- Query language: implement a small KQL/LogsQL-style filter grammar in Go that compiles to DuckDB SQL (LogchefQL is the closest single-node precedent): bare words search the message column, key=value / != / ~ (case-insensitive contains) / !~ / < > <= >= / in (...) / exists, and/or/not with parentheses, dotted keys resolving to map lookups (attributes_string['http.status']) or promoted columns, `| fields`, `| stats count() by service`, `| sort`, `| limit`; auto-inject the time range, ORDER BY timestamp DESC, LIMIT 100 like Logchef, and expose a raw-SQL escape hatch exactly like every tool surveyed.
- Field sidebar: implement it as a facet endpoint on the Go side (VictoriaLogs /select/logsql/facets and /field_values, Loki /detected_fields): given the current filter + time range, return field names with counts and top-N values, computed with a single DuckDB query over map_keys/map_entries (UNNEST) on a sampled or limited row set (VictoriaLogs caps max_values_per_field and max_value_len); cache per (project, filter, time range) in Rails.
- Dashboards and monitors in Rails/SQLite (Parseable/OpenObserve/SigNoz model): Dashboard {title, time_range, variables, tabs} -> Panel {query (filter language or SQL), viz_type (timeseries/bar/pie/table/stat), position, options}; Monitor {query + aggregation, comparator (above/below/eq/neq), threshold, window (rolling|cumulative, duration), match_type (at_least_once|all_times|on_average|in_total|last), frequency (Solid Queue recurring), silence_period, no_data_policy, min_data_points, labels, notification_channels}; evaluation runs in a Solid Queue job that calls the Go query API and persists state transitions, reusing the existing notification system.
- Live tail: match SigNoz/HyperDX/VictoriaLogs rather than websockets. Go endpoint GET /api/:project_id/logs/tail?query=... streams SSE or NDJSON, ticks every 1-5 s, queries logs_hot only (never Parquet) with `uuid > $last_uuid` (UUIDv7 is time-ordered, so this is the 'id > $id' cursor SigNoz uses), applies a small delivery delay (VictoriaLogs uses 5 s) to tolerate the 1 s DuckDB flush, forbids aggregation pipes in tail mode, and the React UI keeps a bounded buffer (HyperDX keeps 5 pages / 30 s gc). Rails simply proxies or the browser connects directly once read-API auth exists.
- Ingest path: a schemaless POST /api/:project_id/logs (single object or array, like logdk and Parseable) that reuses the existing Pebble WAL -> DuckDB Appender pipeline; add Parseable's rules: reserved prefix normalization, RFC3339 timestamp detection with ingestion-time fallback, per-event type inference with per-key type recording (for autocomplete typing), a max payload (10 MiB) and max fields per event (VictoriaLogs uses 2000).

## Open questions

- Parseable's exact object-store path granularity (minute-level partitions and manifest/snapshot JSON format) was not reachable in docs fetched; only a stream/year=/month=/day= example and prose about manifests were verified.
- OpenObserve's on-disk placement of tantivy index files relative to Parquet files (per-file .ttv vs puffin sidecar) is not documented on the pages read.
- Whether DuckDB Parquet bloom filters are consulted when reading through a UNION ALL view with union_by_name=true and hive_partitioning=true (vs. direct read_parquet) should be benchmarked on duckdb-go v2.5.4 before relying on them.
- DuckDB MAP columns in Parquet: bloom filters are not written for nested types, so promoted scalar columns are the only bloom-accelerated path; measure whether map_extract on a 10-20k rows/s hot table is acceptable for sidebar facets or whether a periodic 'field stats' rollup table is required.
- Loki's detected_fields cardinality/type inference algorithm and Grafana's Logs Drilldown sidebar were not examined in source; the Loki facet endpoints were verified only at the API-shape level.
- No mature open-source DuckDB+Parquet log server with a full UI was found (logdk is early-stage Zig; Tailpipe is CLI/SIEM and moved to DuckLake), so SolidTrace would be breaking new ground on compaction and manifest management for DuckDB specifically; DuckLake as an alternative to a hand-rolled manifest should be evaluated for duckdb-go v2.5.4 compatibility.
