# Re-archiving a date overwrites that day's Parquet file

Status: resolved

**Source:** found while designing [ingest write path](../../ingest-write-path/spec.md) (2026-09-26), not a `review.md` item
**Category:** bug
**Area:** `event_store/storage/duckdb.go` (`ArchiveEventsForDate`), `event_store/pipeline/archive_consumer.go`

## Problem

`ArchiveEventsForDate` always writes `event_date=<date>/data.parquet`. If that date is archived a second time, `COPY ... TO` replaces the file, and the Events archived the first time are lost from every query. Raw payloads stay in Pebble.

A late Event doesn't trigger a second archive by itself. The Console's `EventStoreArchiveJob` sends `archive_events` for `Date.yesterday` only, once a day at 2am. So a late Event for an already-archived date stays in `events_hot` for good: still queryable, never archived. Examples of late Events:
- a client with a skewed clock,
- an SDK that sends a queued Event later.

Today a date is archived twice only if someone sends `archive_events` for it by hand, or the daily job fires twice.

After the [ingest write path](../../ingest-write-path/spec.md) change, many more Events land late. When Event processing catches up a backlog, it appends older Events to `events_hot` after their date may already be archived. Archiving those stranded rows means archiving a date again, which hits this bug.

## Decided

Settled in triage on 2026-09-30. The agent brief under Comments is the contract.

## Comments

### 2026-09-30 triage

> *This was generated by AI during triage.*

- **Reproduced.** A temporary test wrote 2 Events for a past date, archived that date, wrote a late Event for the same date, and archived it again. A query returned 3 Events before the second archive and 1 after it. The overwrite comes from the hard-coded path at `event_store/storage/duckdb.go:452`.
- **The trigger in the first draft was wrong.** Late Events aren't lost today. They're stranded in `events_hot`. The Problem section is now corrected.
- **Retries are safe today by accident.** If `COPY` succeeds and the commit fails (`review.md` §10), a retry overwrites the leftover file with the same rows. A file name per run removes this, so a fix needs its own way to handle a leftover file.
- **Constraint.** The ingest write-path spec (§ "The archive never runs inside a batch") has the archive and Event processing share a lock. A fix has to keep that.
- **Redundancy:** nothing appends to or merges an existing partition. There's no `.out-of-scope/` directory.
- **State:** stays `needs-triage` until grilling settles (1) whether the archive sweeps every date before today, and (2) how it writes a second file for a date and recovers from a failed run.

### 2026-09-30 agent brief

> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** An archive run must never overwrite an existing archive file, and it must also move Late Events for dates that are already archived.

**Current behavior:**
- `DuckDBWriter.ArchiveEventsForDate(date)` moves the rows in `events_hot` whose `CAST(timestamp AS DATE)` equals `date` into `<parquet root>/event_date=<date>/data.parquet`, then deletes those rows and rebuilds the `events` view.
- The file name is fixed. A second archive of the same date replaces the file, so every Event from the first archive disappears from queries. This is reproduced: archive a past date that has 2 Events, add 1 more Event for that date, archive it again. The query then returns 1 Event, not 3.
- Only the requested date is moved. The Console's daily job sends yesterday, so Events that arrive after their date was archived stay in `events_hot` forever.
- `COPY ... TO` writes the file outside the transaction. If the commit fails or the process dies after `COPY`, the file stays while its rows also stay in `events_hot`. Today a retry happens to overwrite that file. With unique file names it would not.

**Desired behavior:**
- **Cutoff.** The `date` in an `archive_events` message is a cutoff. A run moves every row in `events_hot` whose date is on or before the cutoff. The existing rule stays: a cutoff of today or later (UTC) fails the message. The Console doesn't change.
- **One file per date per run.** For each date among the rows it moves, a run writes one new file `event_date=<date>/data-<run id>.parquet`. The run id is the run's UTC start time, formatted so that file names sort by run. A run never overwrites or deletes a `.parquet` file. Existing `data.parquet` files are left as they are and are still read.
- **Order.** A run:
  1. writes every file under a staging name `<final name>.tmp`. The view reads only `*.parquet`, so it skips these files;
  2. deletes the moved rows from `events_hot` and commits, in one transaction;
  3. renames each `.tmp` file to its final name;
  4. rebuilds the `events` view.

  A run that finds no rows writes nothing.
- **Recovery.** At startup, before the archive consumer runs, and again at the start of every run, EventStore checks each `.tmp` file under the parquet root:
  - if the file's Events are still in `events_hot`, the commit didn't happen, so it deletes the file;
  - otherwise the commit happened, so it renames the file to its final name.

  A run's commit removes all of its rows or none, so checking one `uuid` from the file is enough. Runs never overlap, so every `.tmp` file found at those points belongs to a run that has ended. If a run fails before its commit, it tries to delete its own `.tmp` files, but correctness doesn't depend on that cleanup succeeding.
- After recovery or a run, the `events` view includes every `.parquet` file, and no Event appears twice.

**Key interfaces:**
- `DuckDBWriter.ArchiveEventsForDate(date time.Time) error`: becomes "archive up to and including `date`". Rename it if the new meaning needs a new name, and update `ArchiveConsumer`.
- `ArchivePayload.Date`: same field and format (`2006-01-02`). Its meaning changes to a cutoff.
- A recovery step on `DuckDBWriter`, called by the constructor, or before the archive consumer starts, and at the start of each run.
- `recreateEventsView`: its glob of `*/*.parquet` must keep skipping `.tmp` files.

**Acceptance criteria:**
- [ ] Archive date D (2 Events), add a Late Event for D, archive with cutoff D again. A query returns all 3 Events, and D's directory has 2 `.parquet` files.
- [ ] With Events on D-3 and D-1 in `events_hot`, one run with cutoff D-1 moves both dates into their own directories, and `events_hot` keeps only Events dated after D-1.
- [ ] A run with no rows up to the cutoff writes no file and makes no change.
- [ ] Recovery, commit not done: a `.tmp` file whose Events are still in `events_hot` is deleted. Queries return each of those Events once.
- [ ] Recovery, commit done: a `.tmp` file whose Events are no longer in `events_hot` is renamed to `.parquet`. Queries return its Events.
- [ ] Recovery runs at the start of a run as well as at startup. A `.tmp` file left by a failed run is deleted by the next run and can't come back later as a duplicate.
- [ ] Existing `TestArchiveEventsForDate` and the archive part of `integration_test.go` pass, updated for the new file names. `go test ./...` passes in `event_store`.

**Out of scope:**
- Merging small files in a date directory.
- Any retention rule that deletes old archive files.
- Console changes: `EventStoreArchiveJob` still sends yesterday.
- The shared lock between the archive and Event processing. That belongs to ingest write-path ticket 03. This fix ships first, and ticket 03 must keep the archive between batches.
- Changing the row schema or the `event_date=` directory layout.


### 2026-09-30 implementation

> *This was generated by AI during implementation.*

- `DuckDBWriter.ArchiveEventsForDate` is now `ArchiveEventsUpTo(cutoff)`, and `ArchiveConsumer` calls it. Each run writes `event_date=<date>/data-<run id>.parquet`. The run id is `20060102T150405.000000000Z` in UTC, which is fixed width, so names sort by run. Files are staged as `.tmp`, the delete commits, then the files are renamed and the view is rebuilt.
- `recoverStagedFiles` runs in `NewDuckDBWriter`, before the view is built and before the consumer starts, and again at the start of every run.
- Beyond the brief, from review:
  - A run with nothing to move still rebuilds the view, because recovery may have published a file.
  - The delete uses the same date predicate as the rows it copied, not `uuid IN (...)`. `events_hot` doesn't enforce unique uuids, so the uuid form could delete a later-dated copy that was never archived.
  - An unreadable `.tmp` file is logged as an error and left in place, not deleted. EventStore can't tell whether its run committed, and the view never reads `.tmp` files, so leaving it can't cause duplicates. An operator has to decide what to do with it.
- **Known edge, accepted:** recovery's one-uuid check assumes uuids are unique in `events_hot`. Suppose the same Event is written again in the window after a commit and before the rename, and then the process crashes. Recovery would delete that committed file. The re-sent copy stays in `events_hot`, but any other Events in the file are lost from queries. Their payloads remain in Pebble.
- Tests are in `event_store/storage/duckdb_test.go`: the re-archive, cutoff, empty-run and recovery cases.
