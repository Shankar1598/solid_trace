# Issues list recomputes counts from EventStore on every render

Status: resolved

**Source:** `review.md` §7
**Category:** enhancement (data model)
**Area:** `console/app/serializers/issue_serializer.rb`, `console/app/controllers/issues_controller.rb`, `console/db/`, `console/app/jobs/event_store_message_processor_job.rb`, `event_store/processing/`

## Problem

`issues` has no `times_seen`, `first_seen_at` or `last_seen_at`. `IssueSerializer` computes `events_count` and `last_seen_at` with `@issue.events.count` and `@issue.events.first`. Each is an HTTP call to EventStore that runs a DuckDB query over the `events` view. The list is `2 x N` calls for N Issues.

`IssuesController#index` has no pagination, so N is every Issue the Organization has ever had. At about 500 Issues the page does not render.

## Scope

- Add `times_seen`, `first_seen_at` and `last_seen_at` to `issues`. No backfill: the data is test data, so the database is wiped and recreated.
- Keep them current as Events arrive, written by EventStore in Event processing (see Decision).
- Serve the list and the sort from those columns, with no EventStore call per Issue.
- Paginate the Issues list.

Out of scope, kept for later: FTS5 search instead of `title LIKE '%query%'`, and wiring the dead time-range, sort and environment controls in `Issues/Index.tsx`.

## Decision (2026-10-02)

EventStore writes the columns directly, under [ADR 0001](../../../docs/adr/0001-eventstore-writes-console-tables.md). Console does not count from messages: they carry only `issue_ids`, they are at-least-once, and a crash can lose an `issue_created` (accepted gap), so counts from messages could drift both ways.

Writing directly is still not exactly-once. Event processing moves the processing cursor in Pebble after its SQLite work, so a crash replays the batch. The update needs a replay guard (see the agent brief).

No backfill, because the data is disposable.

## Acceptance

- The Issues list makes no per-Issue EventStore call.
- The list is paginated, and sorts by last seen and first seen.
- Counts match EventStore after a burst of Events, and after a replayed batch.

## Agent Brief

**Category:** enhancement
**Summary:** Keep per-Issue seen counts and timestamps on `issues`, written by Event processing, and serve a paginated Issues list from them.

**Current behavior:**
`issues` has no count or timestamp columns. For each Issue the Console's serializer asks EventStore for an Event count and the newest Event, and each is a DuckDB query. The Issues list has no pagination and is ordered by creation time, so it makes `2 x N` EventStore calls for N Issues and stops rendering at about 500.

**Desired behavior:**
- `issues` has `times_seen` (not null, default 0), `first_seen_at` and `last_seen_at`. Console owns the migration.
- Event processing updates them as it handles Events, through the `IssueRepository` seam and its SQLite adapter. An Issue's `times_seen` is the number of its Events that reached DuckDB. `first_seen_at` and `last_seen_at` are the oldest and newest of those Events' `timestamp`. Events skipped for bad content are not counted.
- The update is idempotent against replay. A batch can be handled again from the processing cursor after a crash, including a batch that now holds more Events than before. The counts must come out the same as if each Event were counted once. Store the guard in SQLite, and commit it in the same transaction as the count change, because the processing cursor is in Pebble.
- Console reads the counts from the columns. The Issues list and the Issue page make no per-Issue EventStore call for the count or the last-seen time. Until an Issue has a counted Event, its `last_seen_at` falls back to `created_at`.
- `IssuesController#index` is paginated, 25 per page, with a `page` param, and the response carries enough to render page controls (current page, total pages, total count). The default sort is last seen, descending. A sort param also supports first seen. Status, query and project filters keep working and apply before pagination.

**Key interfaces:**
- `IssueRepository` (in Event processing): gains a way to record counted Events for a batch. The domain decision about what counts stays in Event processing, and the repository only persists it.
- The Issue serializer: `events_count` and `last_seen_at` come from the columns, and `first_seen_at` is added.
- The Issues list props: an Issues page plus pagination metadata, and a sort filter alongside the existing filters.
- ADR 0001 applies: the Go SQLite code and the Console schema change in the same commit.

**Acceptance criteria:**
- [ ] A Go test shows that after a burst of Events across several Issues, `times_seen`, `first_seen_at` and `last_seen_at` equal what DuckDB holds for each Issue.
- [ ] A Go test replays a batch (crash after the Issue work and before the cursor move, and a replay whose batch is larger than the first) and shows the counts unchanged.
- [ ] An Event skipped for bad content does not change any Issue's counts.
- [ ] A Rails test shows the Issues list makes no EventStore call per Issue.
- [ ] The list returns 25 Issues per page, `page` selects the page, and the pagination metadata is correct, including with filters applied.
- [ ] The list sorts by last seen (default) and by first seen, and the sort is done in SQL on the columns.
- [ ] The Index page renders pagination and the sort control for last seen and first seen.
- [ ] On a freshly created database, `bin/rails db:reset` and the Go integration test still pass.

**Out of scope:**
- Backfilling existing Issues; the database is wiped and recreated.
- FTS5 search instead of `title LIKE`.
- The Priority sort, the time-range picker, and the `environment` filter that serializes as `"undefined"`.
- Counting from Console messages, and changing the `issue_created` and `issue_received_event` message payloads.
- Changing how Event processing orders its steps, other than where the new write goes.

> **Resolved (2026-10-02, `8b2af22`).**
>
> - `issues` has `times_seen`, `first_seen_at` and `last_seen_at`. `project_seen_cursors` is the replay guard: per Project, the last Event whose counts are recorded. It is committed in the same SQLite transaction as the counts. ADR 0001 lists it.
> - Event processing records the counts in a new step after DuckDB indexing, through `IssueRepository.RecordSeenEvents`. Only Events that reached DuckDB count.
> - Beyond the brief: on a startup replay, the rows DuckDB held past the cursor are checked one by one (`DuckDBWriter.HotUUIDsBetween`), so a row skipped for bad content before a crash isn't counted. Code review found that gap.
> - The Issue page's events pagination total also reads `times_seen`, so the page makes no EventStore count call.
> - The Priority sort option was removed from `Issues/Index.tsx`, because the server ignores it. The time-range picker and the `environment` filter are untouched.
> - Not done: a `GLOSSARY.md` entry for the seen cursor, next to **Processing cursor**.
