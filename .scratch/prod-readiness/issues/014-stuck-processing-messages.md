# EventStore messages stuck in `processing` are never retried

Status: resolved

**Source:** found while designing [ingest write path](../../ingest-write-path/spec.md) (2026-09-26), not a `review.md` item
**Category:** bug
**Area:** `console/app/jobs/event_store_message_processor_job.rb`, `console/app/models/event_store_message.rb`

## Problem

`EventStoreMessageProcessorJob#process_message` sets a message to `processing` before it handles it. The message only moves to `processed` or `failed` if the job finishes. `EventStoreMessage.processable` selects only `pending` and `failed` messages.

So if the Console process dies in the middle, for example during a deploy, an OOM kill or a crash, that message stays in `processing` forever. Its `issue_created` or `issue_received_event` notifications are never sent.

This matters more after the [ingest write path](../../ingest-write-path/spec.md) change. EventStore now works hard to send each message at least once, and a message lost on the Console side undoes that.

## Decided

Settled in triage on 2026-09-30. The agent brief under Comments is the contract.

- Drop the `processing` claim. A message stays `pending` while it is handled, so a crash leaves it retryable.
- Only one run of the job at a time, with Solid Queue's `limits_concurrency to: 1`.
- The "one transaction" option can't work. The message is in `message_queue.sqlite3`, and `perform_later` writes to Solid Queue's `queue.sqlite3`. SQLite has no transaction across two database files.

## Comments

### 2026-09-30 triage

> *This was generated by AI during triage.*

- **Confirmed from the code.** `process_message` sets `processing` before handling, and `EventStoreMessage.processable` selects only `pending` and `failed`. Nothing else reads or resets `processing`, so a message left there by a crash is never handled. Not reproduced by killing a process.
- **Second gap found.** The job is scheduled every second in `config/recurring.yml` and has no concurrency limit. It reads messages, then updates them, with no atomic claim. If a run takes longer than a second, the next run can handle the same `pending` message and send its notifications twice.
- **One transaction is not possible.** See Decided.
- **Redundancy:** nothing sweeps or reclaims stale messages. There's no `.out-of-scope/` directory.
- **State:** `ready-for-agent`, with option (b) (drop the `processing` claim) chosen over a reclaim timeout because it needs no timeout to tune.

## Agent Brief

**Category:** bug
**Summary:** An `EventStoreMessage` interrupted by a Console crash must be handled again on a later run, and two runs of the processor job must never overlap.

**Current behavior:**
- `EventStoreMessageProcessorJob` runs every second. For each message in `EventStoreMessage.processable` (`pending` or `failed`, with `attempts < 5`), it sets `status: processing` and adds 1 to `attempts`. It then enqueues one `IntegrationNotificationJob` per Issue in `payload["issue_ids"]`, and sets `processed` with `processed_at`, or `failed` with `error_message` if handling raises.
- If the process dies after `processing` is set and before `processed` or `failed`, the message stays `processing` forever. Its notifications are never sent.
- The job has no concurrency limit. Two overlapping runs can both handle the same `pending` message.

**Desired behavior:**
- **No `processing` claim.** A run adds 1 to `attempts` and leaves the status alone while it handles the message. Success sets `processed` with `processed_at`. A raised error sets `failed` with `error_message`, as today. A crash mid-handling leaves the message `pending`, or `failed` if it was `failed` before, so the next run handles it again.
- Delivery is at least once. A message interrupted after some notifications were enqueued can enqueue them again on retry. That's acceptable per the ingest write-path spec.
- The 5-attempt limit still applies, and interrupted attempts count toward it.
- **One run at a time.** The job declares Solid Queue's `limits_concurrency to: 1` with a fixed key, such as `"event_store_message_processor"`, and `on_conflict: :discard`. A run that can't get the limit is dropped, because the next scheduled run starts a second later.
- Leave the `processing` value in the `status` enum, so existing rows still load. Messages already stuck in `processing` in a deployed database should also be handled again. Either `processable` includes `processing`, or a one-off data migration resets them to `pending`. Pick whichever is simpler, and say which in the commit message.

**Key interfaces:**
- `EventStoreMessageProcessorJob#perform` and its per-message handling: no status change before handling.
- `EventStoreMessage.processable`: still `pending` and `failed` with `attempts < 5`, plus stuck `processing` rows if you choose that route.
- The `limits_concurrency` declaration on `EventStoreMessageProcessorJob`. `IntegrationNotificationProcessorJob` already uses the same feature.

**Acceptance criteria:**
- [ ] While a message is being handled, its status is not `processing`. A test can check this by stubbing `IntegrationNotificationJob.perform_later` to record the message's status.
- [ ] A test that simulates a crash mid-handling, for example by raising an exception that isn't a `StandardError` from the stubbed `perform_later`, leaves the message `pending` with `attempts` raised by 1. The next `perform_now` handles it and marks it `processed`.
- [ ] A message that has reached 5 attempts is not handled again.
- [ ] A message already in `processing` from before this change is handled on a later run.
- [ ] `EventStoreMessageProcessorJob` declares `limits_concurrency` with `to: 1` and `on_conflict: :discard`.
- [ ] The existing tests in `event_store_message_processor_job_test.rb` pass, and so does the full Console test suite.

**Out of scope:**
- Exactly-once delivery or de-duplicating notifications. Threshold alerts already de-duplicate per the integration-notification spec.
- `ConsoleMessage` and any other message table.
- EventStore's side of the message queue.
- Changing the retry limit, or adding backoff between attempts.

### 2026-09-30 resolved

> *This was generated by AI during implementation.*

- `EventStoreMessageProcessorJob` no longer sets `processing`. It only adds 1 to `attempts` before handling, so a crash leaves the message `pending` (or `failed`).
- Stuck rows: `EventStoreMessage.processable` now includes `processing`, which is simpler than a data migration.
- `limits_concurrency to: 1, key: "event_store_message_processor", on_conflict: :discard`. The lock uses Solid Queue's default duration of 3 minutes. A run longer than that could overlap the next one, and a crashed run holds the lock for up to 3 minutes. Both are acceptable under at-least-once delivery.
