# v0.9.0 (2026-10-22)

Filters on one Service or one log file read far fewer Logs: each Log file is sorted by the Project's Log file order, and a busy Project's Logs reach sorted Log files every quarter-hour instead of every hour. It's still a 0.x prototype, not yet hardened for production.

## What's new

- **Log file order.** The export sorts each Log file by the Project's Log file order, then time, so a filter on those Fields skips most of a file's row groups.
  - The default is `service`, then the `file` Attribute. An admin can change it on the Project's settings page, beside Log Retention: up to three Fields, from `service`, `environment`, `level` or an Attribute name. "Time only" turns it off.
  - A change applies to Logs exported after it.
  - On a real hour of a busy Project, sorted by `file, time`, `file == "sidekiq.log" and message contains …` went from 1,384 to 210 ms, and the file came out 13% smaller.
  - MCP `list_projects` shows each Project's Log file order.
- **Busy Projects' Logs exported every quarter-hour.** A Project whose last quarter-hour holds at least 122,880 Logs (one DuckDB row group) has each quarter-hour written to its own sorted Log file, 15 minutes after it ends. Its hot table, where nothing is sorted, holds 15 to 30 minutes instead of one to two hours, and each export is a quarter of the size, so Log processing waits less.
  - Quiet Projects keep one Log file an hour, as before.
  - The export runs at each quarter-hour start. An hour that has quarter-hour files keeps them; Logs that arrive for a range already exported go to the hour's late file at the next run.
- **A notice for slow SQL text matches.** SQL that matches `message` with `ILIKE` (or `LIKE … ESCAPE`) and a leading `%` still runs, and the answer now carries a notice with the faster SQL (`contains(lower(message), …)`). MCP `run_sql` passes the notice on.

## Behaviour changes

- **The hot window starts at the quarter cutoff.** A Log sent more than 15 to 30 minutes after its time is now a late Log, where before it took an hour or more. Late Logs are still stored, listed and filtered, and they get promoted columns at export. They aren't counted in Attribute counts, though, so `list_fields` says a Log sent more than about 15 minutes late may not be counted.
- **After an outage,** Logs held back by a shipper for more than 15 to 30 minutes arrive as late Logs, so they are read from the late table until the next export, which is at most 15 minutes away for a busy Project.
- **Bucket objects:** a busy Project now has up to four Log files an hour instead of one, so its bucket objects and cold-read requests grow up to fourfold.

## Upgrading from v0.8.0

One migration adds `projects.log_file_order`. Console runs it when it starts, so there's nothing to do by hand. There are no config changes. Hours already exported keep their files. The first export after the upgrade decides for each Project whether it is busy.

```bash
git fetch --tags && git checkout v0.9.0 && deploy/install
```
