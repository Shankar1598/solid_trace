# v0.15.0 (2026-10-27)

Adds Traces: SolidTrace stores the Transactions that Sentry SDKs send, shows a trace with its Logs and Issues across an Organization's Projects, and lists each Project's requests and jobs by the time they take. It's still a 0.x prototype, not yet hardened for production.

## Added

- **Traces.** EventStore keeps the `transaction` items Sentry SDKs send, with the sample rate from the envelope, and stores their Spans in ClickHouse with each Span's self time, its group (op and description, literals taken out) and how often it repeats. Turn tracing on in the SDK with a sample rate, such as 1–5%; [docs/traces.md](../traces.md) shows how.
- **The trace page.** A trace opens as a waterfall across the Organization's Projects, with repeated Spans collapsed (×n), the critical path marked, and the trace's Issues and Logs beside it. It opens even when the trace wasn't sampled, with the Logs and Issues that carry its id. An Issue's Event, a Log in the explorer and a trace id pasted into the command palette each open it.
- **Performance.** Each Project's Transactions, one row per name, by the time they take: throughput, p50, p95, p99, error rate and time consumed, each against the period before. Throughput and time consumed are estimates, scaled up by the sample rate. A Transaction's page shows its p95 by release, where its time goes by op and by Span group, its repeated Spans and its slowest traces.
- **Trace Retention.** Spans are kept 14 days unless set otherwise on Settings → Instance or a Project's page, and move to the bucket after `local_cache_hours` like Logs. They count toward the disk limit.
- **MCP tools.** `list_transactions`, `get_transaction` and `get_trace` answer what the Performance, Transaction and trace pages show, `get_trace` summarised to about 200 rows. `run_sql` reads a Project's `spans` table, and `create_project`, `update_project` and the instance settings tools set trace Retention.
- **Spans on the Overview.** Spans received and stored, per Project and in total, and the Storage section counts them with Logs. `get_overview` adds a Datadog APM estimate.
- **Sending to sentry.io and SolidTrace at once.** [docs/traces.md](../traces.md) has a Ruby and a Go transport that send each envelope to both, for moving over one app at a time, and request and Sidekiq middleware that put the trace id on Logs, with the Log transform that reads it.
- **SolidTrace traces itself.** Console sends the Transactions of 5% of its requests and jobs to the Meta Organization's Project. Its Logs carry their trace id, and the Project starts with the Log transform that reads it, so a Console request opens as a trace with its Logs. It never traces its every-second message job or health checks.
- **Send Console's Issues and Trace Console** on Settings → Instance, and in `update_instance_settings`, turn off Console's Events and its tracing with no restart. Both start on.

## Changed

- **Console's Issues go to the Meta Organization's Project.** Console sends its own exceptions there with the DSN `deploy/install` writes, rather than to the DSN in its credentials, which it still uses when `SENTRY_DSN` is unset. A job that fails notifying the Meta Organization's Integrations sends no Event, as it would notify them again.
- **The Project page's Retention card** sets Logs and Traces, and Settings → Instance's default is now "Default Log Retention".

## Upgrading from v0.14.1

`deploy/install` runs Console's two migrations (trace Retention, and the two Console toggles) and adds two settings to `deploy/.env`, once: `SENTRY_DSN`, the Meta Project's DSN made from `META_PROJECT_KEY`, and `SENTRY_TRACES_SAMPLE_RATE=0.05`. Set the rate to `0` to trace none of Console's requests. `db_prepare` gives the Meta Project its Log transform, unless it has had one. EventStore adds the `spans` and `trace_index` tables, a trace id index on Logs and Events' trace id on its first start; the indexes cover parts written from then on.

```bash
git fetch --tags && git checkout v0.15.0 && deploy/install
```
