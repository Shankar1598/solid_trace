# v0.24.0

EventStore takes Logs and metrics from an OpenTelemetry Collector or SDK, on `POST /v1/logs` and `POST /v1/metrics`. An Admin can make the Agent Project's one key, for Claude Code's OpenTelemetry only, and SolidTrace keeps only the records of a Captured repository. The new `solidtrace-skills` plugin reviews a change, opens its PR and writes its Review record, which the new Review records page and two MCP tools show. The Agent sessions page sorts by a column and shows the effort of each reply, and Console's pages send their errors to its Sentry. It's still a 0.x prototype, not yet hardened for production.

## Added

- **OpenTelemetry Logs and metrics.** An OpenTelemetry Collector or SDK sends to the Ingest URL over OTLP/HTTP, in protobuf or JSON, with the Project's key. See [docs/logs/opentelemetry.md](../logs/opentelemetry.md).
  - `POST /v1/logs` takes Logs. The resource, scope and record attributes become Attributes in one flat namespace. The record wins over the scope, and the scope wins over the resource. `severity_number` gives the Level, else `severity_text`. `body` gives the message, and `service.name` gives the Service. A body that is not a string is kept as `original.message`. The [ADR 0002 amendment](../adr/0002-logs-scoped-by-project-flat-attributes.md#amended-how-an-otlp-log-record-becomes-a-log-2026-11-23) has every rule.
  - `POST /v1/metrics` takes metrics. EventStore has no metric store, so it stores each Metric data point as one Log. The message is the metric name, the time is the time of the data point, and the Level is `info`. A sum or a gauge has its number in `metric.value`. A histogram or a summary has `metric.count` and `metric.sum`, and a histogram also has `metric.min` and `metric.max`. `metric.type`, `metric.unit`, `metric.temporality` and `metric.start_time` tell what the values are. EventStore does not keep the buckets. A sender's own `metric.*` attribute is kept as `original.metric.*`. Send delta temporality. EventStore stores a cumulative value as it comes, so a `sum` of cumulative values is too large.
  - Both routes take the key as the other Log routes do (`Authorization: Bearer <key>`, or a `sentry_key=` form), with the same limits (10 MiB as sent, 50 MiB after decoding) and the same Content-Encodings. One request is one Log batch, and it adds to the Project's Ingest counts. The answer is an OTLP export response in the encoding of the request. EventStore does not store a Log over 1 MB, and `partial_success` counts it (`rejected_log_records`, or `rejected_data_points` for metrics). Another Content-Type gets 415, a body that does not decode gets 400, and an overloaded EventStore answers 503 with `Retry-After`. EventStore takes no gRPC and no traces. With `ingest_refuse_forwarded_http` on, `/v1` refuses plain HTTP that a load balancer forwarded, as `/api` does.
  - The Logs explorer of a Project with no Logs has two OpenTelemetry tabs in its Get started panel, with the Ingest URL and the key filled in. One is a Collector config file that runs as it is. The other is the environment variables of an SDK.
- **Claude Code's telemetry in the Agent Project.** Claude Code can send OpenTelemetry events and metrics while it works: the tokens, the cost, the model and the effort of each API request, the tool results, the lines of code and more, with the engineer and the repository on each record. SolidTrace stores them as Logs of the Agent Project, next to the Agent sessions. The records do not hold the text of a prompt, a reply, a Bash command or a tool input. See [Send Claude Code's telemetry to SolidTrace](../agent-sessions.md#send-claude-codes-telemetry-to-solidtrace) and [ADR 0023](../adr/0023-the-agent-project-takes-one-key-for-opentelemetry-only.md).
  - An Admin clicks **Generate a key** on the Agent Project's page in **Projects**, or calls `create_key`. The Agent Project can have only one key, and Console refuses a second. Rotate and delete work as for the keys of other Projects, and each member can read the key. The key has no DSN, so the Project page and `get_project_setup` give only the key, with what it is for.
  - The key works on `/v1/logs` and `/v1/metrics` only. The store, envelope and JSON Log routes answer 403 for it, so it makes no Event, Issue, Span or JSON Log.
  - Ingest keeps a record only when its own `vcs.repository.url.full` matches a Captured repository. A value on the resource does not count. Ingest drops each other record when it arrives, and does not store it. Claude Code gets a success for a dropped record, so it shows no warning. An empty list of Captured repositories drops every record, and a change to the list applies to the next request. Claude Code reads only the `origin` remote of the folder where it starts.
  - SolidTrace stores each record of the key in the file `otel`, and keeps a `file` that the sender sends as `original.file`. So a record cannot show as a Run, a Dispatcher Log or an Agent session step. Start each Query on these records with `file == "otel"`.
  - Settings → Agent sessions → Capture setup has step 5, **Send telemetry (optional)**. It gives the `env` block for `~/.claude/settings.json`, and a managed-settings block that pushes the plugin and the telemetry together. Console fills in the Ingest URL and the key, or `<key>` with a link to the Agent Project's page while it has no key. The block does not set `OTEL_LOG_USER_PROMPTS` or `OTEL_LOG_TOOL_DETAILS`, because Claude Code sends the records of every repository on the machine. Claude Code reads the settings only when it starts.
  - The Overview shows the dropped records in **Received → Kept → Stored**, as a hatched slice after Kept, and as **Filtered out as not of a Captured repository** below the band. Each Project's row shows its Logs filtered out, and `get_overview` gives them as `filtered_logs`.
  - The Get started panel of the Agent Project's Logs explorer links to step 5, in place of the snippets and the test Log of other Projects. While the Agent Project has no key, it says that an Admin makes the key first.
- **Review records.** **Review records** is a new page in the Organization's navigation, next to **Agent sessions**. It has one row for each PR whose `open-pr` or `update-pr` Agent session uploaded, the PR stored last first. Each row has the PR, its newest round, the time when SolidTrace stored it, the counts of findings, fixed findings, findings that the reviews missed and confirmations not given, and a link to its Agent session. Click a PR to open its record: the story of the feature, the review runs with their reviewers and models, each finding with its decisions in order and its outcome, the confirmations, and the other rounds of the PR. The pages show the record as text only, never as HTML or Markdown. Each member can read them. See [Read the Review records](../agent-sessions.md#read-the-review-records) and [ADR 0024](../adr/0024-review-records-come-from-the-final-reply-of-an-agent-session.md).
  - Over MCP, `list_review_records` lists the newest record of each PR, at most `limit` rows (50 by default, 200 at most). `get_review_record` gives one record with the rounds of its PR, and gives its findings in pages: `findings_limit` findings (30 by default, 1 to 100) from `findings_from`. The answer has `findings_total`, and `next_findings_from`, which is `null` after the last page. So the first page of a large record stays below Claude Code's limit of 25,000 tokens for an MCP answer. A token with `mcp:read` can call both tools. A token that reads only one Project cannot. See [docs/mcp.md](../mcp.md).
  - SolidTrace reads a record from the final reply of an uploaded Agent session: the last `solidtrace-pr-record` block of an agent reply in the main transcript, when it is valid JSON of version 2. It keeps the whole record, also past the 64 KiB at which a Log cuts a string. The records follow the Agent Project's Retention.
- **The `solidtrace-skills` plugin.** A second plugin of the SolidTrace marketplace, `solidtrace-skills@solidtrace`, reviews a change in two stages, opens its PR, works on the PR's feedback, and records each finding with each decision on it. It is not on by default, and it needs the `solidtrace` CLI. The release has it as `solidtrace-skills.zip`, in the same `marketplace.json`. See [Record what each review found](../agent-sessions.md#record-what-each-review-found-the-skills-plugin).
  - `/solidtrace-skills:code-review` reviews one step of a feature with three reviewers at the same time: bugs and spec, tests, and code quality. The agent decides each finding (`fix`, `dispute`, `trivial`, `defer` or `ask`), and a verifier checks each finding that the agent disputes or calls trivial. A fix commit ends with a trailer such as `Review-Findings: run 1: F2, F5`, so `git log` finds the fix of each finding.
  - `/solidtrace-skills:deep-review` tries to break the whole branch with several adversaries (three on Opus xhigh by default), each in its own worktree. It keeps only the findings that a run proves again. When `open-pr` skips it because the diff changes only docs, tests or test data, the reason is `no code`.
  - `/solidtrace-skills:open-pr` runs the final stage on the whole branch diff, in this order: the deep review, high availability and infrastructure, the person's decisions and the fixes, and security last. Then it pushes the branch and opens the PR on GitHub or Bitbucket, or with `solidtrace pr` in a Run. It stops when the branch already has an open PR. `open-pr local` does all of it but the push, and writes the PR to `solidtrace-pr/<branch>.md` in the repository's Git folder. The PR body shows the record, and the final reply ends with it.
  - `/solidtrace-skills:update-pr` works on the open PR's comments, reviews and failed checks. Each change request is a finding, with who found it. The agent fixes only after the person's go-ahead, runs security on the fix diff, replies to each comment, and writes the next round of the record.
  - The `record-writer` agent can only read files. It writes the notes of the record: the story, the person's words, and what the reviews missed.
  - `.solidtrace/review.toml` in the repository sets the model and the effort of each role.
  - New CLI commands do the mechanical part. `solidtrace review sessions` lists the Agent sessions on the machine that link to a PR's branch, and `review digest` makes one short timeline of them. `review block` checks and records a findings block, and `review fixed` records the fixes of a commit from its trailers. `review record` builds the record from the digest and merges the notes. `review check` checks a record against its digest, and exits 1 when it finds a problem.
- **`/solidtrace-skills:try-pr <PR>`** runs a PR's dev stack on your machine before you approve the PR. It takes a GitHub or Bitbucket Cloud PR link, a PR number of the clone's `origin`, or a branch name, and puts the code in a worktree of its own, `<clone>/.worktrees/try-pr-<n>`. It finds the repository's launch recipe (a launch skill, else the docs), starts the stack on ports and data of its own, and gives the URLs and the sign-in. Before it starts the PR of another author, it asks you, because the PR's scripts run as you. It refuses a closed or merged PR and a Bitbucket PR from a fork. It never runs a start script that kills processes or holds fixed ports. `try-pr done <PR>` stops the stack and removes the worktree, and `try-pr list` shows each one. See [the try-pr skill](../../cli/plugin-skills/skills/try-pr/SKILL.md).
- **Sort the Agent sessions.** See [docs/agent-sessions.md](../agent-sessions.md).
  - On the Agent sessions page, click the heading of **Start**, **Last activity**, **Tokens** or **Estimated cost** to sort the list by it. The first click shows the latest times, the most tokens or the highest cost first. A second click turns the order around. An arrow next to the heading shows the sorted column and its direction. The other sortable headings show a quiet up-down arrow on hover and on focus. **Tokens** sorts on a phone too. EventStore sorts all the Agent sessions that the filters select before it takes the 500 rows of the page, so the most expensive Agent sessions of a range are always on the page, also when the range has more than 500. Agent sessions that tie go by id, so the rows are always the same. An Agent session with no cost comes after those with a cost, in both directions. The order is in the page's URL (`sort` and `direction`), and a change of the range or a filter keeps it.
  - `list_agent_sessions` takes `sort` and `direction`. `sort` is `last` (the default), `start`, `tokens` or `cost`, and `direction` is `desc` (the default) or `asc`, as on the page. So an agent can ask for the most expensive Agent sessions with `sort: cost`. The answer gives the order, and its link opens the page in that order. See [docs/mcp.md](../mcp.md).
  - EventStore's list of Agent sessions (`POST /api/:project_id/agent-sessions`) takes `sort` and `direction` with the same values. Any other value gets 400. The limit applies after the sort.
- **Agent session effort.** The effort of each Claude Code reply (`low`, `medium`, `high`, `xhigh` or `max`), from Claude Code 2.1.296, shows next to its model. The Agent session page has an **Effort** row in its details, with the effort of the latest reply in the main transcript. The title of each reply shows `model · effort` before its tokens, as `claude-opus-5-5 · high`. The Model column of the Agent sessions list shows `model · effort` too. `get_agent_session` and `list_agent_sessions` over MCP give `effort` next to `model`. A reply's Log has its effort in the `agent.effort` Attribute, next to `agent.model`. A reply that Claude Code writes itself, such as an API error, shows no model. See [docs/agent-sessions.md](../agent-sessions.md).
- **Console's pages send their errors to its Sentry.** While Console has a DSN and **Send Console's Issues** is on (Settings → Instance), a signed-in user's browser sends its errors to Console: an uncaught error, a rejected promise, or a page that stops while it renders. Console sends them on with its own DSN, to the Meta Organization's Project on an install, so the browser never holds that Project's key. Before it sends a frame, Console un-minifies it with the build's source maps, so an error stays one Issue after a release. The browser sends errors only, not traces. With **Send Console's Issues** off, Console sends no errors of its pages and none of its server. See [docs/traces.md](../traces.md#solidtrace-traces-itself).
- **The Factory's Google Cloud wizard.** `factory/setup/gcp-wizard` sets up the Factory on Google Cloud in 17 stages, from an empty project to a first Run that opens a PR on a Bitbucket test repository. It asks where the Dispatcher, the Nomad server and Squid run: on a server VM of their own (the default), or on the SolidTrace VM. It makes one agent VM and adds one Claude account. For each command, the operator chooses: the wizard runs it, the operator runs it, or the operator skips it. The wizard keeps its values in `~/.config/solidtrace-factory/gcp/values.env`, and the secrets stay on the VMs. It does not set up webhooks, autoscaling or take-over. See [docs/factory.md](../factory.md).

## Changed

- **Agent sessions page.** **Last activity** shows how long ago it was, such as "a few seconds ago" or "5 minutes ago", and changes while the page is open. The hover text shows the time. The list still opens with the latest activity first.
- **Agent sessions page.** The person or the Run of a row is plain text, not a link of its own. A click anywhere on the row opens the Agent session, and the title stays the row's link.
- **Agent sessions page.** When the limit leaves Agent sessions out, the note under the list says the order of the rows, as "The first 500 of 812 Agent sessions, most tokens first".
- **A page that stops with an error** shows "This page stopped with an error", with the error and a **Reload page** button, in place of a blank page.
- **The dark theme** is a scale of greys, not black and white. The page, the sidebar, the menus and the hover each have a grey of their own, the sidebar has no border line, and the text is softer. The light theme does not change.
- **The starter Factory Dashboard's Queries** read only the files of run events (`file startswith "runs/"`). So the Logs of the Agent Project's key, in the file `otel`, do not change the numbers of its Charts. A migration changes the Charts of the Factory Dashboards that exist (see Upgrading).
- **The Factory guide** lets the Dispatcher, the Nomad server and Squid run on the SolidTrace VM, beside Console, for a pilot ([ADR 0019](../adr/0019-agents-run-on-nomad-and-the-factory-is-a-separable-module.md)). No agent runs there, and never a Nomad client. A server VM of their own stays the default. On the SolidTrace VM, each download of an agent goes through that VM, they use about 1 GB of memory, and that VM holds the agents' secrets. See [docs/factory.md](../factory.md).

## Fixed

- **A Captured repository matched a remote only with the same letter case.** The CLI and EventStore ignored the case of the host only. So an entry `github.com/someowner/repo` did not match the remote `github.com/SomeOwner/repo`, and the Agent session did not upload. Now the CLI, the upload check of EventStore and the telemetry filter ignore the case of the whole name, on both sides. The names of GitHub, GitLab and Bitbucket repositories do not depend on case, and Claude Code's telemetry gives the repository in lower case. An engineer gets the new rule for Agent sessions with the CLI of this release.
- **A Table preview in the chart editor stopped the Dashboard page.** The cells of the table are tags, which need the tag menu, and the menu was only around the cards of the Dashboard. Now the chart editor is inside the menu too, and the preview shows the table.

## Upgrading from v0.23.3

EventStore runs 3 ClickHouse steps when it first starts. They add a column or a table, and change no data:

- 11203 adds the `last_reply_effort` column to `agent_sessions` (`ALTER TABLE … ADD COLUMN IF NOT EXISTS`), for the effort of an Agent session.
- 11204 adds the `logs_filtered` column to `log_ingest_counts` (`ALTER TABLE … ADD COLUMN IF NOT EXISTS`), for the Logs that the Agent Project's key filtered out.
- 11205 makes the table `review_records` (`CREATE TABLE IF NOT EXISTS`), for the Review records. It is partitioned by Project and day, as `agent_sessions` is, so it follows the Agent Project's Retention, the deletion of the Project and the disk limit.

Console runs 1 migration when it starts, `20261125100000_add_run_files_to_factory_dashboard_queries`. It changes data, not the schema. On the Dashboards of each Agent Project, a Chart whose Query is still one of the 4 Queries of the starter Factory Dashboard of v0.23.0 to v0.23.3 gets `file startswith "runs/" and` at the start of its `where`. A Chart that has one of the 4 titles, but a Query that a person changed, stays as it is. The migration names each such Chart and its Dashboard in Console's output at start (`sudo docker compose -f deploy/docker-compose.yml logs console`). Add `file startswith "runs/"` to the Query of such a Chart by hand. This is the only step by hand, and only when the migration names a Chart.

`deploy/` has no change. There is no new key in `event_store.yml` and no new variable in `deploy/.env`. The ingest address (port 4443) sends each path to EventStore, so `/v1/logs` and `/v1/metrics` work with no change to Caddy.

An Agent session that EventStore parsed before the update has no effort, and its page shows "Not known". It has no Review record either. EventStore does not parse a stored transcript again. The parse reads each upload one time, and a second parse would add its tokens to the totals again. An Agent session that continues after the update gets an effort when a new reply in its main transcript has one, and a Review record when a new final reply has one.

The new features need no step at the update. After it:

- To send Claude Code's telemetry, an Admin makes the Agent Project's key, and each engineer adds the settings of step 5 of Capture setup. A team that uses managed settings can use the block of step 5, which has the plugin and the telemetry.
- For the `solidtrace review` commands and the letter-case rule of Captured repositories, each engineer installs the CLI of this release (step 1 of Capture setup).
- To use the review skills, an engineer installs `solidtrace-skills@solidtrace` from this release's `marketplace.json` (step 2 of Capture setup has the file).

```bash
bin/upgrade v0.24.0
```
