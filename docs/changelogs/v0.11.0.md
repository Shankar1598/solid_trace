# v0.11.0 (2026-10-23)

EventStore keeps Logs and Events in ClickHouse, which runs beside it in the compose stack, and DuckDB leaves EventStore. Queries use about half the CPU they did on DuckDB, and there's far less machinery: no hot tables, Log export, late Logs, promotion, manifest, uploads, eviction or Event archive. [ADR 0016](https://github.com/Shankar1598/solid_trace/blob/v0.11.0/docs/adr/0016-logs-and-events-in-clickhouse.md) has the design and the numbers. It's still a 0.x prototype, not yet hardened for production.

## What's new

- **ClickHouse 26.8 LTS** (`clickhouse/clickhouse-server:26.8.34.13`), a new compose service on `127.0.0.1:4200`. EventStore talks to it over the native protocol.
- **Logs** are one shared `logs` table, partitioned by Project and UTC day and sorted by Project, `service`, the `file` Attribute and time. Attributes are one JSON column, and each value keeps its type. A Log is in its final place once inserted, whatever its time. Pebble still holds Logs before ingest answers `200`. Log processing inserts about once a second, exactly once, with a dedup token.
- **Events** are one `events` table. The Event archive is gone.
- **The bucket:** with an `object_store`, a day's Logs move to the bucket once they're `local_cache_hours` old (24 by default), under the `clickhouse/` prefix.
- **Retention, Project deletion and the disk limit** drop whole (Project, day) partitions.
- **Charts and the histogram:** a minute-counts materialized view feeds the histogram, and the bin cache stays.
- **SQL queries are ClickHouse SQL.** Each runs as a per-Project read-only ClickHouse user. Row policies show it only its Project's rows, and a settings profile caps its time, memory, threads and result size. It has no grants for files, URLs, table functions or system tables. `logs` and `events` still show the explorer's range, and SQL may widen it only within its Project.

## Behaviour changes

- **SQL written for DuckDB** may need changes to run as ClickHouse SQL. `run_sql`'s description and the SQL docs describe the new tables.
- **The Log file order setting is gone** from Project settings and MCP. `projects.log_file_order` stays in the table, ignored, so you can roll back to v0.10.0.
- **The bucket is no longer a self-contained copy of Logs.** ClickHouse keeps the parts' metadata on local disk, so the bucket alone can't restore them.
- **ClickHouse gets half the machine's memory** (`max_server_memory_usage`), set by `deploy/install`. There's no container memory limit: under one, ClickHouse 26.8 scans run about 1.9× slower.

## Logs from before the upgrade

Log files written by DuckDB releases stay where they are, on disk or in the bucket. They're read in place until Retention deletes them; nothing is imported. SQL queries don't read them.

## Upgrading from v0.9.0 or v0.10.0

```bash
git fetch --tags && git checkout v0.11.0 && deploy/install
```

`deploy/install` does the rest:
1. It writes `SOLIDTRACE_CLICKHOUSE_PASSWORD` and ClickHouse's memory to `deploy/.env`.
2. If `logs.duckdb` has no `prepare-clickhouse` marker, it stops the services and runs v0.10.0's `prepare-clickhouse`, which pulls v0.10.0's EventStore image. Logs in DuckDB are exported to Log files first, so this takes a while on a busy install. If it fails, the services stay stopped, and it says how to retry or go back to v0.10.0.
3. It starts ClickHouse, then EventStore.

EventStore refuses to start on a `logs.duckdb` that `prepare-clickhouse` didn't prepare. `event_store.yml` needs no edits. `duckdb_path` and `logs_duckdb_path` now only locate the old Logs, and `parquet_storage_path`, `duckdb_memory_limit` and `duckdb_temp_directory` are ignored with a warning. The `clickhouse` block is optional, and its defaults match the compose service.

Coming from v0.9.0 also brings v0.10.0's changes: email settings moved into Console (copy `SMTP_*` and `MAIL_FROM` into Settings → Email), and the request log.
