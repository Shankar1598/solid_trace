# v0.17.0 (2026-10-30)

Sizes a Query before running it, so one that would read too much is refused at once with narrower ways to run it, instead of timing out after 30 s, and stops small Queries stalling in ClickHouse's planning. It's still a 0.x prototype, not yet hardened for production.

## Added

- **Sizing a Query first.** EventStore estimates how much a Query would read from the Logs and bytes each file sends, without reading the Logs. In the Logs explorer and over MCP, a Query that matches text (`search`, or `contains`, `startswith`, `=~` or `matches regex` on `message`) and would read over 4 GiB is refused at once. The refusal says how much it would read, the largest range that fits, the busiest files to filter on, and a narrower Query that fits. Plain Log lists, other tables, Dashboard Charts and Monitors are never refused. [docs/logs/query-language.md](../logs/query-language.md#reading-less) has the rule.
- **The refusal in the Logs explorer** shows the estimate against the budget, a button that sets the largest range that fits, a button per busy file that adds its `file` filter, and Run anyway, which runs the Query as written. The histogram follows the Query.
- **One large Query at a time.** A heavy read, a text match over a quarter of the budget or a forced run, takes one of `logs_heavy_read_slots` (1 below 8 CPU cores, 2 from 8). Past them, the Logs explorer and MCP refuse another at once and say to run them one at a time. A new search in the Logs explorer stops the same user's older heavy read instead. Forced reads run at a lower ClickHouse priority than other Log reads. Charts and Monitors aren't capped.
- **MCP.**
  - `query_logs` takes `force`, which runs a refused Query as written, and `estimate`, which answers how much a Query would read without running it.
  - `list_projects` gives each Project's Logs and bytes an hour over the last 24 hours and how many files sent Logs, for choosing a range before a `search`.

## Fixed

- **A timed-out run's answer reaches the client.** Console's Thruster closed a request at 30 s, the same as a run's timeout, so the timeout's advice was cut off: MCP clients saw a bare `Error POSTing to endpoint:`. `deploy/docker-compose.yml` sets Thruster's `HTTP_WRITE_TIMEOUT` to 60 s.
- **Planning stalls.** A small Query naming Attributes could spend 10–80 s before reading anything, as ClickHouse 26.8 sized each Attribute in every part, reading the bucket's parts one GET at a time without the filesystem cache. EventStore's connection and the SQL users' profile set `allow_calculating_subcolumns_sizes_for_merge_tree_reading=0`. Scans that read Attributes may take about 10–20% more CPU.

## Changed

- **go-jose 4.1.6** in EventStore, fixing CVE-2026-116587.

## Upgrading from v0.16.0

`deploy/install` brings Console's new `HTTP_WRITE_TIMEOUT`. No migrations. An existing `config/event_store.yml` needs no change: the two new settings, commented in `deploy/event_store.yml`, default as above. `logs_text_match_budget_mb` (4096) sets the budget, and 0 refuses none; `logs_heavy_read_slots` sets the slots, and 0 caps none.

```bash
git fetch --tags && git checkout v0.17.0 && deploy/install
```
